## 1. Предметная область

**Industrial Asset Hub (IAH)** — распределённая информационная система для управления B2B-каталогом промышленного оборудования и связанными с ним цифровыми ресурсами.

Система предназначена для организаций, занимающихся продажей промышленной техники, оборудования и комплектующих.

Основные возможности системы:

- **Управление каталогом:** создание и редактирование товаров, характеристик, цен, категорий и сведений о поставщиках.
    
- **Управление файлами:** загрузка, хранение, скачивание, версионирование и удаление фотографий, технической документации и других файлов.
    
- **Публикация товаров:** автоматическая проверка данных и документов с последующим согласованием публикации администратором организации.
    
- **Управление доступом:** аутентификация сотрудников, разграничение полномочий и изоляция данных организаций.
    
- **Публичный каталог:** предоставление неавторизованным посетителям доступа к опубликованным товарам и разрешённым файлам.
    

Система поддерживает несколько независимых организаций. Каждая организация управляет собственными товарами и сотрудниками, при этом опубликованные товары формируют единый общедоступный каталог.

## 2. Общая архитектура

Industrial Asset Hub строится на основе **микросервисной архитектуры** с разделением ответственности между независимыми сервисами.

Система включает три основных микросервиса.

### 2.1. Catalog Service

**Catalog Service** — основной сервис системы и единая внешняя точка входа для клиентских HTTP-запросов.

Реализуется на Python с использованием FastAPI.

Основные обязанности:

- Предоставление публичного и защищённого REST API.
    
- Управление организациями, товарами, категориями и поставщиками.
    
- Работа с файлами через S3 API объектного хранилища RustFS.
    
- Хранение метаданных файлов и информации об их версиях.
    
- Обработка запросов на создание и согласование публикаций.
    
- Предоставление публичного каталога.
    
- Взаимодействие с Auth Service через gRPC.
    
- Обмен событиями с Publishing Service через Apache Kafka.
    

Catalog Service является владельцем бизнес-данных товаров и определяет их фактическую доступность в публичном каталоге.

### 2.2. Auth Service

**Auth Service** — внутренний сервис аутентификации и авторизации.

Предоставляет gRPC-интерфейс для взаимодействия с другими сервисами и не имеет публичного HTTP API.

Основные обязанности:

- Хранение учётных записей пользователей.
    
- Проверка учётных данных.
    
- Выдача и обновление JWT.
    
- Управление ролями сотрудников и их принадлежностью организациям.
    
- Проверка полномочий на выполнение защищённых операций.
    

Catalog Service выполняет локальную проверку подписи JWT, а при необходимости обращается к Auth Service для проверки актуальных разрешений.

### 2.3. Publishing Service

**Publishing Service** — внутренний сервис управления жизненным циклом публикации товаров.

Основные обязанности:

- Получение событий о запросах на публикацию из Apache Kafka.
    
- Проверка полноты и корректности данных товара.
    
- Проверка наличия, целостности и результатов проверки прикреплённых файлов.
    
- Создание заявок на согласование публикации.
    
- Обработка решений Org Admin об утверждении или отклонении.
    
- Публикация событий о результатах проверки и согласования.
    

Publishing Service хранит состояние процесса согласования, но не изменяет напрямую данные товаров в Catalog Service.

Синхронные команды согласования выполняются через gRPC. Асинхронные события передаются через Kafka.

## 3. Инфраструктурные компоненты

### 3.1. PostgreSQL

Основная реляционная СУБД системы.

Используется один экземпляр PostgreSQL, содержащий три логически независимые базы данных:

- `catalog_db` — товары, поставщики, категории, метаданные файлов.
    
- `identity_db` — пользователи, роли, членство в организациях, сессии.
    
- `publishing_db` — заявки на публикацию, результаты проверок, решения администраторов.
    

Каждый сервис владеет своей базой данных и использует отдельные учётные данные для подключения. Прямой доступ к данным других сервисов запрещён.

### 3.2. Redis

Общий инфраструктурный экземпляр Redis для кэширования.

Каждый сервис владеет собственным пространством ключей и использует отдельные права доступа.

Основные сценарии применения:

- Кэширование популярных товаров и категорий.
    
- Кэширование результатов проверок прав.
    
- Ограничение частоты запросов.
    

Redis не является источником истины для бизнес-данных.

### 3.3. Apache Kafka

Брокер событий, обеспечивающий асинхронное взаимодействие микросервисов.

На первом этапе используется для обмена событиями между Catalog Service и Publishing Service.

Kafka позволяет независимо подключать новых потребителей событий, включая будущие сервисы уведомлений, аналитики и аудита.

Надёжность публикации событий обеспечивается механизмом Transactional Outbox, а повторная доставка обрабатывается идемпотентными потребителями.

### 3.4. RustFS

S3-совместимое объектное хранилище для бинарных данных.

Используется для хранения:

- Фотографий оборудования.
    
- Видеоматериалов.
    
- Технических паспортов и инструкций.
    
- Сертификатов и коммерческих документов.
    
- Предыдущих версий файлов.
    

Catalog Service взаимодействует с RustFS через S3 API. Данные о принадлежности файлов товарам хранятся в PostgreSQL.

Для прямой передачи файлов по presigned URL предусматривается отдельный клиентский HTTPS-маршрут к S3 API. Административная консоль RustFS остаётся внутренней.

## 4. Межсервисное взаимодействие

В системе используются три способа взаимодействия:

|Механизм|Назначение|
|---|---|
|REST / HTTP|Взаимодействие внешних клиентов с Catalog Service|
|gRPC|Синхронные запросы между внутренними микросервисами|
|Apache Kafka|Асинхронная доставка событий и запуск бизнес-процессов|

Каждый сервис самостоятельно управляет собственными данными. Межсервисная согласованность обеспечивается посредством событий и контролируемых переходов состояний.

## 5. Основной бизнес-процесс

1. **Catalog Manager** создаёт товар через REST API Catalog Service.
    
2. Catalog Service сохраняет товар в PostgreSQL со статусом `DRAFT`.
    
3. Catalog Manager загружает фотографии и документы, которые сохраняются в RustFS.
    
4. Catalog Manager отправляет товар на публикацию.
    
5. Catalog Service публикует событие `PublicationRequested` в Kafka.
    
6. Publishing Service получает событие, проверяет данные и документы.
    
7. После успешной проверки заявка ожидает решения **Org Admin**.
    
8. Org Admin утверждает или отклоняет заявку через REST API Catalog Service, который обращается к Publishing Service по gRPC.
    
9. При утверждении Publishing Service публикует событие `PublicationApproved` в Kafka.
    
10. Catalog Service проверяет актуальность согласованной ревизии и переводит товар в `PUBLISHED`.
    
11. Товар становится доступен неавторизованным посетителям публичного каталога.
    

При отклонении заявка закрывается с указанием причины, а товар возвращается на доработку.

## 6. Принципы развития системы

Архитектура предусматривает независимое развитие и масштабирование сервисов.

Новые функциональные подсистемы подключаются посредством gRPC и подписки на события Kafka без необходимости изменять внутреннюю структуру существующих баз данных.

Предусмотрено дальнейшее расширение системы сервисами уведомлений, аналитики, поиска и интеграции с внешними информационными системами.

**Базовый принцип архитектуры:** каждый микросервис самостоятельно управляет своей предметной областью, синхронное взаимодействие осуществляется через gRPC, асинхронное — через Kafka, а файлы хранятся отдельно от структурированных бизнес-данных в RustFS.
