# Урок 16. Шифрование и браузерный доступ

> [!abstract] Цель урока
> Разделить защиту канала, шифрование сохранённых объектов и правила браузерного доступа; проверить возможности своей версии RustFS.

**Предварительные знания:** политики доступа, подпись запросов, presigned URLs.  
**Практическая среда:** лаборатория RustFS, AWS CLI, `curl`, браузер.  
**Критерий завершения:** получены наблюдения о шифровании и CORS; понятно, какую угрозу устраняет каждый механизм.  
**Время чтения:** до 5 минут, практика отдельно.

---

## 1. Три независимых решения

Представь загрузку фотографии прямо из браузера по подписанной ссылке. TLS защищает байты при передаче. Серверное шифрование защищает сохранённые данные. CORS определяет, разрешит ли браузер странице работать с ответом другого origin. Политики и подпись при этом проверяют право выполнить операцию.

Зашифрованный объект может быть доступен посторонним, а подписанная ссылка — не работать из JavaScript из-за CORS.

## 2. TLS: границы защищённого канала

HTTPS использует TLS: клиент проверяет сертификат сервера, стороны защищают соединение от чтения и изменения трафика. Подпись SigV4 сама по себе не шифрует тело запроса.

Если TLS завершается на reverse proxy, дальше начинается отдельный участок связи до RustFS. Решение о его защите принимают отдельно. Сертификат должен соответствовать имени endpoint; его проверка подтверждает подлинность сервера.

Локальный HTTP endpoint лаборатории удобен для изучения API, но не показывает защищённую передачу. Не отправляй через него реальные секретные данные.

## 3. SSE: кто распоряжается ключами

**Server-side encryption** означает, что сервис шифрует объект при сохранении и расшифровывает при разрешённом чтении. 

- **SSE-S3:** ключами управляет сервис; API обозначает режим значением `AES256`.
- **SSE-KMS:** используется служба управления ключами; в AWS это AWS KMS, с разрешениями и аудитом.
- **SSE-C:** клиент передаёт собственный ключ серверу при записи и чтении. Ключ нельзя терять или помещать в журналы; для передачи необходим HTTPS.

В AWS новые объекты автоматически получают SSE-S3. SSE-C по умолчанию отключён для новых обычных бакетов и требует явного разрешения. Эти настройки AWS нельзя переносить на RustFS по аналогии.

> [!important] Доступность ключей — часть доступности данных
> Сохранённые байты недостаточны для восстановления зашифрованного объекта: нужен доступ к ключам. План восстановления должен охватывать обе зависимости.

## 4. Что проверять в RustFS

Официальная документация описывает SSE-S3, SSE-C и SSE-KMS; для KMS перечислены Local, Vault KV2 и Vault Transit. Название SSE-KMS не доказывает интеграцию с AWS KMS.

Для описанного RustFS режима SSE-S3 требуется настроенная KMS. Принятое правило шифрования бакета ещё не доказывает работоспособность: запись может завершиться ошибкой, если KMS недоступна. Проверка включает запись, чтение и сравнение байтов на установленной сборке.

## 5. CORS: разрешение браузеру

**Origin** состоит из схемы, имени хоста и порта. Поэтому страница на `http://localhost:3000` и API на `http://localhost:9000` имеют разные origin.

Браузер может предварительно отправить `OPTIONS`, проверяя разрешение метода и заголовков. Правило CORS задаёт допустимые origin, методы и заголовки; `ExposeHeaders` определяет, какие дополнительные заголовки ответа сможет прочитать JavaScript.

AWS предоставляет настройки CORS бакета. RustFS также документирует общую настройку origin для S3 listener — `RUSTFS_CORS_ALLOWED_ORIGINS`; для Console существует отдельная переменная. 

> [!warning] CORS не выдаёт права на объект
> Он не заменяет авторизацию. Успех `curl` не доказывает, что браузер разрешит странице прочитать ответ.

## 6. Короткая практика и самостоятельные задания

Используй отдельный тестовый бакет `lesson16`. Подготовь профиль AWS CLI и `hello.txt`. Зафиксируй версию RustFS.

```fish
aws --endpoint-url http://127.0.0.1:9000 s3api put-object --bucket lesson16 --key encrypted.txt --body hello.txt --server-side-encryption AES256
```

Если запись прошла, выполни знакомые `HeadObject` и `GetObject`: проверь режим шифрования в ответе и совпадение скачанных байтов. При ошибке запиши код и проверь требования KMS по документации своей версии. Ошибка конфигурации не опровергает поддержку API.

Для CORS добавь в `environment` Compose значение `RUSTFS_CORS_ALLOWED_ORIGINS: "http://localhost:3000"`, примени изменение через `docker compose up -d`, затем проверь:

```fish
curl -i -H 'Origin: http://localhost:3000' http://127.0.0.1:9000/
```

Повтори с другим origin. Сравни `Access-Control-Allow-Origin` отдельно от HTTP-статуса. Полный браузерный сценарий проверяется реальным запросом страницы.

**Самостоятельно:** объясни, почему успешный GET не доказывает шифрование диска; опиши последствия потери KMS; назови проверки для браузерного PUT по presigned URL.
