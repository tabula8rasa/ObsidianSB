# Урок 13. Как хранилище проверяет подпись запроса

> [!abstract] Цель урока
> Понять назначение ключей доступа, разобрать AWS Signature Version 4 и отличить неверную подпись от недостаточных прав.

**Предварительные знания:** HTTP, AWS CLI, политики доступа из урока 12.  
**Практическая среда:** локальный RustFS, терминал `fish`, настроенный профиль AWS CLI.  
**Критерий завершения:** ты находишь поля подписи в запросе и сравниваешь успешный вызов с вызовом, подписанным неверным секретом.  
**Время чтения:** до 5 минут, практика отдельно.

---

## 1. Две разные проверки

Аутентификация отвечает на вопрос: «Кто отправил запрос и подтверждено ли владение его реквизитами?» Авторизация проверяет, разрешено ли этой личности нужное действие над ресурсом.

Правильная подпись не даёт дополнительных прав. Пользователь с доступом только к одному бакету не сможет читать другой, даже если запрос подписан безупречно. И наоборот: широкая политика не исправляет подпись, вычисленную неверным секретом.

При разборе ошибки проверяй не только HTTP-статус, но и код ошибки S3 в ответе. Один статус `403` недостаточен для диагноза.

## 2. Access Key и Secret Key

**Access Key ID** — идентификатор учётных данных. **Secret Access Key** — секрет, которым клиент подтверждает владение этими данными. Он используется при вычислении подписи, но не передаётся в заголовке запроса.

Сервер получает идентификатор, находит соответствующие реквизиты и проверяет подпись. Это позволяет обнаружить изменение подписанных элементов запроса по дороге.

> [!warning] Подпись не шифрует запрос
> Для защиты содержимого и служебных заголовков нужен HTTPS. HTTP используем только в локальной лаборатории на `127.0.0.1`. Секреты и диагностические журналы не публикуем.

В RustFS административную пару задают `RUSTFS_ACCESS_KEY` и `RUSTFS_SECRET_KEY`. Для повседневных опытов используй ограниченного пользователя из предыдущего урока.

## 3. Что связывает Signature Version 4

SigV4 приводит запрос к согласованному представлению — **canonical request**. Оно учитывает HTTP-метод, путь, параметры запроса, выбранные заголовки и представление тела для подписания. Затем клиент строит строку для подписи и вычисляет HMAC-SHA256 производным ключом, связанным с датой, регионом и сервисом.

В заголовке `Authorization` важны три поля:

- `Credential`: Access Key ID и область подписи вида `дата/регион/s3/aws4_request`.
- `SignedHeaders`: имена заголовков, включённых в подпись.
- `Signature`: результат вычисления подписи.

Время запроса обычно передаётся в `x-amz-date`. Рассинхронизация часов мешает проверке. Прокси, меняющий подписанный `Host` или путь, тоже способен нарушить подпись.

Для тела S3 допускает разные режимы, включая `UNSIGNED-PAYLOAD`; поэтому наличие SigV4 само по себе не означает проверку хеша всех передаваемых байтов. ETag объекта — другая сущность.

## 4. Временные учётные данные

В AWS временный набор, выдаваемый STS, содержит Access Key ID, Secret Access Key, **Session Token** и срок окончания действия. При подписанном обращении к S3 токен передают в `x-amz-security-token`. Пары ключей без соответствующего токена недостаточно.

После истечения срока приложение получает новый набор. Архитектурная выгода — отсутствие необходимости раздавать приложениям постоянные секреты; срок действия и права остаются отдельными ограничениями.

Документация RustFS описывает STS `AssumeRole` и временные реквизиты. Это не обещание полной совместимости со всеми сценариями AWS IAM: доступность конкретного потока проверяй на своей версии. В сегодняшней практике STS не требуется.

## 5. Практика: правильный и неправильный секрет

Пусть профиль называется `rustfs`; замени имя своим. Выбери существующий бакет, который пользователь вправе перечислять. Команда только читает список:

```fish
aws --profile rustfs --endpoint-url http://127.0.0.1:9000 \
  s3api list-objects-v2 --bucket s3-course-lesson1 --max-keys 1 \
  --debug 2>sigv4-debug.log
```

В локальном журнале найди `CanonicalRequest`, `StringToSign` и поля `Authorization`. Сопоставь метод, путь и область подписи. Маскирование отдельных значений зависит от версии клиента.

Теперь подставь тот же идентификатор и заведомо неверный секрет только для одного процесса:

```fish
env AWS_ACCESS_KEY_ID=(aws configure get aws_access_key_id --profile rustfs) \
  AWS_SECRET_ACCESS_KEY=deliberately-wrong AWS_SESSION_TOKEN= \
  aws --endpoint-url http://127.0.0.1:9000 --region us-east-1 \
  s3api list-objects-v2 --bucket s3-course-lesson1 --max-keys 1
```

Регион должен совпадать с успешным запросом. Ожидай отказ проверки подписи, обычно `SignatureDoesNotMatch`. Запиши фактический код. Если первый вызов неуспешен, сначала исправь профиль, бакет и права: иначе сравнение неоднозначно. После разбора удали диагностический журнал.

## 6. Самостоятельные задания

3. Опиши, что должен обновить клиент после истечения временной сессии.
