# RustFS — управление доступом и безопасность

В RustFS модель управления доступом включает четыре основные сущности: **Policies**, **Access Keys**, **Users** и **User Groups**. Отдельно необходимо учитывать **Root Account** и **STS**.

> [!important] Ключевое различие
> Создание **Access Key (Service Account)** и создание **IAM User** — разные операции. При обычном **Key Login** веб-консоль RustFS вызывает STS `AssumeRole`. Это важно при диагностике ошибок входа с дочерними ключами.

## 1. Policies — определение прав доступа

Policy — именованный JSON-документ, описывающий разрешённые и запрещённые действия над ресурсами RustFS.

Условная модель записи:

```text
Name = "lesson12-readonly"
Document = { ... JSON ... }
```

Пример JSON-политики:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": ["s3:GetObject"],
      "Resource": ["arn:aws:s3:::lesson12-private/*"]
    }
  ]
}
```

Здесь три основных элемента:

- `Effect` — разрешить (`Allow`) или запретить (`Deny`).
- `Action` — какие действия регулируются, например `s3:GetObject`, `s3:PutObject`, `admin:CreateUser`.
- `Resource` — к каким ресурсам применяется правило.

Важное дополнение: policy регулирует не только доступ к объектам и бакетам. RustFS также поддерживает административные разрешения `admin:*`, STS-разрешения и KMS-разрешения.

### Как RustFS принимает решение

Для обычного IAM User сервер проверяет применимые политики.

1. Если существует подходящий явный `Deny`, операция запрещена.
2. Если есть подходящий `Allow` и отсутствует применимый явный запрет, операция разрешена с учётом остальных действующих ограничений.
3. Если подходящего `Allow` нет, операция запрещена по умолчанию.

Это означает, что не нужно явно запрещать всё, что не разрешено.

Ещё одно важное свойство: создание политики ничего не разрешает само по себе. Её необходимо назначить пользователю или группе. Для дочерних Access Keys действует отдельная схема наследования, которую разберём дальше.

Отдельно существуют Bucket Policies: они привязаны к конкретному бакету, а не к IAM User. Поэтому итоговые права зависят и от политик идентичности, и от применимых ресурсных политик.

## 2. Access Keys — дополнительные ключи доступа

Access Keys в этом разделе Console — это service accounts: дочерние ключи, связанные с уже существующей идентичностью. Это не самостоятельные пользователи и не обязательно временные ключи.

Когда ты авторизован под основным администратором и создаёшь Access Key, RustFS создаёт дополнительную пару ключей, принадлежащую родительской идентичности.

### Поля Access Key в Console

| Поле                    | Назначение                                     |
| ----------------------- | ---------------------------------------------- |
| Access Key              | Публичный идентификатор пары ключей            |
| Secret Key              | Секрет для формирования SigV4-подписи          |
| Expiry                  | Необязательная дата окончания действия         |
| Name                    | Человекочитаемое название                      |
| Description             | Описание назначения                            |
| Use main account policy | Наследование политик родительской идентичности |

Не все перечисленные параметры обязательны. Сами ключи RustFS умеет генерировать автоматически, а Expiry, Name и Description в API необязательны.

Если Expiry не задан, дата автоматического окончания действия отсутствует.

### Как работают политики для Access Keys

Рассмотрим два случая.

**Случай А.** `Use main account policy` включён.

Дочерний ключ наследует разрешения родителя. Если родитель — администратор, ключ получает его права.

**Случай Б.** `Use main account policy` выключен и задана отдельная policy.

Документ политики для service account является дополнительным ограничением. Он не расширяет права родителя.

Например, если родитель умеет читать и записывать объекты, а дочернему ключу разрешён только `s3:GetObject`, то дочерний ключ сможет читать, но не записывать.

Это пересечение разрешений, а не их объединение.

### Почему дочерний административный Access Key не проходит Key Login?

В исходном коде веб-консоли RustFS обычный Key Login реализован следующим образом:

```text
Key Login (Access Key + Secret Key)
    ↓
STS AssumeRole (запрос временных credentials)
    ↓
Временные credentials (AccessKeyId + SecretAccessKey + SessionToken)
    ↓
Работа с Console (SigV4-подпись последующих запросов)
```

В официальной документации RustFS указано: service accounts не могут выполнять `AssumeRole`. Этот запрет относится к типу учётных данных, а не к отсутствию права `admin:*`.

Следовательно, получаем такую ситуацию:

- Основные ключи IAM User или root могут использоваться для предусмотренного сервером вызова `AssumeRole`.
- Ключи service account могут подписывать разрешённые S3-запросы.
- Ключ service account не может инициировать новую STS-сессию через `AssumeRole`, даже когда родитель обладает административными разрешениями.

> [!warning] Диагностика входа
> Запрет `AssumeRole` для service account объясняет отказ в Key Login даже при административных разрешениях. Для окончательной диагностики конкретного сбоя нужны версия сервера и текст ошибки.

Проверка ключа через AWS CLI:

```bash
aws configure --profile test-service-key
```

Ввести созданную пару ключей и выполнить:

```bash
aws --profile test-service-key \
  --endpoint-url http://127.0.0.1:9000 \
  s3api list-buckets
```

Если команда выполняется успешно, значит пара работает для этой S3-операции. Это не означает, что с ней получится пройти Key Login в Console.

## 3. Users — самостоятельные учётные записи

### 3.1. За что отвечает User?

User — это самостоятельная IAM-идентичность внутри RustFS, которой назначаются собственные credentials и политики доступа.

В отличие от Access Keys, пользователь не является дочерним ключом другого пользователя.

Пример — пользователь `lesson12-reader`:

| Атрибут | Значение |
| --- | --- |
| IAM User | `lesson12-reader` |
| Access Key | `lesson12-reader` |
| Secret Key | Секрет пользователя |
| Policy | `lesson12-readonly` |
| Groups | Нет |

Этот пользователь имеет собственную идентичность, собственный секрет и собственные разрешения.

Ключевое различие:

- User — самостоятельная учётная запись с собственными политиками.
- Access Key из раздела Access Keys — дополнительная пара credentials, связанная с родительским аккаунтом.

### 3.2. Username = Access Key, а Password = Secret Key?

Да, для встроенных IAM Users в RustFS это верное соответствие.

В документации API создания пользователя используется следующий запрос:

```http
PUT /rustfs/admin/v3/add-user?accessKey=alice
```

Тело:

```json
{
  "secretKey": "alice-secret",
  "status": "enabled"
}
```

То есть:

| В интерфейсе Users       | В S3-аутентификации               |
| ------------------------ | --------------------------------- |
| Username: `alice`        | Access Key ID: `alice`            |
| Password: `alice-secret` | Secret Access Key: `alice-secret` |

Но важно правильно понимать назначение пароля.

В RustFS Secret Key используется для криптографического подписания запросов по AWS Signature Version 4. Это не отдельный пароль веб-интерфейса, как в AWS Management Console.

Различие с AWS: в AWS IAM пароль для входа в веб-консоль и программные Access Keys — отдельные механизмы. Не следует переносить эту модель на встроенных пользователей RustFS.

### 3.3. Где пользователь, под которым я захожу в Console?

Это отдельная сущность — Root Account.

Root Account не создаётся в разделе Users и не обязан отображаться в списке IAM-пользователей.

Его credentials задаются при запуске сервера:

```dotenv
RUSTFS_ACCESS_KEY=admin
RUSTFS_SECRET_KEY=your-strong-secret
```

Если переменные не заданы, RustFS использует стандартную пару `rustfsadmin` / `rustfsadmin`.

Поэтому отсутствие пользователя `rustfs-console` в Users — нормальная ситуация. Console является клиентским интерфейсом; отдельная учётная запись с таким названием ей не требуется.

Отличие root от обычного IAM User:

- Root создаётся конфигурацией сервера.
- Root обходит проверку IAM identity policies, обладая привилегиями владельца.
- При этом применимые Bucket Policies могут ограничивать даже root при S3-операциях; документация предусматривает специальные исключения для управления политикой бакета.
- Обычный User получает права через назначенные ему политики и группы.

Для работы с кластером рекомендуется использовать IAM Users с минимально необходимыми правами, а root оставлять для первоначальной настройки и восстановления доступа.

## 4. User Groups — групповые политики

User Group — это именованное объединение IAM Users, позволяющее назначать политики сразу всем его участникам.

Например, у нас есть три сотрудника, которым необходимо читать содержимое бакета.

Вместо того чтобы каждому назначать `lesson12-readonly`, создаём группу `readers` и назначаем политику ей.

```text
Group: readers
├── Policy: lesson12-readonly
└── Users: alice, bob, charlie
```

Важные особенности:

- Пользователь получает все разрешения своих непосредственных политик и политик всех групп, в которых состоит.
- Права `Allow` объединяются, но применимый явный `Deny` имеет приоритет.
- Изменение политики группы влияет на всех её участников.
- Root и временные STS-идентичности нельзя добавлять в группы.

И отдельно: User Group — не механизм аутентификации. У группы нет собственных Access Key и Secret Key для выполнения S3-запросов.

## 5. STS — временные credentials и STS Login

STS расшифровывается как Security Token Service.

Это механизм выдачи временных учётных данных на основании существующей идентичности.

### 5.1. Где создаётся STS-сессия?

В отличие от Users и Access Keys, STS-сессию обычно не создают вручную через административное меню.

Клиент вызывает STS API на S3 endpoint RustFS.

RustFS поддерживает две операции:

- `AssumeRole` — получение временных credentials по существующей долгосрочной паре ключей.
- `AssumeRoleWithWebIdentity` — получение временных credentials через внешний OIDC-токен.

При `AssumeRole` запрос подписывается долгосрочным Secret Key. Сервер проверяет идентичность и право на операцию, после чего выдаёт временный набор:

```json
{
  "AccessKeyId": "TEMP_ACCESS_KEY",
  "SecretAccessKey": "TEMP_SECRET_KEY",
  "SessionToken": "TEMP_SESSION_TOKEN",
  "Expiration": "2026-10-21T12:00:00Z"
}
```

Это иллюстрация структуры, а не реальные credentials или ответ API. RustFS возвращает их в XML-ответе STS.

Срок действия STS credentials в RustFS — от 15 минут до 12 часов, по умолчанию 1 час.

### 5.2. Где делается STS Login?

Форма **STS Login** в Console запрашивает:

| Поле Console      | Что вставлять               |
| ----------------- | --------------------------- |
| STS Username      | Временный `AccessKeyId`     |
| STS Key           | Временный `SecretAccessKey` |
| STS Session Token | Выданный `SessionToken`     |

Важно: это не первоначальные Username и Password пользователя. Это три значения, полученные от STS.

Сам процесс выглядит так:

```text
IAM User (долгосрочная пара ключей)
    ↓
STS AssumeRole (проверка запроса сервером RustFS)
    ↓
Временные credentials (Access Key + Secret Key + Session Token)
    ↓
STS Login в Console (передача трёх значений)
```

Таким образом, создание STS credentials и вход с ними — разные действия.

## 6. Итоговая модель

| Сущность                     | Основная задача                                                    |
| ---------------------------- | ------------------------------------------------------------------ |
| Policy                       | Определяет разрешения и запреты                                    |
| Access Key (Service Account) | Предоставляет дополнительные credentials родительской идентичности |
| User                         | Создаёт самостоятельную IAM-идентичность                           |
| User Group                   | Назначает общие политики нескольким пользователям                  |
| STS                          | Выдаёт временные credentials существующей идентичности             |

> [!summary] Главный принцип
> **Кто выполняет запрос**, **чем подтверждается идентичность** и **что разрешено делать** — три разных вопроса. Root, IAM User, Service Account и STS-сессия предоставляют разные способы идентификации, а политики определяют допустимые операции с учётом наследования и ограничений.
