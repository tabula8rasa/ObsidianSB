# `git fetch` vs `git pull`

```text
git fetch = скачать изменения в .git
git pull  = git fetch + встроить изменения в текущую ветку
```

`fetch` обновляет информацию об удалённом репозитории, но не трогает твои файлы. `pull` после скачивания меняет текущую ветку, индекс и рабочую директорию.

---

## Исходная ситуация

```text
A──B──C  main
       \
        D──E  origin/main
```

Локальный `main` указывает на `C`, а на сервере уже есть `D` и `E`. Локальный Git об этом пока не знает: `refs/remotes/origin/main` всё ещё указывает на `C`.

---

## Что делает `git fetch`

```bash
git fetch origin
```

**Что меняется в `.git`:**

- `objects/`: новые коммиты, деревья и blob'ы (обычно упакованные в `.pack` и `.idx`).
- `refs/remotes/origin/main`: `C → E`. Это не ветка на сервере, а локальная ссылка на её последнее известное состояние.
- `FETCH_HEAD`: что именно только что скачано (после `fetch` можно сделать `git merge FETCH_HEAD`).
- reflog удалённой ветки: запись `C -> E`.

**Что не меняется:** рабочая директория, `.git/index`, `refs/heads/main`, `HEAD`.

`git status` покажет `Your branch is behind 'origin/main' by 2 commits`, но файлы останутся прежними.

---

## Что делает `git pull`

```text
git pull           ≈ git fetch + git merge origin/main
git pull --rebase  ≈ git fetch + git rebase origin/main
```

### 1. Fast-forward (локальных коммитов нет)

```text
A──B──C──D──E
            ↑
     main, origin/main
```

- `refs/heads/main`: `C → E`, плюс запись в reflog.
- `.git/HEAD` текстово не меняется (`ref: refs/heads/main`), но теперь разрешается в `E`.
- `.git/index` обновляется под дерево `E`.
- Рабочая директория переходит из состояния `C` в `E`: файлы создаются, меняются, удаляются, обновляются права и симлинки.

### 2. Ветки разошлись (есть локальные коммиты)

```text
        D──E
       /    \
A──B──C      M  main
       \    /
        X──Y
```

Создаётся merge-коммит `M`. `ORIG_HEAD` хранит положение ветки до операции (`Y`), так что откатиться можно через `git reset --hard ORIG_HEAD`.

### 3. Конфликт

`pull` останавливается на этапе merge.

- В `.git` появляются `MERGE_HEAD` (что вливаем), `MERGE_MSG` (будущее сообщение коммита) и `MERGE_MODE`.
- В `.git/index` у конфликтующего файла три версии (смотреть через `git ls-files --stage`): stage 1 — общий предок, stage 2 — наша, stage 3 — входящая.
- В файле появляются маркеры:

```text
<<<<<<< HEAD
локальная версия
=======
удалённая версия
>>>>>>> origin/main
```

К этому моменту `origin/main` уже обновлён и объекты скачаны, но merge ещё не завершён.

### 4. `git pull --rebase`

```text
A──B──C──D──E──X'──Y'
                  main
```

- Локальные `X` и `Y` переносятся поверх `E`. У `X'` и `Y'` новые хеши, потому что изменились родители.
- Старые `X` и `Y` остаются в reflog, пока их не удалит `git gc`.
- Во время rebase существует `.git/rebase-merge/` или `.git/rebase-apply/`.

---

## Сравнение

|Область|`git fetch`|`git pull`|
|---|---|---|
|`.git/objects/`|Загружает новые объекты|То же, плюс возможные merge/rebase-коммиты|
|`FETCH_HEAD`, `refs/remotes/origin/*`|Обновляет|Обновляет|
|`refs/heads/main`|Не меняет|Обычно меняет|
|`.git/index`|Не меняет|Обновляет|
|Рабочая директория|Не меняет|Обновляет файлы|
|Конфликты|Невозможны|Возможны|
|Новые хеши локальных коммитов|Нет|При `--rebase`|
