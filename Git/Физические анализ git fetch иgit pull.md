Главная разница:

```text
git fetch = скачать изменения в .git
git pull  = git fetch + встроить изменения в текущую ветку
```

То есть `fetch` обновляет информацию об удалённом репозитории, но не меняет твои файлы. `pull` после скачивания пытается изменить текущую ветку, индекс и рабочую директорию.

---

# До выполнения команд

Представим такую историю:

```text
A──B──C  main
       \
        D──E  origin/main
```

Локальная ветка `main` указывает на `C`, а на сервере уже появились коммиты `D` и `E`.

Однако локальный Git ещё может об этом не знать. Внутри `.git` хранится старое состояние:

```text
.git/refs/heads/main
C

.git/refs/remotes/origin/main
C
```

Здесь:

- `refs/heads/main` — локальная ветка `main`;
    
- `refs/remotes/origin/main` — локальное представление удалённой ветки;
    
- реальная ветка на GitHub или GitLab физически находится на сервере.
    

---

# Что делает `git fetch`

```bash
git fetch origin
```

Git связывается с сервером, определяет отсутствующие объекты и скачивает их.

## Что меняется в `.git`

### 1. Загружаются новые Git-объекты

Новые коммиты, деревья и файлы попадают в:

```text
.git/objects/
```

Например, Git может сохранить их как отдельные объекты:

```text
.git/objects/ab/cdef...
.git/objects/42/1234...
```

Но чаще при загрузке с удалённого репозитория объекты приходят в упакованном виде:

```text
.git/objects/pack/pack-abc123.pack
.git/objects/pack/pack-abc123.idx
```

Файл `.pack` содержит сами объекты:

- `commit`;
    
- `tree`;
    
- `blob`;
    
- `tag`.
    

Файл `.idx` содержит индекс для быстрого поиска объектов внутри `.pack`.

---

### 2. Обновляется remote-tracking ветка

Файл или packed-ссылка:

```text
.git/refs/remotes/origin/main
```

начинает указывать на новый коммит:

```text
E
```

Теперь локальный Git знает:

```text
main        -> C
origin/main -> E
```

История становится такой:

```text
A──B──C  main
       \
        D──E  origin/main
```

Важно: `origin/main` — не настоящая ветка на сервере. Это локальная ссылка, которая хранит последнее известное состояние серверной ветки.

---

### 3. Обновляется `FETCH_HEAD`

Git записывает информацию о загруженных ветках в:

```text
.git/FETCH_HEAD
```

Упрощённо содержимое может выглядеть так:

```text
<hash E>    branch 'main' of github.com:user/project
```

`FETCH_HEAD` позволяет Git понять, какие коммиты только что были получены.

Например, после `fetch` можно выполнить:

```bash
git merge FETCH_HEAD
```

---

### 4. Обновляется reflog удалённой ветки

При включённом reflog может измениться:

```text
.git/logs/refs/remotes/origin/main
```

Там записывается перемещение ссылки:

```text
C -> E
```

---

## Что не меняется при `git fetch`

Не изменяются:

```text
рабочая директория
.git/index
.git/refs/heads/main
HEAD
```

То есть файлы проекта остаются такими же, как до команды.

Если выполнить:

```bash
git status
```

Git может сообщить:

```text
Your branch is behind 'origin/main' by 2 commits
```

Но содержимое файлов не поменяется.

---

# Что делает `git pull`

Обычный:

```bash
git pull
```

приблизительно равен:

```bash
git fetch
git merge origin/main
```

Но поведение зависит от настроек. Вместо merge может использоваться rebase:

```bash
git pull --rebase
```

что приблизительно равно:

```bash
git fetch
git rebase origin/main
```

---

# `git pull` с fast-forward

Предположим, локальных коммитов после `C` нет:

```text
A──B──C  main
       \
        D──E  origin/main
```

После `git pull` Git может просто передвинуть локальную ветку:

```text
A──B──C──D──E
            ↑
     main, origin/main
```

Это называется **fast-forward**.

## Что меняется в `.git`

### Локальная ветка

Было:

```text
.git/refs/heads/main
C
```

Стало:

```text
.git/refs/heads/main
E
```

### Reflog локальной ветки

Обновляется:

```text
.git/logs/refs/heads/main
```

Там записывается перемещение:

```text
C -> E
```

### `HEAD`

Обычно `.git/HEAD` физически не меняется:

```text
ref: refs/heads/main
```

`HEAD` продолжает указывать на ветку `main`. Но ветка `main` теперь указывает на другой коммит, поэтому фактически `HEAD` тоже разрешается в `E`.

---

## Что меняется в индексе

Файл:

```text
.git/index
```

обновляется под дерево коммита `E`.

Индекс — это промежуточное состояние между последним коммитом и рабочей директорией. После успешного `pull` он обычно соответствует новому коммиту.

---

## Что меняется в рабочей директории

Git сравнивает дерево старого коммита `C` с деревом нового коммита `E` и обновляет файлы:

```text
рабочая директория: состояние C -> состояние E
```

Git может:

- создать новые файлы;
    
- изменить существующие;
    
- удалить файлы;
    
- изменить права, например executable-бит;
    
- создать или изменить символические ссылки.
    

---

# `git pull`, когда есть локальные коммиты

Представим:

```text
        D──E  origin/main
       /
A──B──C
       \
        X──Y  main
```

Локальная и удалённая ветки разошлись.

При обычном `git pull` Git сначала выполнит `fetch`, затем `merge`.

Результат:

```text
        D──E
       /    \
A──B──C      M  main
       \    /
        X──Y
```

Создаётся merge-коммит `M`.

## Дополнительные изменения в `.git`

Могут обновиться:

```text
.git/refs/heads/main
.git/logs/refs/heads/main
.git/index
.git/ORIG_HEAD
```

`ORIG_HEAD` обычно хранит положение ветки до операции:

```text
Y
```

Это позволяет вернуться назад:

```bash
git reset --hard ORIG_HEAD
```

При успешном merge временные служебные файлы удаляются.

---

# Что происходит при конфликте

Когда Git не может автоматически объединить изменения, `pull` останавливается на этапе merge.

В `.git` появляются служебные файлы:

```text
.git/MERGE_HEAD
.git/MERGE_MSG
.git/MERGE_MODE
```

## `MERGE_HEAD`

Содержит хеш коммита, который Git пытается влить:

```text
E
```

## `MERGE_MSG`

Содержит будущее сообщение merge-коммита:

```text
Merge remote-tracking branch 'origin/main'
```

## Индекс при конфликте

В `.git/index` для конфликтующего файла могут одновременно храниться три версии:

```text
stage 1 — общий предок
stage 2 — наша версия
stage 3 — входящая версия
```

Посмотреть их можно командой:

```bash
git ls-files --stage
```

Например:

```text
100644 <hash-base>   1 file.txt
100644 <hash-ours>   2 file.txt
100644 <hash-theirs> 3 file.txt
```

---

## Рабочая директория при конфликте

Файл может получить маркеры:

```text
<<<<<<< HEAD
локальная версия
=======
удалённая версия
>>>>>>> origin/main
```

В этот момент:

- `origin/main` уже обновлён;
    
- новые объекты уже скачаны;
    
- локальная ветка `main` ещё не завершила merge;
    
- рабочая директория изменена;
    
- индекс содержит конфликтующие состояния.
    

---

# `git pull --rebase`

Команда:

```bash
git pull --rebase
```

выполняет:

```bash
git fetch
git rebase origin/main
```

Было:

```text
        D──E  origin/main
       /
A──B──C
       \
        X──Y  main
```

Git временно убирает `X` и `Y`, переносит ветку на `E`, а затем заново применяет локальные изменения:

```text
A──B──C──D──E──X'──Y'
                  main
```

Коммиты `X'` и `Y'` имеют новые хеши, потому что у них изменились родители.

## Что меняется физически

В `.git/objects` создаются новые commit-объекты:

```text
X'
Y'
```

Старые `X` и `Y` сразу не удаляются. Некоторое время они могут быть доступны через reflog, а позже их может удалить сборщик мусора:

```bash
git gc
```

Во время rebase появляются служебные директории:

```text
.git/rebase-merge/
```

или:

```text
.git/rebase-apply/
```

Рабочая директория и индекс обновляются при применении каждого локального коммита.

# Сравнение на уровне файлов

|Область|`git fetch`|`git pull`|
|---|---|---|
|`.git/objects/`|Загружает новые объекты|Загружает новые объекты и может создать merge/rebase-коммиты|
|`.git/objects/pack/`|Может добавить `.pack` и `.idx`|То же самое|
|`.git/FETCH_HEAD`|Обновляет|Обновляет|
|`refs/remotes/origin/*`|Обновляет|Обновляет|
|`refs/heads/main`|Не меняет|Обычно меняет|
|`.git/HEAD`|Обычно не меняет|Обычно текст файла не меняется, но начинает разрешаться в новый коммит|
|`.git/index`|Не меняет|Обновляет|
|Рабочая директория|Не меняет|Обновляет файлы|
|Merge-коммит|Не создаёт|Может создать|
|Новые хеши локальных коммитов|Нет|Возможны при `--rebase`|
|Конфликты в файлах|Обычно невозможны|Возможны|

# Самая важная схема

```text
git fetch
    │
    ├── скачивает объекты в .git/objects
    ├── обновляет origin/main
    └── не трогает main, index и рабочие файлы
```

```text
git pull
    │
    ├── выполняет git fetch
    └── выполняет merge или rebase
            │
            ├── изменяет локальную ветку
            ├── изменяет .git/index
            ├── изменяет рабочую директорию
            └── может создать новые commit-объекты
```

# Практическое правило

Когда хочешь сначала безопасно посмотреть изменения:

```bash
git fetch
git log --oneline --graph --decorate main..origin/main
git diff main..origin/main
```

И только потом встроить их:

```bash
git merge origin/main
```

> `git fetch` почти всегда безопасен для незакоммиченных файлов, потому что не меняет рабочую директорию. `git pull` уже может изменить файлы, остановиться из-за локальных изменений или привести к конфликтам.
