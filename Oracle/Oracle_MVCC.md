## Принцип
- Oracle реализует **MVCC через UNDO и SCN**, а не хранит последовательные версии строк в основной таблице.
- **UPDATE** изменяет текущую строку в блоке данных и создаёт **UNDO-записи** для отмены изменений и согласованного чтения.
- **SCN (System Change Number)** задаёт логическую точку согласованности данных.
- Если блок содержит изменения, которые не должны быть видны запросу, Oracle создаёт **consistent read (CR) copy** блока и реконструирует его состояние на нужный SCN с помощью UNDO.
- Чтение не блокирует обычную запись, а запись не блокирует обычное согласованное чтение.

## Время жизни версий
- **Фиксированной глубины истории нет**: старые состояния доступны, пока сохранены необходимые UNDO-записи.
- `UNDO_RETENTION` задаёт целевое время удержания, **не жёсткий TTL**. При нехватке места UNDO завершённых транзакций может переиспользоваться раньше; `RETENTION GUARANTEE` меняет это поведение.
- UNDO активных транзакций сохраняется для возможности отката.
- Если нужная UNDO-история недоступна, длинный запрос может завершиться **ORA-01555: snapshot too old**.

## Изоляция
- `READ COMMITTED` (по умолчанию): **отдельный снимок для каждого SQL-оператора**.
- `SERIALIZABLE`: **снимок на уровне транзакции**; при конфликте записи возможна `ORA-08177`.
- Отдельного уровня `REPEATABLE READ` в Oracle нет.

## Отличие от PostgreSQL
| PostgreSQL | Oracle |
|---|---|
| `UPDATE` создаёт новую версию строки в heap | Изменяется текущая строка; история реконструируется по UNDO |
| Старые версии убирает `VACUUM` | UNDO переиспользуется автоматически |
| Риск MVCC-bloat таблиц и индексов | Нет аналогичного накопления dead tuples; остаются другие проблемы использования места |
| Долгие снимки мешают очистке версий | При утрате UNDO долгий запрос рискует получить `ORA-01555` |
