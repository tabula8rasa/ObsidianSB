## Что такое HTTP

HTTP — прикладной протокол request/response.

Он определяет:

- методы: `GET`, `POST`, `PUT`, `DELETE`, ...;
- URL/path;
- headers;
- body;
- status codes;
- правила формирования сообщений.

HTTP/1.x обычно работает поверх TCP.

```text
HTTP
 ↓
TCP
 ↓
IP
```

Для HTTPS:

```text
HTTPS
 ↓
TLS
 ↓
TCP
 ↓
IP
```

---

# HTTP/1.0

HTTP/1.0 был относительно простой моделью:

```text
открыть TCP
↓
отправить request
↓
получить response
↓
закрыть TCP
```

Например:

```http
GET /cat.jpg HTTP/1.0
Host: example.com
```

Ответ:

```http
HTTP/1.0 200 OK
Content-Type: image/jpeg
Content-Length: 53242

<binary body>
```

---

# Главная проблема HTTP/1.0

Современная веб-страница состоит из множества ресурсов:

```text
HTML
CSS
JavaScript
images
fonts
API calls
...
```

Если для каждого ресурса создавать новое TCP-соединение, приходится повторять:

```text
TCP handshake
↓
TLS handshake для HTTPS
↓
HTTP request
↓
HTTP response
↓
close
```

Это создаёт лишнюю задержку и нагрузку.

---

# TCP handshake

До передачи обычных данных TCP устанавливает соединение:

```text
CLIENT                       SERVER

SYN ------------------------>

     <---------------- SYN + ACK

ACK ------------------------>
```

Это требует как минимум сетевого обмена до начала обычной передачи данных.

Для HTTPS дополнительно требуется криптографическое согласование TLS.

Поэтому постоянное создание новых соединений дорого.

---

# HTTP/1.1

Одна из важнейших идей HTTP/1.1 — **persistent connections**.

Вместо:

```text
TCP #1 → GET /a → close
TCP #2 → GET /b → close
TCP #3 → GET /c → close
```

можно:

```text
TCP connection
│
├── GET /a
├── response
│
├── GET /b
├── response
│
├── GET /c
└── response
```

То есть TCP-соединение переиспользуется.

---

# Keep-Alive и время жизни соединения

У HTTP/1.1 нет универсального фиксированного времени жизни соединения.

Оно может существовать:

```text
несколько секунд
десятки секунд
минуты
```

Реальное время определяется:

- клиентом;
- HTTP-сервером;
- reverse proxy;
- load balancer;
- idle timeout;
- ошибками сети;
- явным закрытием соединения.

Например сервер может закрыть idle connection после 60 секунд отсутствия активности.

Поэтому корректная модель:

> HTTP/1.1 connection живёт, пока стороны хотят и могут его переиспользовать.

---

# HTTP/1.1 и последовательность сообщений

Основная проблема HTTP/1.1: одно TCP-соединение неудобно для большого числа параллельных независимых запросов.

Упрощённая последовательная модель:

```text
GET /large.jpg
↓
large response
████████████████████████████████

GET /style.css
↓
small response
██

GET /app.js
↓
small response
███
```

Маленький важный ресурс может ждать длинный ответ перед ним.

---

# HTTP pipelining

HTTP/1.1 предусматривал pipelining: клиент мог отправить несколько запросов, не ожидая каждый ответ.

```text
GET /a
GET /b
GET /c
```

Но ответы должны были соответствовать порядку запросов.

Если первый ответ долгий, следующие ответы не могли произвольно обогнать его в том же соединении.

Из-за практических проблем pipelining не стал полноценным решением.

---

# Workaround браузеров

Для параллельной загрузки браузеры исторически открывали несколько TCP-соединений к одному origin.

```text
TCP #1 → resource A
TCP #2 → resource B
TCP #3 → resource C
TCP #4 → resource D
```

Это даёт параллелизм, но создаёт дополнительные:

- TCP handshakes;
- TLS handshakes;
- kernel buffers;
- congestion-control states;
- сокеты;
- нагрузку на клиент и сервер.

HTTP/2 решает эту проблему иначе: [[03 HTTP 2 - streams и multiplexing]].

---

# HTTP/1.1 — текстовый протокол

HTTP/1.1 сообщения имеют человекочитаемую текстовую стартовую строку и headers.

Например:

```http
POST /users HTTP/1.1
Host: example.com
Content-Type: application/json
Content-Length: 16

{"name":"Ilya"}
```

TCP не знает, где здесь заканчивается запрос.

HTTP сам определяет его границы. См. [[05 HTTP framing - как определяется конец сообщения]].

---

# Важное разделение

HTTP/1.1 определяет структуру прикладного сообщения.

TCP обеспечивает доставку его байтов.

```text
HTTP:
GET /users
headers
body

       ↓ serialization

TCP:
байты 1000...
байты 2000...
байты 3000...
```

TCP не знает, что байты относятся к `GET /users`.

---

# Главное отличие HTTP/1.0 и HTTP/1.1

```text
HTTP/1.0:
простая request/response модель,
часто новое TCP-соединение на отдельный запрос

HTTP/1.1:
переиспользование TCP-соединений,
более полноценная модель современного HTTP
```

Но HTTP/1.1 всё ещё не имеет полноценного multiplexing независимых запросов внутри одного TCP-соединения.
