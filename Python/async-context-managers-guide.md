# Полный гайд: асинхронные контекстные менеджеры (`async with`, `__aenter__`/`__aexit__`)

Продолжение гайда по контекстным менеджерам — теперь для асинхронного кода. Будем идти той же дорогой: зачем это нужно → примитивное решение → проблема → протокол → синтаксический сахар.

---

## 1. Сначала — зачем вообще асинхронность (коротко, для контекста)

### 1.1 Проблема блокирующих операций

Обычный (синхронный) код, когда делает `f.read()` или `socket.recv()`, **блокирует весь поток**: поток буквально останавливается и ждёт, пока ОС не вернёт данные (диск прочитается, пакет придёт по сети). Пока поток ждёт — он не может делать ничего другого.

Для одной операции это нормально. Но если сервер должен обслуживать 10 000 одновременных сетевых соединений, а каждое из них большую часть времени просто **ждёт** данные (сеть — это медленно по сравнению с CPU), то создавать 10 000 потоков ОС ради этого — дорого: каждый поток — это отдельный стек памяти (обычно мегабайты), плюс накладные расходы ядра на переключение контекста между ними.

### 1.2 Решение: событийный цикл (event loop) и кооперативная многозадачность

Идея `asyncio` (и async/await вообще): вместо того чтобы поток *блокировался* в ожидании, код явно говорит: "я сейчас жду результата, можешь пока заняться чем-то другим" — и **отдаёт управление** обратно в единый цикл событий (event loop), который работает в одном потоке и переключается между множеством "корутин" (coroutines), пока каждая из них ждёт свою I/O-операцию.

```python
async def fetch_data():
    data = await some_io_operation()   # "отдаю управление, разбуди меня когда будут данные"
    return data
```

Ключевое слово `await` — это и есть точка, где корутина говорит event loop'у: "приостанови меня здесь, выполни что-то ещё, а когда операция завершится — вернись сюда".

### 1.3 Почему это ломает обычные context manager'ы

Вспомним протокол из синхронного гайда:

```python
def __enter__(self): ...
def __exit__(self, exc_type, exc_value, traceback): ...
```

Эти методы — **обычные, синхронные функции**. Они не могут содержать `await` внутри себя. А что если "закрытие ресурса" — это тоже I/O-операция? Например:

- закрыть сетевое соединение с корректным TCP-рукопожатием завершения — это тоже требует общения по сети (ожидания ответа сервера);
- закоммитить транзакцию в асинхронной БД (`asyncpg`, `aiomysql`) — сетевой round-trip к серверу БД;
- отпустить асинхронный `Lock` в `asyncio`, разбудив следующую корутину в очереди.

Если бы `__exit__` вызывал внутри себя блокирующую операцию (даже "быстро" ожидая ответ сервера синхронно) — это заблокировало бы **весь event loop**, а вместе с ним — вообще все остальные корутины, которые в этот момент ждут своей очереди выполниться. Это свело бы на нет весь смысл асинхронности.

**Вывод:** нужен способ вызвать `await` внутри "входа" и "выхода" из ресурса. Обычный протокол `__enter__`/`__exit__` для этого не подходит в принципе — нужен отдельный протокол.

## 2. Шаг 1: примитивное решение — `try/finally` с `await`

Точно так же, как в синхронном мире всё начиналось с `try/finally`, в асинхронном мире мы можем сделать то же самое, просто добавив `await` там, где нужно:

```python
conn = await open_async_connection("db://...")
try:
    result = await conn.query("SELECT * FROM users")
    process(result)
finally:
    await conn.close()   # закрытие тоже асинхронное — требует await!
```

Здесь `await conn.close()` — это ключевое отличие от синхронного случая: закрытие соединения может само по себе быть корутиной, которая дожидается сетевого подтверждения закрытия. Обычный `f.close()` для файла — синхронный и мгновенный (буфер сбросить — дёшево), а вот `conn.close()` для сетевого соединения или БД — часто асинхронный.

### 2.1 Те же проблемы, что и раньше

- Многословно.
- Легко забыть обернуть в `try/finally`.
- Плохо масштабируется на несколько ресурсов.
- Паттерн "открыть асинхронно → использовать → закрыть асинхронно" повторяется в куче мест: сетевые сессии (`aiohttp`), соединения с БД (`asyncpg`), блокировки (`asyncio.Lock`), семафоры, пулы соединений.

Ровно та же логика, что подтолкнула к появлению протокола `__enter__`/`__exit__`, подталкивает к появлению его асинхронного аналога.

## 3. Шаг 2: протокол асинхронного контекстного менеджера

Python вводит два новых магических метода — **корутины** вместо обычных функций:

```python
class AsyncManagedConnection:
    def __init__(self, url):
        self.url = url
        self.conn = None

    async def __aenter__(self):
        print(f"Открываю соединение с {self.url}")
        self.conn = await open_async_connection(self.url)
        return self.conn              # это попадёт в "as conn"

    async def __aexit__(self, exc_type, exc_value, traceback):
        print("Закрываю соединение")
        if self.conn:
            await self.conn.close()   # можем await'ить здесь!
        return False                  # не подавляем исключения
```

Отличия от `__enter__`/`__exit__` ровно два:

1. Методы объявлены как `async def` — то есть они сами являются корутинами, а не обычными функциями.
2. Внутри них можно использовать `await` — то есть выполнять асинхронные операции при входе и выходе из блока.

Сигнатура `__aexit__` та же самая: `exc_type`, `exc_value`, `traceback` — и та же семантика возвращаемого значения (`True` подавляет исключение, `False`/`None` — пропускает дальше).

## 4. Шаг 3: `async with` — сахар над асинхронным протоколом

```python
async def main():
    async with AsyncManagedConnection("db://...") as conn:
        result = await conn.query("SELECT * FROM users")
        process(result)

asyncio.run(main())
```

Важные моменты:

- `async with` можно использовать **только внутри `async def`** функции — потому что внутри него будут вызовы `await __aenter__()` и `await __aexit__()`, а `await` разрешён только внутри корутин.
- Разворачивание концептуально то же самое, что у синхронного `with`, только с `await` перед вызовами методов:

```python
mgr = AsyncManagedConnection("db://...")
conn = await mgr.__aenter__()
try:
    result = await conn.query("SELECT * FROM users")
    process(result)
except Exception as e:
    if not await mgr.__aexit__(type(e), e, e.__traceback__):
        raise
else:
    await mgr.__aexit__(None, None, None)
```

То есть `async with` относится к `try/finally + await` ровно так же, как обычный `with` относится к обычному `try/finally` — просто интерпретатор сам вызывает нужные корутины в нужный момент, гарантируя, что `__aexit__` выполнится даже при исключении, и при этом позволяя этому "выходу" быть асинхронной операцией.

## 5. Реальные примеры из экосистемы

### 5.1 `asyncio.Lock` — асинхронная блокировка

В многопоточном коде для защиты общих данных используют `threading.Lock`. В асинхронном коде, где вместо потоков — корутины, используют `asyncio.Lock`, и он тоже реализует асинхронный протокол:

```python
import asyncio

lock = asyncio.Lock()

async def critical_section():
    async with lock:
        # только одна корутина одновременно может быть здесь
        await do_something()
```

`__aenter__` здесь — это `await lock.acquire()` (ожидание, пока блокировка освободится — а это ожидание не должно блокировать весь event loop, поэтому оно и асинхронное), `__aexit__` — `lock.release()`.

### 5.2 `aiohttp` — асинхронные HTTP-сессии и запросы

```python
import aiohttp

async def fetch(url):
    async with aiohttp.ClientSession() as session:   # открытие сессии — асинхронный ресурс
        async with session.get(url) as response:     # сам запрос — тоже асинхронный контекстный менеджер
            return await response.text()
```

Здесь два вложенных `async with`: `ClientSession` управляет пулом соединений (его нужно корректно закрыть, освободив сетевые ресурсы), а объект ответа `response` — сам по себе контекстный менеджер, закрывающий сетевой поток данных при выходе из блока.

### 5.3 `asyncpg` — соединение с PostgreSQL

```python
import asyncpg

async def main():
    conn = await asyncpg.connect(user="user", database="db")
    try:
        rows = await conn.fetch("SELECT * FROM users")
    finally:
        await conn.close()

# или, если библиотека предоставляет транзакцию как контекстный менеджер:
async def transactional():
    conn = await asyncpg.connect(...)
    async with conn.transaction():     # BEGIN при входе, COMMIT/ROLLBACK при выходе
        await conn.execute("INSERT INTO ...")
        await conn.execute("UPDATE ...")
    await conn.close()
```

Здесь особенно наглядно видно, зачем нужен именно асинхронный `__aexit__`: при выходе из блока транзакции нужно отправить `COMMIT` (или `ROLLBACK`, если было исключение) **на сервер БД по сети** и дождаться подтверждения — это неотъемлемо асинхронная операция.

### 5.4 Аналог `open()` для файлов — `aiofiles`

Стандартный `open()` в Python — **синхронный**, потому что дисковый I/O в большинстве ОС не имеет удобного неблокирующего API (в отличие от сетевых сокетов). Поэтому для по-настоящему асинхронной работы с файлами используют сторонние библиотеки вроде `aiofiles`, которые под капотом выполняют файловые операции в отдельном пуле потоков, но наружу дают асинхронный интерфейс:

```python
import aiofiles

async def read_file():
    async with aiofiles.open("data.txt", mode="r") as f:
        content = await f.read()
    return content
```

## 6. Более короткий способ: `contextlib.asynccontextmanager`

Точно так же, как `@contextmanager` избавляет от написания класса с `__enter__`/`__exit__`, есть асинхронный аналог — `@asynccontextmanager`, применяемый к **асинхронному генератору**:

```python
from contextlib import asynccontextmanager

@asynccontextmanager
async def managed_connection(url):
    conn = await open_async_connection(url)
    try:
        yield conn          # всё до yield — это "__aenter__"
    finally:
        await conn.close()  # всё после yield — это "__aexit__", можно await!

async def main():
    async with managed_connection("db://...") as conn:
        result = await conn.query("SELECT * FROM users")
```

Механика та же, что у синхронного `@contextmanager`, только:

- функция объявлена как `async def` и использует `yield` внутри асинхронного генератора;
- код до и после `yield` может содержать `await`;
- исключение из блока `async with` так же "пробрасывается" внутрь генератора в точке `yield`, и `finally` (с возможным `await`) отрабатывает гарантированно.

## 7. Несколько асинхронных ресурсов одновременно

```python
async def main():
    async with aiohttp.ClientSession() as session, session.get(url) as response:
        data = await response.text()
```

Работает так же, как и в синхронном случае — эквивалентно вложенным `async with`, и `__aexit__` каждого ресурса будет вызван (с `await`) в порядке, обратном открытию, даже при исключении.

Для динамического количества асинхронных ресурсов (когда заранее неизвестно, сколько их) используют `contextlib.AsyncExitStack`:

```python
from contextlib import AsyncExitStack

async def process_many(urls):
    async with AsyncExitStack() as stack:
        sessions = []
        for url in urls:
            session = await stack.enter_async_context(aiohttp.ClientSession())
            sessions.append(session)
        # при выходе из блока все сессии будут закрыты в обратном порядке,
        # даже если их количество определилось только во время выполнения
```

## 8. Частая ошибка: смешение `with` и `async with`

Если объект реализует только `__enter__`/`__exit__` (синхронный протокол), но внутри его логики закрытия на самом деле нужна сетевая операция — библиотека вынуждена либо блокировать поток внутри `__exit__` (что плохо в асинхронном приложении), либо запускать асинхронную операцию "и забыть" (fire-and-forget), не дожидаясь её завершения — что ненадёжно (ресурс может не успеть закрыться до завершения программы).

Поэтому правило простое: **если создание/закрытие ресурса требует I/O и должно быть неблокирующим — ресурс обязан реализовывать `__aenter__`/`__aexit__` и использоваться через `async with`**, а не через обычный `with`. Попытка написать `with aiohttp.ClientSession()` (без `async`) просто вызовет ошибку, потому что `ClientSession` не реализует `__enter__`/`__exit__` вовсе — только асинхронные версии.

## 9. Резюме: путь от event loop до `async with`

| Уровень | Что происходит |
|---|---|
| Причина | Блокирующие `__enter__`/`__exit__` заблокировали бы весь event loop — а закрытие сетевых/БД-ресурсов часто само требует I/O |
| Наивно | `conn = await open(...)`, работа, `await conn.close()` — ломается при исключении |
| `try/finally` + `await` | Гарантирует закрытие, но многословно, легко забыть, плохо масштабируется |
| Абстракция | Протокол `__aenter__`/`__aexit__` — те же идеи, что `__enter__`/`__exit__`, но методы объявлены `async def` и умеют `await` |
| Синтаксис | `async with` — вызывает `await __aenter__()`/`await __aexit__()` автоматически, разворачиваясь в `try/finally` с `await` |
| Готовые решения | `asyncio.Lock`, `aiohttp.ClientSession`, `asyncpg`-транзакции, `aiofiles.open` — все уже реализуют протокол |
| Сахар для авторов ресурсов | `@contextlib.asynccontextmanager` — асинхронный генератор с одним `yield` вместо класса с двумя методами |
| Несколько ресурсов | Несколько `async with` подряд, или `contextlib.AsyncExitStack` для динамического числа ресурсов |

Итог: `async with` — та же самая идея, что и обычный `with` (гарантированное освобождение ресурса даже при исключении), перенесённая в мир, где "освобождение ресурса" само может быть операцией, требующей ожидания — и потому не может быть выражено обычной синхронной функцией.
