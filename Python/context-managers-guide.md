# Полный гайд: контекстные менеджеры, `with` и `open()`

От операционной системы до Python-протокола `__enter__`/`__exit__`.

---

## 1. Зачем вообще что-то "особенное" при работе с файлами

### 1.1 Файл — это не просто данные, это ресурс операционной системы

Когда программа хочет поработать с файлом, она не может просто "взять данные из файла" напрямую — файл физически лежит на диске (или в другом хранилище), и доступ к нему контролирует **операционная система**. Процесс не имеет прямого доступа к диску — это было бы опасно (представь, что любая программа могла бы напрямую писать байты на диск в обход файловой системы).

Поэтому взаимодействие идёт через **системные вызовы** (system calls) — специальный интерфейс, через который процесс просит ядро ОС сделать что-то от его имени.

Базовые системные вызовы для файлов (в POSIX/Linux, но концептуально то же в Windows):

```
open()   — попросить ОС открыть файл, получить дескриптор
read()   — прочитать байты через этот дескриптор
write()  — записать байты
close()  — сообщить ОС, что мы закончили
```

### 1.2 Файловый дескриптор (file descriptor)

Когда вызывается `open()`, ядро ОС:

1. Находит файл в файловой системе (по пути).
2. Проверяет права доступа.
3. Создаёт в своих внутренних структурах данных запись — **открытый файл** (в Linux это entry в системной таблице открытых файлов), которая хранит: текущую позицию курсора чтения/записи, режим доступа, буферы и т.д.
4. Возвращает процессу **небольшое целое число** — файловый дескриптор (file descriptor, fd). Это просто индекс в *таблице дескрипторов процесса*, которая указывает на ту самую запись в ядре.

```
Процесс                          Ядро ОС
┌─────────────────────┐         ┌──────────────────────────┐
│ fd table             │         │ Open File Table            │
│  0 → stdin            │         │ [позиция курсора, режим,  │
│  1 → stdout           │────────▶│  буферы, ссылка на inode] │
│  2 → stderr           │         └──────────────────────────┘
│  3 → наш файл  ───────┼───────────────────▶ ...
└─────────────────────┘
```

Важно: **дескрипторы — ограниченный ресурс**. У каждого процесса есть лимит на число одновременно открытых файлов (`ulimit -n` в Linux, обычно 1024 по умолчанию). У ОС в целом тоже есть глобальный лимит. Это не "бесконечная" абстракция вроде переменной в памяти — это реальный, конечный ресурс, за которым кто-то должен следить.

### 1.3 Что если не закрыть файл

Когда процесс вызывает `close(fd)`, происходит несколько вещей:

- Ядро **сбрасывает буферы** (flush) — то, что было записано в память, но ещё физически не долетело до диска, дозаписывается.
- Освобождается запись в таблице открытых файлов.
- Дескриптор становится свободным и может быть переиспользован.

Если файл **не закрыть явно**:

- **Утечка дескрипторов (fd leak).** Дескрипторы не освобождаются, пока процесс жив (или пока не сработает сборщик мусора — но полагаться на это опасно, см. ниже). Долго работающий процесс (веб-сервер, скрипт с циклом) может исчерпать лимит и начать падать с `OSError: Too many open files`.
- **Потеря данных.** Если запись буферизована (а она почти всегда буферизована — Python и ОС по умолчанию не пишут каждый байт на диск немедленно ради производительности), а процесс упал/завершился аварийно до `close()`/`flush()`, то часть данных может **не долететь до диска**.
- **Блокировки файлов.** На некоторых ОС (особенно Windows) незакрытый файл может оставаться заблокированным для других процессов.

Это не абстрактная опасность — это ровно то, почему во всех языках, где есть ручное управление ресурсами (файлы, сокеты, соединения с БД, блокировки/мьютексы, память в C), придумали механизмы гарантированного освобождения.

## 2. Как Python оборачивает это

В Python `open()` — это не сам системный вызов, а обёртка над ним. Под капотом (в CPython) `open()` в итоге дёргает `os.open()`, который уже делает системный вызов `open(2)`, и оборачивает низкоуровневый fd в Python-объект — `io.TextIOWrapper` (для текстового режима) или `io.BufferedReader`/`BufferedWriter` (для бинарного).

```python
f = open("data.txt", "r")
print(type(f))        # <class '_io.TextIOWrapper'>
print(f.fileno())     # возвращает тот самый целочисленный fd, например 3
```

Этот Python-объект `f` — тоже ресурс, который держит системный дескриптор "внутри себя" и должен быть явно закрыт методом `f.close()`, чтобы освободить его на уровне ОС.

### 2.1 Наивный подход

```python
f = open("data.txt", "r")
content = f.read()
f.close()
print(content)
```

Выглядит нормально. Но что если между `open()` и `close()` произойдёт исключение?

```python
f = open("data.txt", "r")
content = f.read()          # предположим, здесь падает исключение
process(content)            # никогда не выполнится
f.close()                   # тоже никогда не выполнится!
```

Если `process(content)` бросит `ValueError`, интерпретатор немедленно начнёт "разматывать стек" (stack unwinding) в поисках обработчика исключения, и строка `f.close()` **никогда не будет выполнена**. Файл останется открытым до тех пор, пока Python не соберёт мусор и не закроет его сам (в CPython это часто происходит быстро благодаря подсчёту ссылок, но это **деталь реализации**, а не гарантия языка — в PyPy, например, сборка мусора устроена иначе, и момент закрытия непредсказуем).

**Вывод:** нельзя полагаться на "код после операции" для освобождения ресурса, если между ними может вылететь исключение. А исключение может вылететь практически где угодно.

## 3. Шаг 1: примитивное решение — `try/finally`

Именно для этой задачи в языке существует конструкция `try/finally`: блок `finally` выполняется **всегда** — было исключение или нет, дошло выполнение до конца блока `try` или прервалось через `return`, `break`, `continue` где-то внутри.

```python
f = open("data.txt", "r")
try:
    content = f.read()
    process(content)
finally:
    f.close()
```

Как это работает пошагово:

1. `open()` выполняется вне `try` — если сам `open()` упадёт (файла не существует), нет смысла пытаться его закрыть, поэтому его иногда оставляют снаружи (хотя чаще всё же кладут внутрь `try` для единообразия — тогда в `finally` дополнительно проверяют, что `f` вообще успел присвоиться).
2. Внутри `try` выполняется потенциально опасный код.
3. Если исключение произошло — Python запоминает его, **сначала выполняет `finally`**, и только потом продолжает "выброс" исключения наверх.
4. Если исключения не было — `finally` всё равно выполняется перед тем, как управление уйдёт дальше.

Более аккуратная версия, где `open` тоже "защищён":

```python
f = None
try:
    f = open("data.txt", "r")
    content = f.read()
    process(content)
finally:
    if f is not None:
        f.close()
```

### 3.1 Проблемы такого подхода

1. **Многословность.** На одну содержательную строку (`content = f.read()`) — три строки инфраструктуры.
2. **Легко забыть.** Ничто не заставляет разработчика обернуть код в `try/finally` — это соглашение, а не гарантия языка.
3. **Плохо масштабируется.** Если нужно открыть два файла — вложенность растёт:

```python
f1 = open("a.txt")
try:
    f2 = open("b.txt")
    try:
        # работа с f1 и f2
        pass
    finally:
        f2.close()
finally:
    f1.close()
```

4. **Повторяющийся паттерн для любого ресурса.** Та же самая структура нужна для сетевых сокетов, блокировок (locks), соединений с БД, транзакций — то есть `try/finally` вокруг "открыть → использовать → закрыть" — это общий шаблон, а не что-то специфичное для файлов. А раз паттерн общий и повторяющийся — это сигнал, что его стоит **абстрагировать**.

## 4. Шаг 2: абстрагируем паттерн — протокол context manager

Идея: раз структура "выполнить что-то до блока, выполнить что-то после блока (даже при исключении)" повторяется постоянно, давайте вынесем её в **объект**, который умеет сам о себе рассказать, что делать "до" и что делать "после" — а Python возьмёт на себя вызов этих действий в нужный момент.

Так появляется **протокол контекстного менеджера** (context manager protocol) — соглашение, что объект, если хочет участвовать в конструкции `with`, должен реализовать два специальных ("магических") метода:

```python
class MyResource:
    def __enter__(self):
        # код, который выполняется при ВХОДЕ в блок
        # то, что возвращает этот метод, попадает в переменную "as x"
        ...
        return self

    def __exit__(self, exc_type, exc_value, traceback):
        # код, который выполняется при ВЫХОДЕ из блока
        # выполняется ВСЕГДА: и при обычном завершении, и при исключении
        ...
```

Это ровно то же самое, что "тело перед `try`" и "тело `finally`" — только оформленное как метод объекта, а не как код, который надо не забыть написать вручную каждый раз.

### 4.1 Реализуем свой файлоподобный контекстный менеджер вручную

Чтобы понять механику "снизу", напишем игрушечный класс, повторяющий логику `open()`:

```python
class ManagedFile:
    def __init__(self, filename, mode="r"):
        self.filename = filename
        self.mode = mode
        self.file = None

    def __enter__(self):
        print(f"Открываю {self.filename}")
        self.file = open(self.filename, self.mode)
        return self.file          # это попадёт в "as f"

    def __exit__(self, exc_type, exc_value, traceback):
        print(f"Закрываю {self.filename}")
        if self.file:
            self.file.close()
        # return None (или False) — исключение, если было, полетит дальше
        # return True — исключение будет ПОГЛОЩЕНО (подавлено)
        return False
```

## 5. Шаг 3: `with` — синтаксический сахар над протоколом

Теперь у нас есть объект, который знает, как себя "открыть" и "закрыть". Конструкция `with` — это то, что **автоматически вызывает `__enter__` при входе и `__exit__` при выходе**, избавляя от ручного `try/finally`:

```python
with ManagedFile("data.txt", "r") as f:
    content = f.read()
    process(content)
```

Что происходит под капотом (это официально задокументированное поведение, можно считать "разворачиванием" `with`):

```python
mgr = ManagedFile("data.txt", "r")
value = mgr.__enter__()
exc = True
try:
    try:
        f = value
        content = f.read()
        process(content)
    except:
        exc = False
        if not mgr.__exit__(*sys.exc_info()):
            raise
finally:
    if exc:
        mgr.__exit__(None, None, None)
```

Упрощённо — это то же самое, что:

```python
mgr = ManagedFile("data.txt", "r")
f = mgr.__enter__()
try:
    content = f.read()
    process(content)
except Exception as e:
    if not mgr.__exit__(type(e), e, e.__traceback__):
        raise
else:
    mgr.__exit__(None, None, None)
```

То есть **`with` — это `try/finally`, но который пишет за нас интерпретатор**, вызывая методы конкретного объекта вместо того, чтобы мы вручную писали блок `finally`.

### 5.1 Что означают аргументы `__exit__`

Если исключение произошло, Python передаёт в `__exit__` три вещи (те же, что вернул бы `sys.exc_info()`):

| Аргумент | Что это |
|---|---|
| `exc_type` | класс исключения (например `ValueError`) или `None`, если исключения не было |
| `exc_value` | сам объект исключения |
| `traceback` | объект трассировки стека |

И главное: **возвращаемое значение `__exit__` решает судьбу исключения**.

```python
class SuppressValueError:
    def __enter__(self):
        return self

    def __exit__(self, exc_type, exc_value, traceback):
        if exc_type is ValueError:
            print("Проглатываю ValueError")
            return True   # исключение подавлено, код после with продолжит работу
        return False       # любое другое исключение улетит дальше

with SuppressValueError():
    raise ValueError("упс")

print("А мы всё ещё живы")
```

Это мощная и потенциально опасная возможность — подавлять исключения нужно очень осознанно, потому что молча "съеденная" ошибка усложняет отладку.

## 6. Как `open()` реализует этот протокол

Возвращаемый `open()` объект (`TextIOWrapper` и т.п.) **сам является контекстным менеджером** — у него уже реализованы `__enter__` и `__exit__`:

- `__enter__` просто возвращает `self` (сам файловый объект).
- `__exit__` вызывает `self.close()` и возвращает `False` (то есть не подавляет исключения — если при чтении файла что-то упало, ошибка долетит до вызывающего кода как обычно, но файл всё равно будет закрыт).

Именно поэтому работает:

```python
with open("data.txt", "r") as f:
    content = f.read()
    process(content)
# здесь f уже гарантированно закрыт — и при успехе, и при исключении
```

Это ровно тот путь, который мы прошли: `try/finally` → протокол `__enter__`/`__exit__` → `with`. `open()` просто **встроил в себя** этот протокол, поэтому нам не нужно писать свой `ManagedFile`.

Проверить самостоятельно:

```python
f = open("data.txt")
print(hasattr(f, "__enter__"), hasattr(f, "__exit__"))  # True True
```

## 7. Более короткий способ писать контекстные менеджеры: `contextlib.contextmanager`

Писать класс с `__enter__`/`__exit__` ради простого случая — многословно. Модуль `contextlib` даёт способ превратить обычную функцию-генератор в контекстный менеджер:

```python
from contextlib import contextmanager

@contextmanager
def managed_file(filename, mode="r"):
    f = open(filename, mode)
    try:
        yield f            # всё до yield — это "__enter__", f — то, что попадёт в "as"
    finally:
        f.close()          # всё после yield — это "__exit__"

with managed_file("data.txt") as f:
    content = f.read()
```

Механика: декоратор `@contextmanager` оборачивает генератор так, что:

- код **до `yield`** выполняется в момент входа в `with` (аналог `__enter__`), а значение, переданное в `yield`, становится результатом `as`;
- код **после `yield`**, обёрнутый в `try/finally` внутри самой функции, выполняется при выходе из `with` (аналог `__exit__`) — причём если внутри `with` возникло исключение, оно "пробрасывается" внутрь генератора ровно в точке `yield` (как будто там стоит `raise`), поэтому `finally` в генераторе отрабатывает так же надёжно, как и `__exit__` в классе.

Так мы вернулись к тому же самому `try/finally`, с которого начали — просто теперь он написан **один раз внутри реализации ресурса**, а не каждый раз в коде, который этот ресурс использует.

## 8. Несколько ресурсов одновременно

```python
with open("in.txt") as fin, open("out.txt", "w") as fout:
    fout.write(fin.read())
```

Это эквивалентно вложенным `with`:

```python
with open("in.txt") as fin:
    with open("out.txt", "w") as fout:
        fout.write(fin.read())
```

Оба файла будут закрыты гарантированно, даже если исключение случится между открытием `fin` и `fout`, или во время записи — `__exit__` каждого уже открытого менеджера будет вызван в порядке, обратном открытию.

## 9. Резюме: путь от ОС до `with open`

| Уровень | Что происходит |
|---|---|
| ОС | Файл — ограниченный ресурс ядра; `open`/`close` — системные вызовы; незакрытые дескрипторы = утечка и риск потери данных |
| Python, наивно | `f = open(...)`, работа, `f.close()` — ломается при исключении между строками |
| Python, `try/finally` | Гарантирует `close()` в любом случае, но многословно и легко забыть |
| Абстракция | Протокол `__enter__`/`__exit__` — переносим "открыть/закрыть" внутрь объекта |
| Синтаксис | `with` — автоматически вызывает `__enter__`/`__exit__`, разворачиваясь в `try/finally` под капотом |
| Готовое решение | `open()` уже реализует протокол сама — `with open(...) as f` использует всё вышеописанное "из коробки" |
| Сахар для авторов ресурсов | `@contextlib.contextmanager` позволяет написать контекстный менеджер как генератор с одним `yield`, вместо класса |

Итог: `with open(...)` — это не магия, а результат прямой цепочки решений: ресурс ОС → нужна гарантия освобождения → `try/finally` → повторяемость паттерна → протокол объекта → синтаксический сахар языка.
