Собрал в порядке частоты использования в реальной работе — от повседневных до диагностических.

## Ежедневные — создание и применение миграций

```bash
alembic revision --autogenerate -m "add cancellation reason to orders"
```

Генерирует новый файл в `versions/` на основе диффа моделей и реальной БД. Самая частая команда — используется при **каждом** изменении модели.

```bash
alembic revision -m "custom data migration"
```

Создаёт **пустой** файл миграции без автогенерации — нужен, когда миграция не про схему, а про данные (например, заполнить новое поле вычисленными значениями), или когда автогенерация не справляется (переименования).

```bash
alembic upgrade head
```

Применяет все неприменённые миграции до последней. Самая частая команда после создания миграции и на деплое.

```bash
alembic upgrade +1
```

Применяет только следующую одну миграцию — полезно, когда хочешь применять пошагово и проверять каждый шаг отдельно.

## Откат

```bash
alembic downgrade -1
```

Откатывает последнюю применённую миграцию на шаг назад — нужно, если только что накатил миграцию и заметил ошибку у себя локально.

```bash
alembic downgrade <revision_id>
```

Откатывает до конкретной ревизии (не обязательно на один шаг — можно сразу на несколько назад).

```bash
alembic downgrade base
```

Откатывает вообще всё, до пустой БД. Используется редко — разве что полностью пересобрать локальную тестовую БД с нуля через полный цикл down→up.

## Диагностика — "где я сейчас"

```bash
alembic current
```

Показывает, на какой ревизии сейчас находится **подключённая** БД (значение из `alembic_version`). Первое, что стоит выполнить, если непонятно, применены ли уже последние миграции.

```bash
alembic current -v
```

То же самое, но подробнее — с датой и сообщением коммита миграции.

```bash
alembic history
```

Показывает всю цепочку миграций от начала до head'а — удобно посмотреть порядок и что вообще есть.

```bash
alembic history --verbose
```

То же, но с описаниями каждой миграции (сообщением из `-m`).

```bash
alembic heads
```

Показывает текущую "голову"/головы цепочки в файлах. Если выводит **больше одной** ревизии — сигнал, что у тебя конфликт (multiple heads), который надо смержить.

```bash
alembic show <revision_id>
```

Печатает содержимое конкретной миграции — что в её `upgrade()`/`downgrade()` — без необходимости открывать файл руками.

## Конфликты в команде

```bash
alembic merge heads -m "merge migrations"
```

Создаёт merge-миграцию, объединяющую разошедшиеся головы в одну линейную цепочку — нужно после `git merge`, если два человека параллельно генерировали миграции от одной базы.

## Специальные ситуации

```bash
alembic stamp head
```

Помечает БД как "уже на последней версии" **без выполнения SQL**. Нужна, когда схему накатили не через Alembic (восстановили из бэкапа прода, скопировали с другого окружения) — служебную таблицу надо синхронизировать вручную, не пересоздавая структуру.

```bash
alembic stamp <revision_id>
```

То же, но на конкретную ревизию — полезно, если знаешь, что БД физически соответствует именно этому шагу истории.

```bash
alembic upgrade head --sql
```

Не выполняет миграции, а печатает итоговый SQL в stdout — offline-режим, для сред, где прямого доступа к прод-БД нет, и SQL передаётся администраторам отдельно.

```bash
alembic check
```

Сверяет модели с реальной БД и падает с ошибкой, если есть неучтённые изменения (модель поменялась, а миграция не сгенерирована) — полезно вставлять как шаг в CI, чтобы никто не закоммитил изменение модели без миграции.

## Сводная таблица по частоте использования

| Частота               | Команды                                             |
| --------------------- | --------------------------------------------------- |
| Каждый день           | `revision --autogenerate`, `upgrade head`           |
| Периодически          | `current`, `history`, `downgrade -1`                |
| При конфликтах        | `heads`, `merge heads`                              |
| Редко / особые случаи | `stamp`, `upgrade --sql`, `downgrade base`, `check` |
