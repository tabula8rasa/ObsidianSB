# Управление памятью в Python
> [!important]
> Ниже речь в первую очередь идёт о **CPython** — стандартной и самой распространённой реализации Python. Сам язык Python не требует, чтобы все реализации использовали именно `pymalloc`, арены, пулы и подсчёт ссылок в том виде, в котором это делает CPython.

## Общая схема

```text
Python-код
    ↓
Python-объекты
    ↓
Memory Manager CPython
    ↓
pymalloc / object-specific allocators / system allocator
    ↓
виртуальная память процесса
    ↓
операционная система
    ↓
RAM / swap
```

Python использует **автоматическое управление памятью**. Программист создаёт объекты и работает с ними, а выделением, переиспользованием и освобождением памяти занимается интерпретатор.

---

# 1. Взаимодействие программы с операционной системой

## Опосредованный доступ

Программы и процессы в Python не могут напрямую обращаться к физической оперативной памяти. Между «железом» и программой всегда стоит **операционная система**.

Обычный процесс работает прежде всего с **виртуальным адресным пространством**. Например, Python может иметь указатель:

```text
0x7f2c8a123400
```

Но это не означает, что объект физически лежит по такому адресу в RAM. ОС и процессор через таблицы страниц сопоставляют виртуальные адреса процесса физическим страницам памяти.

Упрощённо:

```text
Python
  ↓
виртуальный адрес
  ↓
таблицы страниц
  ↓
RAM / swap
```

## Запрос и возврат памяти

Чтобы использовать память, интерпретатор запрашивает её у ОС определёнными долями — кусочками. В идеале ненужная память должна максимально эффективно освобождаться и при возможности возвращаться операционной системе, чтобы избежать утечек и нехватки ресурсов.

Но важно различать:

```text
Python-объект уничтожен
```

и:

```text
память возвращена операционной системе
```

Это **не одно и то же**.

Часто происходит так:

```text
объект уничтожен
      ↓
блок стал свободным
      ↓
CPython оставил память у себя
      ↓
позже использовал её для нового объекта
```

Поэтому после `del obj` или удаления большого количества объектов RSS процесса не обязан сразу уменьшиться.

# 2. Фрагментация памяти

При неаккуратном заполнении памяти возникает **фрагментация** — ситуация, когда между занятыми участками остаются свободные «дыры».

Например:

```text
[занято][свободно][занято][свободно][занято]
```

Свободной памяти суммарно может быть достаточно, но отдельного непрерывного участка нужного размера может не оказаться.

Это называется **внешней фрагментацией**.

Также существует **внутренняя фрагментация**. Например, если объекту нужно `17` байт, а allocator выдаёт блок `32` байта:

```text
нужно:      17 B
выделено:   32 B
не занято:  15 B
```

Эти лишние байты находятся уже внутри выделенного блока.

# 3. Stack и Heap
![[Pasted image 20260811154556.png]]

Для понимания работы памяти Python удобно логически разделять память на две основные структуры:

```text
Stack
Heap
```

Но это учебная модель.

> [!warning]
> Фраза «все локальные переменные Python физически лежат в обычном машинном stack» является упрощением. Корректнее говорить о **логическом стеке вызовов Python**, состоящем из кадров выполнения (`frames`). Ссылки на локальные значения принадлежат состоянию frame. То, как frame связан с нативным C-stack, — деталь реализации CPython.

# 4. Стек вызовов — Call Stack

Стек вызовов работает по принципу:

```text
LIFO
Last In — First Out
```

Например:

```python
def c():
    return 10


def b():
    return c()


def a():
    return b()


a()
```

Логически стек развивается так:

```text
a()
```

```text
a()
└── b()
```

```text
a()
└── b()
    └── c()
```

После завершения `c()` её кадр убирается, затем `b()`, затем `a()`.

# 5. Frame — кадр вызова

Для каждого вызова функции создаётся **кадр (`frame`)** — структура, содержащая состояние выполнения функции.

В нём логически находятся:

- аргументы;
- локальные переменные;
- ссылки на используемые Python-объекты;
- информация о текущем месте выполнения;
- служебное состояние интерпретатора.

Например:

```python
def calculate(a, b):
    result = a + b
    return result
```

Можно представить:

```text
Frame calculate
├── a      → ссылка на объект
├── b      → ссылка на объект
├── result → ссылка на объект
└── состояние выполнения
```

Когда функция завершается, её активный кадр обычно больше не нужен. Именно поэтому локальные имена функции перестают быть доступны снаружи.

Однако завершение функции **не означает**, что все объекты, использовавшиеся внутри неё, обязательно уничтожаются. Если на объект существует другая ссылка, объект продолжает жить.

Кроме того, сам frame иногда может продолжать существовать, например если его удерживает traceback, generator, coroutine или debugger.

# 6. Heap — куча

**Куча (`Heap`)** — большая область памяти, где хранятся Python-объекты и внутренние структуры интерпретатора.

Именно здесь логически находятся:

```text
int
float
str
list
dict
set
tuple
function
class
instance
...
```

Официальная документация CPython называет её **private heap**.

---

# 7. Переменная — это ссылка на объект

Очень важно понимать:

```python
x = 1000
```

полезнее представлять так:

```text
x ─────► int object 1000
```

Сама переменная хранит не объект «внутри себя», а связь имени с объектом.

Например:

```python
a = [1, 2, 3]
b = a
```

Логически:

```text
a ─────┐
       ▼
   [1, 2, 3]
       ▲
b ─────┘
```

Нового списка при `b = a` не создаётся.

```python
a is b
```

даст:

```text
True
```

# 8. Что знает Python-объект

В обычном CPython объект имеет служебный заголовок.

Упрощённо:

```text
Python object
├── reference count
├── pointer to type
└── object-specific data
```

То есть объект знает свой тип данных и содержит служебную информацию для подсчёта ссылок.

Например:

```text
PyLongObject
├── refcount
├── type → int
└── значение
```

> [!note]
> Фраза «объект знает точное количество ссылающихся на него переменных» тоже немного упрощена. Ссылками могут быть не только переменные. Кроме того, в современных версиях CPython существуют **immortal objects**, для которых refcount не обязан буквально совпадать с реальным количеством ссылок.

Подробнее это относится к [[Reference Counting in Python]].

# 9. Memory Manager

За распределение памяти отвечает **Python Memory Manager**.

Это не одна функция, а несколько уровней allocator-ов.

Упрощённо:

```text
Python object
      ↓
object-specific allocator
      ↓
PyObject allocator
      ↓
pymalloc
      ↓
raw allocator
      ↓
malloc / mmap / VirtualAlloc
      ↓
OS
```

Разные типы объектов могут использовать разные внутренние оптимизации, потому что `int`, `str`, `list`, `dict` и другие структуры имеют разные требования к памяти.

# 10. pymalloc

Одна из ключевых частей стандартного CPython — allocator **pymalloc**.

Он оптимизирован для большого количества **маленьких объектов с коротким временем жизни**.

В актуальном CPython `pymalloc` используется для небольших запросов размером до:

```text
512 bytes
```

Упрощённо:

```text
<= 512 B
    ↓
pymalloc
    ↓
Arena
    ↓
Pool
    ↓
Block
```

Для более крупных запросов используется нижележащий allocator.

# 12. Arena

В классической схеме, которая часто приводится в лекциях:

```text
Arena = 256 KB
```

Если arena заполнена, запрашивается новая. Если arena полностью освобождается, она может быть возвращена операционной системе.

Классическая схема:

```text
Arena = 256 KiB
Pool  = 4 KiB

256 / 4 = 64 pools
```

То есть одна arena содержит **64 пула**.

## Уточнение для современного CPython

Конкретный размер зависит от платформы.

```text
32-bit CPython:
Arena = 256 KiB
Pool  = 4 KiB

64-bit CPython:
Arena = 1 MiB
Pool  = 16 KiB
```

В обоих случаях:

```text
64 pools per arena
```

Поэтому утверждение «arena = 256 KB» сохраняем как классическую/32-битную схему, но в современном 64-битном CPython arena обычно имеет размер **1 MiB**.

Также важно: выделение arena не обязательно означает мгновенное выделение всего этого объёма физической RAM. Обычно речь идёт о виртуальной памяти процесса, физические страницы которой используются по мере необходимости.

---

# 13. Pool

Каждая arena делится на **пулы (`Pools`)**.

В классической схеме:

```text
Pool = 4 KB
```

```text
Arena 256 KB
├── Pool 4 KB
├── Pool 4 KB
├── Pool 4 KB
└── ...
```

В современном 64-битном CPython:

```text
Pool = 16 KiB
Arena = 1 MiB
```

И снова получается 64 pool на arena.

---

# 14. Block

**Block** — конечная ячейка, из которой обслуживается небольшой allocation.

Все блоки внутри одного конкретного pool имеют одинаковый размер.

Например:

```text
Pool A:
[16][16][16][16][16]...

Pool B:
[32][32][32][32][32]...
```

Это уменьшает фрагментацию и ускоряет поиск свободной памяти.

В классическом объяснении размеры блоков кратны **8 байтам**:

```text
8
16
24
32
40
...
512
```

Например, запросу `13 B` может быть выдан блок `16 B`.

> [!note]
> В современном 64-битном CPython alignment может составлять `16 B`, поэтому конкретный шаг size classes зависит от платформы и сборки. На 32-bit сохраняется `8 B` alignment.

# 15. Состояния блоков

Блоки можно логически представить в трёх состояниях.

## Untouched

Память ещё ни разу не использовалась.

```text
[untouched]
```

## Allocated

Блок занят конкретным объектом.

```text
[allocated]
```

## Free

Память раньше использовалась, но объект уже освобождён.

```text
[free]
```

Очень важно:

```text
free block
```

не означает:

```text
память сразу вернулась ОС
```

Обычно блок остаётся внутри pool и используется повторно.

---

# 16. Freeblock
![[Pasted image 20260811155029.png]]

Внутри каждого pool существует указатель `freeblock`, связывающий освободившиеся блоки в односвязный список.

Например:

```text
freeblock
   │
   ▼
[Block 7] → [Block 2] → [Block 15] → NULL
```

Когда блок освобождается, он может быть вставлен в начало этого списка.

Следующее выделение памяти получает готовый свободный блок без полного обхода pool.

Это одна из причин высокой скорости `pymalloc`.

---

# 17. Нетронутая память

Allocator старается не трогать память заранее.

Условно pool может выглядеть так:

```text
[allocated][free][allocated][untouched][untouched][untouched]
```

Часть блоков уже использовалась, а часть ещё ни разу не была нужна.

Идея:

```text
не трогать память до момента реальной необходимости
```

---

# 18. Состояния pool
![[Pasted image 20260811155127.png]]
Пулы можно представить в трёх состояниях:

```text
full
used
free / empty
```

## Used

Pool частично занят:

```text
[used][used][free][used][free]
```

## Full

Все блоки заняты:

```text
[used][used][used][used][used]
```

## Empty / Free

Все блоки доступны:

```text
[free][free][free][free][free]
```

В учебной модели удобно говорить, что пулы группируются по спискам `full`, `used`, `free`.

В реальном `pymalloc` частично используемые pools организованы по size classes в `usedpools`. Полный pool исключается из списка доступных для allocation, а пустой возвращается в список свободных pools своей arena.

# 19. Логика Memory Manager при allocation

Допустим, нужно создать небольшой объект.

Упрощённо:

```text
1. Определяется необходимый размер.
2. Выбирается size class.
3. Ищется partially used pool этого класса.
3.1 Если есть freeblock — берётся готовый блок.
3.2 Если подходящего pool нет — берётся свободный pool.
3.3 Если свободных pools нет — используется/создаётся другая arena.
4. Объект размещается в block.
5. Переменная получает ссылку на объект.
```

Схема:

```text
variable
   ↓
object
   ↓
block
   ↓
pool
   ↓
arena
   ↓
system allocator
   ↓
OS
```

# 20. Управление arena

CPython организует доступные arena в **двухсвязный список**, отсортированный по количеству свободных pools.

Главная идея:

```text
наиболее заполненные arena используются первыми
```

Например:

```text
Arena A = 90% занята
Arena B = 50% занята
Arena C = 10% занята
```

Новый allocation выгоднее направить в `Arena A`, а почти пустую `Arena C` оставить в покое.

Почему?

Потому что `Arena C` имеет шанс полностью освободиться и быть возвращённой системе.

---

# 21. Принцип «экологичности»

В ролике эта логика описывается как **принцип экологичности**:

```text
данные сначала записываются в наиболее заполненные arena
```

Цель — уплотнять уже занятые arena и позволять почти пустым полностью очиститься.

Плохо:

```text
Arena A [██████░░░░]
Arena B [██████░░░░]
Arena C [██████░░░░]
```

Лучше:

```text
Arena A [██████████]
Arena B [████████░░]
Arena C [██░░░░░░░░]
```

Во втором случае `Arena C` ближе к состоянию:

```text
completely empty
```

После чего её можно вернуть системному allocator-у.


## 22. Списки свободных блоков (Free Lists) и переиспользование памяти

Python не всегда возвращает память операционной системе сразу после удаления объекта. Вместо этого он использует механизмы повторного использования:

- **Концепция Free List:** Когда объект (например, кортеж) становится не нужен, он может быть помещен в «список свободных», где он хранится как пустая заготовка.
- **Пример с кортежами:**
    - Пустой кортеж всегда существует в памяти в единственном экземпляре.
    - Python хранит списки освободившихся кортежей разной длины (от 0 до 20 элементов). Для каждого размера может храниться до 2000 объектов (в некоторых версиях до 100).
    - Когда программе снова нужен кортеж того же размера, Python берет заготовку из Free List, что гораздо быстрее, чем выделение новой памяти.
- **Идентификация:** Из-за этого часто возникает ситуация, когда две разные переменные, созданные последовательно, получают один и тот же `id` — просто вторая переменная заняла «ячейку» в памяти, которую только что освободила первая.
