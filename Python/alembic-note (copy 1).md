# Alembic — полная заметка (с конфигами и структурой)

## 1. Что это одним предложением

**Alembic** — инструмент версионирования схемы БД для SQLAlchemy: каждое изменение структуры (новая таблица, колонка, индекс) оформляется отдельным файлом-миграцией с шагами "применить" / "откатить", а файлы связаны в цепочку — как коммиты в Git, только для структуры БД, а не для кода.

## 2. Проблема, которую он решает

Без Alembic структура БД нигде не зафиксирована как текст. Схема существует только "физически" внутри самой базы — её нельзя посмотреть в `git log`, нельзя понять по диффу, что именно изменилось между версией приложения на прошлой неделе и сегодня, нельзя гарантированно воспроизвести на новой машине разработчика или на стейджинге в том же порядке, в каком изменения происходили в реальности. Alembic превращает эволюцию схемы БД в такие же версионируемые файлы, как сам код.

---

## 3. Структура проекта после `alembic init`

Команда `alembic init alembic` (имя папки — по договорённости, часто именно `alembic` или `migrations`) создаёт вот такую структуру внутри проекта:

```
myproject/
├── alembic/
│   ├── versions/                  ← сюда складываются файлы миграций
│   │   ├── ae1027a6acf_initial.py
│   │   ├── 3b9e1a2c9d1_add_orders_table.py
│   │   └── f7c88e2a001_add_cancellation_reason.py
│   ├── env.py                     ← конфигурация окружения (см. ниже)
│   ├── script.py.mako             ← шаблон, по которому генерируются новые файлы миграций
│   └── README
├── alembic.ini                    ← основной конфиг-файл Alembic
├── app/
│   ├── models.py                  ← модели SQLAlchemy
│   └── core/config.py
└── ...
```

Важно: `alembic.ini` и папка `alembic/` создаются **один раз** на проект, а `versions/` дальше пополняется — по одному файлу на каждую миграцию, обычно десятки и сотни файлов за жизнь проекта.

## 4. `alembic.ini` — главный конфиг

Урезанный, но реалистичный вид файла, который генерируется автоматически:

```ini
[alembic]
# путь до папки со скриптами миграций
script_location = alembic

# шаблон имени файла миграции (дата + слаг + ревизия)
file_template = %%(year)d%%(month).2d%%(day).2d_%%(rev)s_%%(slug)s

# строка подключения к БД — ЧАСТО убирается отсюда и переносится в env.py,
# чтобы читать её из переменных окружения/настроек приложения, а не хардкодить в ini
sqlalchemy.url = postgresql://user:pass@localhost/mydb

[loggers]
keys = root,sqlalchemy,alembic

[logger_alembic]
level = INFO
handlers =
qualname = alembic
```

Что здесь реально важно на практике:

- **`script_location`** — Alembic должен знать, где искать/создавать файлы миграций.
- **`sqlalchemy.url`** — строка подключения. В реальных проектах почти всегда **не хранится тут в открытом виде** (иначе пароль от БД лежит в Git) — вместо этого либо оставляют плейсхолдер, либо вообще убирают эту строку из `.ini` и подключение целиком настраивают программно в `env.py`, читая из `.env`/настроек приложения (`settings.database_url`, как в примере с FastAPI, который мы разбирали раньше).
- **`file_template`** — определяет, как будут называться файлы: чаще всего добавляют дату в начало имени файла, чтобы в папке `versions/` файлы визуально сортировались по хронологии, а не только по хэшу ревизии (сам хэш ничего не говорит о порядке на глаз).

## 5. `env.py` — сердце конфигурации, разбор по частям

Это самый важный файл для понимания — именно он связывает Alembic, твои модели SQLAlchemy и реальное подключение к БД. Разберём его по кускам (это упрощённая, но структурно верная версия того, что генерируется по умолчанию и правится руками под конкретный проект):

```python
from logging.config import fileConfig
from sqlalchemy import engine_from_config, pool
from alembic import context

# 1. импортируем метаданные моделей — ОТСЮДА Alembic узнаёт,
#    как ДОЛЖНА выглядеть схема согласно коду приложения
from app.models import Base
from app.core.config import get_settings

config = context.config
fileConfig(config.config_file_name)

# 2. подставляем реальную строку подключения программно,
#    а не из alembic.ini — читаем её из настроек приложения
settings = get_settings()
config.set_main_option("sqlalchemy.url", settings.database_url)

# 3. вот он — target_metadata, ключевая точка для автогенерации
target_metadata = Base.metadata


def run_migrations_offline():
    """Генерация SQL-скрипта БЕЗ подключения к реальной БД."""
    url = config.get_main_option("sqlalchemy.url")
    context.configure(url=url, target_metadata=target_metadata, literal_binds=True)
    with context.begin_transaction():
        context.run_migrations()


def run_migrations_online():
    """Обычный режим: подключаемся к БД и применяем миграции напрямую."""
    connectable = engine_from_config(
        config.get_section(config.config_ini_section),
        prefix="sqlalchemy.",
        poolclass=pool.NullPool,
    )
    with connectable.connect() as connection:
        context.configure(connection=connection, target_metadata=target_metadata)
        with context.begin_transaction():
            context.run_migrations()


if context.is_offline_mode():
    run_migrations_offline()
else:
    run_migrations_online()
```

Разберём три ключевые идеи, которые здесь заложены:

### 5.1 `target_metadata` — это и есть "источник правды" для автогенерации

`Base.metadata` — объект SQLAlchemy, который знает обо всех классах-моделях, унаследованных от `Base` (если они импортированы к этому моменту — отсюда частая ошибка новичков: если модель нигде не импортирована в цепочке импортов, до которой доходит `env.py`, Alembic её просто "не увидит" при автогенерации). Именно сравнение `target_metadata` (что должно быть, согласно коду) с реальной структурой БД (что есть сейчас) и порождает автоматически сгенерированный `upgrade()`.

### 5.2 Offline vs online режим

- **Online** (`run_migrations_online`) — стандартный сценарий: Alembic реально подключается к БД и сразу выполняет SQL-команды. Используется в 95% случаев, в том числе в CI/CD при деплое.
- **Offline** (`run_migrations_offline`) — Alembic **не подключается к БД вообще**, а просто генерирует текст SQL-скрипта, который потом можно передать DBA для ручного прогона на БД, к которой у CI нет прямого доступа (частая практика в банках, страховых компаниях, госсекторе — там, где прод-БД изолирована и доступ к ней строго регламентирован отдельной командой администраторов). `alembic upgrade head --sql` печатает такой скрипт в stdout вместо выполнения.

### 5.3 Асинхронный вариант `env.py`

Если проект использует `AsyncEngine`/`AsyncSession` (как в стеке FastAPI + SQLAlchemy async, который мы разбирали ранее), возникает нюанс: сам Alembic **синхронный** внутри — он не умеет напрямую работать с асинхронным движком. Решение — обернуть асинхронный вызов через `run_sync`, "одолжив" синхронный контекст у event loop'а на время выполнения миграции:

```python
import asyncio
from sqlalchemy.ext.asyncio import async_engine_from_config

def do_run_migrations(connection):
    context.configure(connection=connection, target_metadata=target_metadata)
    with context.begin_transaction():
        context.run_migrations()

async def run_migrations_online():
    connectable = async_engine_from_config(
        config.get_section(config.config_ini_section),
        prefix="sqlalchemy.",
        poolclass=pool.NullPool,
    )
    async with connectable.connect() as connection:
        # run_sync — выполняет обычную синхронную функцию Alembic
        # внутри асинхронного соединения
        await connection.run_sync(do_run_migrations)
    await connectable.dispose()

asyncio.run(run_migrations_online())
```

Важная деталь: сами миграции (сравнение схем, генерация `ALTER TABLE`) — это разовая административная операция, а не часть высоконагруженного асинхронного рантайма приложения, поэтому необходимость на секунду "занять" синхронный вызов внутри `run_sync` не создаёт проблем с блокировкой event loop'а, о которой мы говорили в контексте `async with` — миграции не выполняются во время обработки живых пользовательских запросов.

## 6. Анатомия одного файла миграции

Вот как реально выглядит файл, который генерирует `alembic revision --autogenerate -m "add cancellation reason to orders"`:

```python
"""add cancellation reason to orders

Revision ID: f7c88e2a001
Revises: 3b9e1a2c9d1
Create Date: 2026-09-10 14:22:01.123456
"""
from alembic import op
import sqlalchemy as sa

# --- служебные метаданные ревизии ---
revision = "f7c88e2a001"          # уникальный ID этой миграции
down_revision = "3b9e1a2c9d1"     # ID предыдущей миграции — так строится цепочка
branch_labels = None              # используется при разветвлении истории миграций
depends_on = None                 # явная доп. зависимость от другой ревизии (редко нужно)


def upgrade():
    op.add_column(
        "orders",
        sa.Column("cancellation_reason", sa.String(), nullable=True),
    )


def downgrade():
    op.drop_column("orders", "cancellation_reason")
```

Что здесь стоит заметить:

- **`revision` / `down_revision`** — это буквально связный список. `alembic upgrade head` идёт по цепочке `down_revision` от текущей версии БД (записанной в служебной таблице `alembic_version`) до последней ревизии, у которой никто не ссылается на неё как на `down_revision` — это и есть "голова" (head).
- **`op`** — объект из `alembic.operations`, набор высокоуровневых команд (`add_column`, `create_table`, `drop_index`, `alter_column` и т.д.), которые Alembic транслирует в конкретный диалект SQL (PostgreSQL, MySQL, SQLite — синтаксис `ALTER` у них отличается, `op` абстрагирует эту разницу).
- **`upgrade()` и `downgrade()` — зеркальные операции.** Автогенерация обычно неплохо справляется с генерацией обеих функций автоматически, но для сложных миграций (переименование с потерей данных, смена типа с преобразованием значений) `downgrade()` иногда физически невозможно сделать идеально обратимым — это нормально, и в реальных проектах откат старых миграций делают редко (чаще откатывают деплой целиком другим способом, а не через `downgrade`).

## 7. Служебная таблица `alembic_version`

Alembic создаёт в самой БД (не в файлах, а именно как SQL-таблицу) вот такую структуру:

```
alembic_version
┌──────────────────────────────┐
│ version_num                  │
├──────────────────────────────┤
│ f7c88e2a001                  │
└──────────────────────────────┘
```

Одна колонка, одна строка. Именно по значению в ней Alembic при команде `alembic upgrade head` понимает: "текущая версия БД — `f7c88e2a001`, а голова цепочки в файлах — вот такая, значит нужно выполнить `upgrade()` вот этих N миграций между ними, по порядку". Без этой таблицы Alembic вообще не смог бы понять, что уже применено, а что нет — пришлось бы каждый раз выполнять миграции с нуля или гадать.

## 8. Автогенерация подробнее: что видит, а что нет

Хорошо определяет:

- новую/удалённую таблицу;
- новую/удалённую колонку;
- изменение nullable (`NOT NULL` ↔ nullable);
- добавление/удаление индекса и foreign key (в большинстве диалектов).

Плохо определяет или не видит вовсе:

- **Переименование** колонки или таблицы — автогенерация видит это как "старую удалили, новую добавили" (`drop_column` + `add_column`), что физически **уничтожит данные** в этой колонке при `upgrade()`, если не поправить сгенерированный файл руками на `op.alter_column(..., new_column_name=...)`.
- **Изменение типа данных** со сложным преобразованием (например, `String` → `Integer`, где нужно распарсить строки в числа) — автогенерация предложит голый `ALTER COLUMN TYPE`, но не напишет логику конвертации значений — это дописывается вручную.
- **Изменения, специфичные для конкретной СУБД** (например, добавление `CHECK`-constraint в PostgreSQL с сложным условием) — автогенерация по умолчанию не всегда их отслеживает без дополнительных плагинов/настройки `render_item`.

Поэтому индустриальное правило: **автогенерация — это черновик, а не финальный ответ**. Сгенерированный файл миграции всегда проверяется человеком перед коммитом.

## 9. CLI-команды подробнее

| Команда | Что происходит на самом деле |
|---|---|
| `alembic init alembic` | создаёт структуру папки один раз при старте проекта |
| `alembic revision -m "msg"` | создаёт **пустой** файл миграции — `upgrade()`/`downgrade()` пишутся полностью вручную |
| `alembic revision --autogenerate -m "msg"` | подключается к БД, сравнивает с `target_metadata`, генерирует черновик |
| `alembic upgrade head` | применяет все неприменённые миграции по цепочке до последней |
| `alembic upgrade +1` | применяет только одну следующую миграцию |
| `alembic downgrade -1` | откатывает одну последнюю применённую миграцию |
| `alembic downgrade base` | откатывает вообще всё, до пустой БД |
| `alembic current` | печатает `version_num` из таблицы `alembic_version` текущей БД |
| `alembic history --verbose` | печатает всю цепочку миграций с описаниями |
| `alembic stamp head` | **не выполняя SQL**, просто помечает БД как "будто бы уже на последней версии" — используется, когда схему накатили не через Alembic (например, восстановили из бэкапа), а служебную таблицу нужно синхронизировать вручную |
| `alembic merge -m "merge"` | создаёт merge-миграцию, объединяющую две разошедшиеся "головы" истории |

## 10. Множественные головы (multiple heads) — реальный конфликт в команде

Если два разработчика одновременно создают миграции от одной и той же исходной ревизии (у обоих файлов одинаковый `down_revision`), после слияния веток в Git появляются **два файла, претендующих на звание "головы"**. `alembic upgrade head` в этой ситуации откажется работать и явно сообщит об ошибке "multiple heads".

Решение — `alembic merge heads -m "merge migrations"`, которая создаёт новый файл-миграцию без собственных изменений схемы, но с `down_revision`, указывающим сразу на обе разошедшиеся головы — таким образом цепочка снова становится линейной. Это прямой структурный аналог merge-коммита в Git.

## 11. Реальный порядок действий разработчика на практике

1. Меняет модель SQLAlchemy в коде (`app/models.py`).
2. Запускает `alembic revision --autogenerate -m "..."`.
3. Открывает сгенерированный файл в `versions/`, проверяет и при необходимости правит `upgrade()`/`downgrade()` руками (особенно если там переименование или изменение типа).
4. Локально прогоняет `alembic upgrade head` на своей тестовой БД — убеждается, что миграция реально применяется без ошибок.
5. Коммитит **и изменённую модель, и файл миграции** в одном PR — они логически неразделимы: модель без миграции значит, что код ожидает структуру, которой ещё нет в БД, а миграция без изменения модели — мёртвый код, ничего не отражающий в приложении.
6. В CI/CD, перед раскаткой новой версии приложения, отдельным шагом выполняется `alembic upgrade head` против целевой БД (стейджинг/прод) — только после его успешного завершения запускается сама новая версия кода.

## 12. Итог

| Аспект | Детали |
|---|---|
| Роль | Версионирование схемы БД, компаньон SQLAlchemy |
| Ключевые файлы | `alembic.ini` (конфиг CLI), `env.py` (связка с реальным подключением и моделями), файлы в `versions/` (сами миграции) |
| Как БД узнаёт свою версию | Служебная таблица `alembic_version` с одной строкой |
| Как миграции связаны между собой | Через `revision`/`down_revision` — связный список, как коммиты в Git |
| Главная фича | `--autogenerate` — диф между `target_metadata` (модели в коде) и реальной БД |
| Ограничения автогенерации | Не видит переименования, не пишет конвертацию данных при смене типа — сгенерированное всегда проверяется вручную |
| Offline-режим | Генерирует чистый SQL-скрипт без подключения к БД — для сред с ограниченным прямым доступом |
| Async-стек | Alembic сам синхронный — асинхронный движок оборачивается через `connection.run_sync(...)` |
| Конфликты в команде | Multiple heads при параллельных миграциях — решается через `alembic merge heads` |
| Место в деплое | Отдельный обязательный шаг CI/CD **перед** раскаткой новой версии приложения |
