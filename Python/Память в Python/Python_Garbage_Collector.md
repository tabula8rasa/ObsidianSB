# Освобождение памяти и Garbage Collector в Python

Ниже представлен подробный конспект механизмов освобождения памяти и работы сборщика мусора (**Garbage Collector, GC**) в Python.

---

## 1. Подсчет ссылок (Reference Counting)

Это базовый и интуитивно понятный механизм управления памятью в Python.

### Принцип работы

С каждым объектом ассоциирован параметр `refcount` — счетчик, который знает, сколько ссылок на этот объект существует в данный момент.

Когда создается новая ссылка на объект, например через новую переменную, счетчик увеличивается.

Когда ссылка удаляется или переменная выходит из области видимости, счетчик уменьшается.

Пример:

```python
a = [1, 2, 3]
b = a
```

Теперь и `a`, и `b` ссылаются на один и тот же объект списка.

Условно:

```text
a ──┐
    ├──> [1, 2, 3]
b ──┘
```

Количество ссылок на объект увеличивается.

### Оператор `del`

Вопреки распространенному заблуждению, оператор:

```python
del a
```

не удаляет сам объект из памяти.

Он лишь разрывает связь между именем `a` и объектом.

Если после этого остается:

```python
b = [1, 2, 3]
```

то объект продолжает существовать, поскольку на него все еще есть ссылка через `b`.

### Когда объект удаляется

Как только количество ссылок на объект становится равным нулю:

```text
refcount = 0
```

объект считается ненужным.

В CPython память, занимаемая таким объектом, освобождается немедленно.

Таким образом, основная схема выглядит так:

```text
создание ссылки
      ↓
refcount + 1

удаление ссылки
      ↓
refcount - 1

refcount == 0
      ↓
объект уничтожается
```

### `sys.getrefcount()`

С помощью функции:

```python
sys.getrefcount(obj)
```

можно узнать количество ссылок на объект.

Пример:

```python
import sys

a = []
print(sys.getrefcount(a))
```

Важно учитывать, что `sys.getrefcount()` обычно возвращает значение **на единицу больше ожидаемого**.

Причина в том, что при передаче объекта в функцию:

```python
sys.getrefcount(a)
```

сама функция временно получает еще одну ссылку на этот объект.

То есть вызов функции на короткое время увеличивает `refcount`.

## 2. Проблема циклических ссылок

Механизм подсчета ссылок хорошо работает, пока ссылки между объектами не образуют цикл.

### Пример со списком

Можно создать список, который содержит ссылку на самого себя:

```python
L = []

L.append(L)
```

Получается структура:

```text
L ────────┐
          ↓
      +--------+
      | list   |
      |   └────┼───┐
      +--------+   |
           ↑       |
           └───────┘
```

Список ссылается сам на себя.

Если теперь удалить внешнюю переменную:

```python
del L
```

внешняя ссылка исчезнет.

Но внутри самого объекта остается ссылка на самого себя.

Поэтому его `refcount` не станет равен нулю.

В результате обычный механизм подсчета ссылок не сможет удалить этот объект.

Объект фактически становится недоступен программе, но продолжает занимать память.

### Циклы между несколькими объектами

Циклическая ссылка может состоять не только из одного объекта.

Например:

```python
a = []
b = []

a.append(b)
b.append(a)
```

Получается:

```text
a → object A
      ↓
    object B
      ↑
      └──── object A
```

Если удалить внешние ссылки:

```python
del a
del b
```

объекты останутся ссылаться друг на друга.

Их `refcount` не станет нулевым.

### Распространенность циклических ссылок

Циклические ссылки — обычное явление.

Например, экземпляры классов имеют связь со своим классом, класс связан с модулем, в котором он определен, а модуль хранит ссылки на определенные в нем объекты.

То есть граф объектов Python может быть достаточно сложным и содержать множество взаимных ссылок.

Именно поэтому одного только механизма Reference Counting недостаточно.

---

## 3. Сборщик мусора (Garbage Collector)

Для борьбы с циклическими ссылками в Python предусмотрен специальный механизм — **Garbage Collector**, или **GC**.

Главная задача GC — обнаруживать группы объектов, которые:

- ссылаются друг на друга;
- больше недоступны из программы;
- не могут быть удалены обычным подсчетом ссылок.

---

## 4. Какие объекты отслеживает Garbage Collector

GC работает не со всеми объектами Python.

Простые и неизменяемые типы, например:

```python
int
str
```

обычно удаляются только через обычный механизм подсчета ссылок.

Сборщик мусора прежде всего нужен для объектов, которые могут содержать ссылки на другие объекты.

Например:

```python
list
dict
class
instance
```

и другие контейнерные или сложные объекты.

Такие объекты могут участвовать в циклических структурах.

### Объекты под надзором GC

На уровне CPython объекты, за которыми следит Garbage Collector, имеют дополнительную служебную информацию.

В частности:

```text
gc_next
gc_prev
gc_refs
```

### `gc_next` и `gc_prev`

`gc_next` и `gc_prev` используются для связывания объектов между собой во внутренних структурах Garbage Collector.

Условно они позволяют GC организовать отслеживаемые объекты в связанные структуры данных.

### `gc_refs`

`gc_refs` — дополнительный счетчик ссылок, который используется самим сборщиком мусора во время анализа достижимости объектов.

Он отличается от обычного `refcount`.

Обычный `refcount` используется постоянно механизмом подсчета ссылок.

`gc_refs` нужен GC для временных вычислений во время поиска циклов.

### `tp_traverse`

Типы объектов, поддерживающие работу циклического GC, предоставляют механизм:

```text
tp_traverse
```

Он позволяет сборщику мусора пройти по ссылкам, которые объект хранит на другие Python-объекты.

Другими словами, GC может спросить объект:

> На какие другие объекты ты ссылаешься?

### `tp_clear`

Также используется механизм:

```text
tp_clear
```

Он позволяет очистить ссылки внутри объекта.

Это необходимо для разрушения циклических структур.

Например:

```text
A → B
↑   ↓
└───┘
```

Если GC определил, что цикл больше недоступен программе, он может разорвать внутренние ссылки между объектами.

После этого обычный `refcount` сможет упасть до нуля, и объекты будут уничтожены.

## 5. Алгоритм поиска циклических ссылок

Сборщик мусора проходит через несколько фаз, чтобы найти и уничтожить мертвые циклы.

---

### Шаг 1. Копирование счетчиков

Для каждого отслеживаемого объекта значение обычного:

```text
refcount
```

копируется во временный счетчик:

```text
gc_refs
```

Условно:

```text
gc_refs = refcount
```

Например:

```text
Object A

refcount = 3
gc_refs   = 3
```

---

### Шаг 2. Эмуляция удаления внутренних ссылок

GC проходит по всем отслеживаемым объектам.

Используя:

```text
tp_traverse
```

он определяет, на какие другие объекты ссылается каждый объект.

После этого для каждой внутренней ссылки уменьшается соответствующий `gc_refs`.

То есть GC как бы моделирует ситуацию:

> Что произойдет, если не учитывать ссылки объектов друг на друга?

Например:

```text
A → B
B → A
```

Изначально:

```text
A.gc_refs = A.refcount
B.gc_refs = B.refcount
```

Затем GC видит:

```text
A → B
```

и уменьшает:

```text
B.gc_refs -= 1
```

Потом видит:

```text
B → A
```

и уменьшает:

```text
A.gc_refs -= 1
```

Таким образом из счетчиков вычитаются ссылки, которые принадлежат самой анализируемой группе объектов.

---

### Шаг 3. Определение достижимости

После вычитания внутренних ссылок GC анализирует `gc_refs`.

Если:

```text
gc_refs > 0
```

значит, на объект существует ссылка **извне анализируемого цикла**.

Следовательно, объект все еще достижим программой и не является мусором.

Если:

```text
gc_refs == 0
```

объект считается потенциально недостижимым.

Такие объекты помещаются в отдельный список кандидатов на удаление.

Условно:

```text
gc_refs > 0
    ↓
живой объект

gc_refs == 0
    ↓
кандидат на удаление
```

---

### Шаг 4. Восстановление достижимых объектов

Одного значения:

```text
gc_refs == 0
```

недостаточно, чтобы сразу удалить объект.

Может возникнуть ситуация, когда достижимый объект ссылается на объект, который ранее был признан потенциально недостижимым.

Например:

```text
ROOT
 ↓
 A
 ↓
 B
 ↔
 C
```

Если `A` достижим из программы, то объекты `B` и `C` также должны считаться живыми, даже если после первоначального анализа их `gc_refs` оказался равен нулю.

Поэтому GC дополнительно проходит по достижимым объектам.

Если достижимый объект ссылается на объект из списка потенциально недостижимых, этот объект восстанавливается в статусе живого.

Затем проверяются его ссылки и так далее.

По сути выполняется распространение достижимости.

---

### Шаг 5. Очистка настоящих циклов

После восстановления достижимых объектов остаются объекты, которые действительно недоступны программе.

Например:

```text
A ↔ B
```

и никаких внешних ссылок на `A` или `B` больше нет.

Тогда Garbage Collector использует:

```text
tp_clear
```

чтобы разорвать внутренние ссылки.

После разрыва цикла:

```text
A → B
B → A
```

превращается условно в:

```text
A    B
```

Ссылки друг на друга исчезают.

После этого обычные счетчики:

```text
refcount
```

падают до нуля.

И объекты окончательно уничтожаются стандартным механизмом Reference Counting.

---

## 6. Общая схема работы GC

Упрощенно алгоритм можно представить так:

```text
tracked objects
      ↓
копируем refcount → gc_refs
      ↓
вычитаем внутренние ссылки
      ↓
gc_refs > 0 ?
   /        \
 yes        no
 ↓           ↓
живой     потенциально
объект    недостижимый
              ↓
       проверка достижимости
              ↓
        настоящий мусор
              ↓
          tp_clear
              ↓
       refcount → 0
              ↓
       уничтожение объекта
```

## 7. Концепция поколений (Generational GC)

Проверять абсолютно все объекты Python при каждом запуске Garbage Collector было бы слишком дорого.

Поэтому используется идея **поколений**.

Объекты разделяются на поколения:

```text
Generation 0
Generation 1
Generation 2
```

или:

```text
0 → 1 → 2
```

---

### Поколение 0

Все новые объекты сначала попадают в:

```text
Generation 0
```

Это самое молодое поколение.

Оно проверяется Garbage Collector чаще всего.

Причина проста: статистически большинство временных объектов живет недолго.

Например:

```python
def calculate():
    data = []
    ...
```

После завершения функции временные объекты часто становятся ненужными.

---

### Поколение 1

Если объект пережил сборку поколения 0, он перемещается в более старшее поколение:

```text
Generation 1
```

Это означает, что объект уже прожил некоторое время и, вероятно, будет использоваться дальше.

Поэтому проверять его можно реже.

---

### Поколение 2

Если объект продолжает выживать после следующих сборок, он перемещается в:

```text
Generation 2
```

Это самое старое поколение.

Такие объекты проверяются реже всего.

Общая логика:

```text
новый объект
     ↓
Generation 0
     ↓ survived
Generation 1
     ↓ survived
Generation 2
```

Статистическая идея:

> Чем дольше объект уже прожил, тем выше вероятность, что он понадобится программе еще долго.

---

## 8. Пороги Garbage Collector

Для определения момента запуска сборки используются специальные пороги:

```python
gc.get_threshold()
```

В описываемом механизме используются значения:

```text
(700, 10, 10)
```

Их можно изменить через:

```python
gc.set_threshold(n1, n2, n3)
```

---

### Первый порог — `700`

Первый порог относится к поколению 0.

Сборка запускается, когда разница между количеством созданных и удаленных отслеживаемых объектов достигает определенного значения.

Условно:

```text
создано объектов - удалено объектов >= 700
```

После этого запускается GC для молодого поколения.

---

### Второй порог — `10`

Второе значение связано с поколением 1.

Сборка поколения 1 выполняется примерно после определенного количества сборок поколения 0.

В рассматриваемом описании:

```text
10 сборок Generation 0
        ↓
сборка Generation 1
```

---

### Третий порог — `10`

Третье значение связано с самым старым поколением.

В рассматриваемом алгоритме сборка поколения 2 запускается после определенного количества сборок поколения 1.

Условно:

```text
10 сборок Generation 1
        ↓
проверка Generation 2
```

При этом учитывается дополнительная эвристика: доля новых объектов в старшем поколении должна превысить примерно `25%`.

Идея заключается в том, чтобы не сканировать большое количество старых долгоживущих объектов слишком часто.

---

## 9. Ручное управление Garbage Collector

Для управления сборщиком мусора используется встроенный модуль:

```python
gc
```

Подключение:

```python
import gc
```

---

### `gc.collect()`

Функция:

```python
gc.collect()
```

принудительно запускает сборщик мусора.

Можно также передать номер поколения:

```python
gc.collect(0)
gc.collect(1)
gc.collect(2)
```

То есть можно принудительно инициировать сборку конкретного поколения.

---

### `gc.set_threshold()`

Пороговые значения можно изменить:

```python
gc.set_threshold(n1, n2, n3)
```

Например:

```python
import gc

gc.set_threshold(500, 10, 10)
```

Если уменьшить первый порог:

```text
700 → 500
```

GC будет запускаться чаще.

Это может уменьшить потребление памяти, но увеличить нагрузку на CPU.

Если увеличить порог:

```text
700 → 5000
```

GC будет запускаться реже.

Это может повысить производительность за счет меньшего количества сборок, но программа потенциально будет дольше удерживать недостижимые циклические объекты в памяти.

Получается компромисс:

```text
GC чаще
↓
меньше удерживаемой памяти
↓
больше накладных расходов CPU
```

и наоборот:

```text
GC реже
↓
меньше накладных расходов CPU
↓
больше потенциально удерживаемой памяти
```

---

## 10. Почему не стоит постоянно вызывать `gc.collect()`

Принудительный вызов:

```python
gc.collect()
```

может показаться хорошей идеей.

Например:

```python
for batch in batches:
    process(batch)
    gc.collect()
```

Но без реальной необходимости делать это обычно не рекомендуется.

Garbage Collector уже содержит внутренние эвристики, статистику и пороги, которые определяют подходящий момент для запуска сборки.

Постоянный ручной вызов:

```python
gc.collect()
```

может нарушать естественную работу этих эвристик и создавать лишние паузы.

Особенно дорого может стоить полная проверка большого количества объектов.

Поэтому лучше сначала определить реальную причину роста памяти.

Для этого используются:

- профайлеры памяти;
- анализ количества объектов;
- поиск циклических ссылок;
- анализ удерживаемых ссылок;
- настройка порогов GC под конкретную нагрузку.

И только после измерений имеет смысл вмешиваться в стандартную работу Garbage Collector.

## 11. Итоговая архитектура освобождения памяти в CPython

Упрощенно управление временем жизни объектов можно представить следующим образом:

```text
Python object
      ↓
Reference Counting
      ↓
refcount == 0 ?
   /        \
 yes         no
 ↓            ↓
удалить     объект остается
объект      в памяти
                ↓
        может быть цикл?
                ↓
          Garbage Collector
                ↓
        анализ достижимости
                ↓
      недостижимый цикл?
           /        \
         yes         no
          ↓           ↓
      tp_clear      оставить
          ↓
     refcount → 0
          ↓
        удалить
```

Таким образом, в CPython используются два взаимодополняющих механизма:

1. **Reference Counting** — основной механизм, который удаляет большинство объектов сразу после исчезновения последней ссылки.
2. **Garbage Collector** — дополнительный механизм, предназначенный прежде всего для обнаружения и уничтожения недостижимых циклических структур.

## 12. Краткое резюме

**Reference Counting:**

```text
есть ссылка → refcount увеличивается
ссылка исчезает → refcount уменьшается
refcount = 0 → объект удаляется
```

**`del`:**

```python
del variable
```

удаляет не объект, а ссылку имени на объект.

**Проблема циклов:**

```text
A → B
↑   ↓
└───┘
```

После исчезновения внешних ссылок `refcount` объектов может оставаться больше нуля.

**Garbage Collector:**

```text
копирует refcount → gc_refs
↓
вычитает внутренние ссылки
↓
определяет достижимые объекты
↓
находит недостижимые циклы
↓
разрывает их через tp_clear
↓
refcount падает до 0
↓
объекты удаляются
```

**Поколения:**

```text
Generation 0 → Generation 1 → Generation 2
```

Новые объекты проверяются часто, старые — реже.

**Пороги:**

```text
(700, 10, 10)
```

используются для определения частоты запуска разных поколений GC.

**Ручное управление:**

```python
gc.collect()
gc.set_threshold(...)
```

доступно, но использовать его без измерений и реальной необходимости обычно не стоит.
