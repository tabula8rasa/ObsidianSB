# Управление памятью в Python
> [!important]
> Ниже речь в первую очередь идёт о **CPython** — стандартной и самой распространённой реализации Python. Сам язык Python не требует, чтобы все реализации использовали именно `pymalloc`, арены, пулы и подсчёт ссылок в том виде, в котором это делает CPython.

## Общая схема

```text
Python-код
    ↓
Python-объекты
    ↓
Memory Manager CPython
    ↓
pymalloc / object-specific allocators / system allocator
    ↓
виртуальная память процесса
    ↓
операционная система
    ↓
RAM / swap
```

Python использует **автоматическое управление памятью**. Программист создаёт объекты и работает с ними, а выделением, переиспользованием и освобождением памяти занимается интерпретатор.

---

# 1. Взаимодействие программы с операционной системой

## Опосредованный доступ

Программы и процессы в Python не могут напрямую обращаться к физической оперативной памяти. Между «железом» и программой всегда стоит **операционная система**.

Обычный процесс работает прежде всего с **виртуальным адресным пространством**. Например, Python может иметь указатель:

```text
0x7f2c8a123400
```

Но это не означает, что объект физически лежит по такому адресу в RAM. ОС и процессор через таблицы страниц сопоставляют виртуальные адреса процесса физическим страницам памяти.

Упрощённо:

```text
Python
  ↓
виртуальный адрес
  ↓
таблицы страниц
  ↓
RAM / swap
```

## Запрос и возврат памяти

Чтобы использовать память, интерпретатор запрашивает её у ОС определёнными долями — кусочками. В идеале ненужная память должна максимально эффективно освобождаться и при возможности возвращаться операционной системе, чтобы избежать утечек и нехватки ресурсов.

Но важно различать:

```text
Python-объект уничтожен
```

и:

```text
память возвращена операционной системе
```

Это **не одно и то же**.

Часто происходит так:

```text
объект уничтожен
      ↓
блок стал свободным
      ↓
CPython оставил память у себя
      ↓
позже использовал её для нового объекта
```

Поэтому после `del obj` или удаления большого количества объектов RSS процесса не обязан сразу уменьшиться.

# 2. Фрагментация памяти

При неаккуратном заполнении памяти возникает **фрагментация** — ситуация, когда между занятыми участками остаются свободные «дыры».

Например:

```text
[занято][свободно][занято][свободно][занято]
```

Свободной памяти суммарно может быть достаточно, но отдельного непрерывного участка нужного размера может не оказаться.

Это называется **внешней фрагментацией**.

Также существует **внутренняя фрагментация**. Например, если объекту нужно `17` байт, а allocator выдаёт блок `32` байта:

```text
нужно:      17 B
выделено:   32 B
не занято:  15 B
```

Эти лишние байты находятся уже внутри выделенного блока.

# 3. Stack и Heap

Для понимания работы памяти Python удобно логически разделять память на две основные структуры:

```text
Stack
Heap
```

Но это учебная модель.

> [!warning]
> Фраза «все локальные переменные Python физически лежат в обычном машинном stack» является упрощением. Корректнее говорить о **логическом стеке вызовов Python**, состоящем из кадров выполнения (`frames`). Ссылки на локальные значения принадлежат состоянию frame. То, как frame связан с нативным C-stack, — деталь реализации CPython.

---

# 4. Стек вызовов — Call Stack

Стек вызовов работает по принципу:

```text
LIFO
Last In — First Out
```

Например:

```python
def c():
    return 10


def b():
    return c()


def a():
    return b()


a()
```

Логически стек развивается так:

```text
a()
```

```text
a()
└── b()
```

```text
a()
└── b()
    └── c()
```

После завершения `c()` её кадр убирается, затем `b()`, затем `a()`.

---

# 5. Frame — кадр вызова

Для каждого вызова функции создаётся **кадр (`frame`)** — структура, содержащая состояние выполнения функции.

В нём логически находятся:

- аргументы;
- локальные переменные;
- ссылки на используемые Python-объекты;
- информация о текущем месте выполнения;
- служебное состояние интерпретатора.

Например:

```python
def calculate(a, b):
    result = a + b
    return result
```

Можно представить:

```text
Frame calculate
├── a      → ссылка на объект
├── b      → ссылка на объект
├── result → ссылка на объект
└── состояние выполнения
```

Когда функция завершается, её активный кадр обычно больше не нужен. Именно поэтому локальные имена функции перестают быть доступны снаружи.

Однако завершение функции **не означает**, что все объекты, использовавшиеся внутри неё, обязательно уничтожаются. Если на объект существует другая ссылка, объект продолжает жить.

Кроме того, сам frame иногда может продолжать существовать, например если его удерживает traceback, generator, coroutine или debugger.

# 6. Heap — куча

**Куча (`Heap`)** — большая область памяти, где хранятся Python-объекты и внутренние структуры интерпретатора.

Именно здесь логически находятся:

```text
int
float
str
list
dict
set
tuple
function
class
instance
...
```

Официальная документация CPython называет её **private heap**.

---

# 7. Переменная — это ссылка на объект

Очень важно понимать:

```python
x = 1000
```

полезнее представлять так:

```text
x ─────► int object 1000
```

Сама переменная хранит не объект «внутри себя», а связь имени с объектом.

Например:

```python
a = [1, 2, 3]
b = a
```

Логически:

```text
a ─────┐
       ▼
   [1, 2, 3]
       ▲
b ─────┘
```

Нового списка при `b = a` не создаётся.

```python
a is b
```

даст:

```text
True
```

# 8. Что знает Python-объект

В обычном CPython объект имеет служебный заголовок.

Упрощённо:

```text
Python object
├── reference count
├── pointer to type
└── object-specific data
```

То есть объект знает свой тип данных и содержит служебную информацию для подсчёта ссылок.

Например:

```text
PyLongObject
├── refcount
├── type → int
└── значение
```

> [!note]
> Фраза «объект знает точное количество ссылающихся на него переменных» тоже немного упрощена. Ссылками могут быть не только переменные. Кроме того, в современных версиях CPython существуют **immortal objects**, для которых refcount не обязан буквально совпадать с реальным количеством ссылок.

Подробнее это относится к [[Reference Counting in Python]].

# 9. Memory Manager

За распределение памяти отвечает **Python Memory Manager**.

Это не одна функция, а несколько уровней allocator-ов.

Упрощённо:

```text
Python object
      ↓
object-specific allocator
      ↓
PyObject allocator
      ↓
pymalloc
      ↓
raw allocator
      ↓
malloc / mmap / VirtualAlloc
      ↓
OS
```

Разные типы объектов могут использовать разные внутренние оптимизации, потому что `int`, `str`, `list`, `dict` и другие структуры имеют разные требования к памяти.

---

# 10. pymalloc

Одна из ключевых частей стандартного CPython — allocator **pymalloc**.

Он оптимизирован для большого количества **маленьких объектов с коротким временем жизни**.

В актуальном CPython `pymalloc` используется для небольших запросов размером до:

```text
512 bytes
```

Упрощённо:

```text
<= 512 B
    ↓
pymalloc
    ↓
Arena
    ↓
Pool
    ↓
Block
```

Для более крупных запросов используется нижележащий allocator.

---

# 11. Иерархия кучи: Arena → Pool → Block

Для борьбы с фрагментацией `pymalloc` использует иерархию:

```text
Arena
  ↓
Pool
  ↓
Block
  ↓
Python object
```

Схематично:

```text
OS
 │
 ▼
Arena
 ├── Pool
 │    ├── Block
 │    ├── Block
 │    └── ...
 ├── Pool
 ├── Pool
 └── ...
```

---

# 12. Arena

В классической схеме, которая часто приводится в лекциях:

```text
Arena = 256 KB
```

Если arena заполнена, запрашивается новая. Если arena полностью освобождается, она может быть возвращена операционной системе.

Классическая схема:

```text
Arena = 256 KiB
Pool  = 4 KiB

256 / 4 = 64 pools
```

То есть одна arena содержит **64 пула**.

## Уточнение для современного CPython

Конкретный размер зависит от платформы.

```text
32-bit CPython:
Arena = 256 KiB
Pool  = 4 KiB

64-bit CPython:
Arena = 1 MiB
Pool  = 16 KiB
```

В обоих случаях:

```text
64 pools per arena
```

Поэтому утверждение «arena = 256 KB» сохраняем как классическую/32-битную схему, но в современном 64-битном CPython arena обычно имеет размер **1 MiB**.

Также важно: выделение arena не обязательно означает мгновенное выделение всего этого объёма физической RAM. Обычно речь идёт о виртуальной памяти процесса, физические страницы которой используются по мере необходимости.

---

# 13. Pool

Каждая arena делится на **пулы (`Pools`)**.

В классической схеме:

```text
Pool = 4 KB
```

```text
Arena 256 KB
├── Pool 4 KB
├── Pool 4 KB
├── Pool 4 KB
└── ...
```

В современном 64-битном CPython:

```text
Pool = 16 KiB
Arena = 1 MiB
```

И снова получается 64 pool на arena.

---

# 14. Block

**Block** — конечная ячейка, из которой обслуживается небольшой allocation.

Все блоки внутри одного конкретного pool имеют одинаковый размер.

Например:

```text
Pool A:
[16][16][16][16][16]...

Pool B:
[32][32][32][32][32]...
```

Это уменьшает фрагментацию и ускоряет поиск свободной памяти.

В классическом объяснении размеры блоков кратны **8 байтам**:

```text
8
16
24
32
40
...
512
```

Например, запросу `13 B` может быть выдан блок `16 B`.

> [!note]
> В современном 64-битном CPython alignment может составлять `16 B`, поэтому конкретный шаг size classes зависит от платформы и сборки. На 32-bit сохраняется `8 B` alignment.

---

# 15. Состояния блоков

Блоки можно логически представить в трёх состояниях.

## Untouched

Память ещё ни разу не использовалась.

```text
[untouched]
```

## Allocated

Блок занят конкретным объектом.

```text
[allocated]
```

## Free

Память раньше использовалась, но объект уже освобождён.

```text
[free]
```

Очень важно:

```text
free block
```

не означает:

```text
память сразу вернулась ОС
```

Обычно блок остаётся внутри pool и используется повторно.

---

# 16. Freeblock

Внутри каждого pool существует указатель `freeblock`, связывающий освободившиеся блоки в односвязный список.

Например:

```text
freeblock
   │
   ▼
[Block 7] → [Block 2] → [Block 15] → NULL
```

Когда блок освобождается, он может быть вставлен в начало этого списка.

Следующее выделение памяти получает готовый свободный блок без полного обхода pool.

Это одна из причин высокой скорости `pymalloc`.

---

# 17. Нетронутая память

Allocator старается не трогать память заранее.

Условно pool может выглядеть так:

```text
[allocated][free][allocated][untouched][untouched][untouched]
```

Часть блоков уже использовалась, а часть ещё ни разу не была нужна.

Идея:

```text
не трогать память до момента реальной необходимости
```

---

# 18. Состояния pool

Пулы можно представить в трёх состояниях:

```text
full
used
free / empty
```

## Used

Pool частично занят:

```text
[used][used][free][used][free]
```

## Full

Все блоки заняты:

```text
[used][used][used][used][used]
```

## Empty / Free

Все блоки доступны:

```text
[free][free][free][free][free]
```

В учебной модели удобно говорить, что пулы группируются по спискам `full`, `used`, `free`.

В реальном `pymalloc` частично используемые pools организованы по size classes в `usedpools`. Полный pool исключается из списка доступных для allocation, а пустой возвращается в список свободных pools своей arena.

---

# 19. Логика Memory Manager при allocation

Допустим, нужно создать небольшой объект.

Упрощённо:

```text
1. Определяется необходимый размер.
2. Выбирается size class.
3. Ищется partially used pool этого класса.
4. Если есть freeblock — берётся готовый блок.
5. Если подходящего pool нет — берётся свободный pool.
6. Если свободных pools нет — используется/создаётся другая arena.
7. Объект размещается в block.
8. Переменная получает ссылку на объект.
```

Схема:

```text
variable
   ↓
object
   ↓
block
   ↓
pool
   ↓
arena
   ↓
system allocator
   ↓
OS
```

---

# 20. Переиспользование памяти

После удаления небольшого объекта обычно не происходит:

```text
object
↓
free()
↓
OS
```

Вместо этого:

```text
object deleted
      ↓
block becomes free
      ↓
block остаётся внутри pool
      ↓
block используется повторно
```

Например:

```python
a = SomeObject()
del a

b = AnotherObject()
```

Вполне возможно, что второй объект использует память, ранее принадлежавшую первому.

---

# 21. Управление arena

CPython организует доступные arena в **двухсвязный список**, отсортированный по количеству свободных pools.

Главная идея:

```text
наиболее заполненные arena используются первыми
```

Например:

```text
Arena A = 90% занята
Arena B = 50% занята
Arena C = 10% занята
```

Новый allocation выгоднее направить в `Arena A`, а почти пустую `Arena C` оставить в покое.

Почему?

Потому что `Arena C` имеет шанс полностью освободиться и быть возвращённой системе.

---

# 22. Принцип «экологичности»

В ролике эта логика описывается как **принцип экологичности**:

```text
данные сначала записываются в наиболее заполненные arena
```

Цель — уплотнять уже занятые arena и позволять почти пустым полностью очиститься.

Плохо:

```text
Arena A [██████░░░░]
Arena B [██████░░░░]
Arena C [██████░░░░]
```

Лучше:

```text
Arena A [██████████]
Arena B [████████░░]
Arena C [██░░░░░░░░]
```

Во втором случае `Arena C` ближе к состоянию:

```text
completely empty
```

После чего её можно вернуть системному allocator-у.

---

# 23. Когда память возвращается ОС

Уровни освобождения удобно представить так:

```text
Object destroyed
      ↓
Block free
      ↓
Pool eventually empty
      ↓
Arena eventually empty
      ↓
Arena can be returned
      ↓
OS/system allocator
```

То есть освобождение одного блока не означает возврат памяти ОС.

Чтобы `pymalloc` смог отдать крупный участок назад, обычно должна освободиться **вся arena**.

---

# 24. Почему RSS процесса может не уменьшаться

Допустим, приложение создало миллион маленьких объектов, а затем почти все удалило.

Если в каждой arena остался хотя бы один живой объект:

```text
Arena 1 → 1 объект
Arena 2 → 1 объект
Arena 3 → 1 объект
Arena 4 → 1 объект
...
```

эти arena нельзя целиком освободить.

Получается:

```text
объектов почти не осталось
```

но:

```text
процесс всё ещё удерживает большой объём памяти
```

Это может быть следствием фрагментации и стратегии allocator-а, а не настоящей утечки.

---

# 25. Memory leak и удержание памяти allocator-ом

Это разные вещи.

## Логическая утечка

```python
cache = []

while True:
    cache.append(load_something())
```

Объекты продолжают быть достижимыми через `cache`, поэтому Python не имеет права их удалить.

## Память освобождена внутри Python, но не возвращена ОС

```text
object destroyed
↓
block free
↓
pool остаётся
↓
arena всё ещё нужна
↓
RSS не уменьшается
```

Поэтому:

```text
RSS не уменьшился
```

ещё не означает:

```text
memory leak
```

---

# 26. Большие allocations

Иерархия:

```text
Arena → Pool → Block
```

в первую очередь относится к небольшим allocations, обслуживаемым `pymalloc`.

В актуальном CPython порог составляет:

```text
512 B
```

Более крупный запрос передаётся нижележащему allocator-у.

Например:

```python
data = bytearray(100_000_000)
```

не следует представлять как один маленький block внутри обычного pool.

Также составной объект может иметь несколько allocations. Например, `list` содержит сам объект списка и отдельный внутренний массив ссылок на элементы.

---

# 27. Удаление переменной и удаление объекта

Очень важное правило:

```python
del x
```

не означает:

```text
немедленно уничтожить объект и вернуть память ОС
```

`del x` удаляет связь имени `x` с объектом.

Например:

```python
a = []
b = a

del a
```

Объект всё ещё существует:

```text
b ─────► []
```

Пока есть другая сильная ссылка, объект продолжает жить.

---

# 28. Reference Counting

CPython в значительной степени использует **подсчёт ссылок**.

Упрощённо:

```text
object
└── refcount
```

Например:

```python
a = []
```

```text
a ───► list
```

Затем:

```python
b = a
```

```text
a ──┐
    ├──► list
b ──┘
```

После удаления одной ссылки объект продолжает жить. Когда последняя сильная ссылка исчезает, обычный объект CPython обычно может быть уничтожен.

Но подсчёт ссылок не решает проблему циклических ссылок, поэтому существует [[Garbage Collector in Python]].

---

# 29. Garbage Collector

Python имеет автоматическое управление памятью, но:

```text
Memory Manager
```

и:

```text
Garbage Collector
```

не являются полными синонимами.

**Memory Manager** управляет выделением, организацией, переиспользованием и освобождением памяти.

**Reference Counting** отслеживает сильные ссылки.

**Garbage Collector** в CPython нужен прежде всего для поиска циклических структур, которые один reference counting удалить не может.

Например:

```python
a = []
b = []

a.append(b)
b.append(a)
```

Получается цикл:

```text
a-list ─────► b-list
   ▲           │
   └───────────┘
```

Эта тема продолжается в [[Garbage Collector in Python]].

# 30. Почему Python не вызывает системный allocator для каждого объекта

Если бы каждый маленький объект приводил к:

```text
malloc
free
malloc
free
malloc
free
```

это было бы дорого.

Python постоянно создаёт множество небольших объектов, поэтому выгоднее:

```text
OS
↓
крупная arena
↓
много pools
↓
много blocks
↓
быстрые allocations Python
```

После уничтожения объекта block остаётся у allocator-а и быстро переиспользуется.

# 31. Пример полного жизненного цикла

```python
def foo():
    a = [1, 2, 3]
    b = a
    return b


x = foo()
```

Логически:

```text
1. Вызывается foo().
2. Создаётся frame.
3. Создаётся объект list.
4. a получает ссылку на list.
5. b получает ссылку на тот же list.
6. Ссылка возвращается наружу.
7. foo() завершается.
8. Локальные имена a и b исчезают.
9. Сам list остаётся, потому что на него ссылается x.
```

После выполнения:

```text
x ─────► [1, 2, 3]
```

После:

```python
del x
```

если других сильных ссылок нет, объект списка может быть уничтожен. Но его память не обязана немедленно вернуться ОС — allocator может оставить её для повторного использования.

# 32. Инструменты для наблюдения за памятью

## `id()`

```python
x = [1, 2, 3]

print(id(x))
print(hex(id(x)))
```

В CPython `id()` обычно связан с адресом объекта на протяжении его жизни. Но на уровне самого языка гарантируется прежде всего уникальность `id` среди одновременно живых объектов.

## `sys.getsizeof()`

```python
import sys

x = []
print(sys.getsizeof(x))
```

Он показывает непосредственный размер объекта, но не обязательно полный объём памяти всей структуры вместе со всеми объектами, на которые она ссылается.

## `tracemalloc`

```python
import tracemalloc

tracemalloc.start()

data = [str(i) for i in range(100_000)]

current, peak = tracemalloc.get_traced_memory()
print("current:", current)
print("peak:", peak)

tracemalloc.stop()
```

`tracemalloc` помогает понять, где в Python-коде происходили allocations.

## `PYTHONMALLOCSTATS`

Для низкоуровневой диагностики CPython:

```bash
PYTHONMALLOCSTATS=1 python script.py
```

Можно получить статистику allocator-а, включая arena/pool данные.

# 33. Практический смысл архитектуры

Вся архитектура существует ради нескольких целей:

- ускорить создание маленьких объектов;
- уменьшить количество обращений к системному allocator-у;
- переиспользовать ранее выделенную память;
- уменьшить фрагментацию;
- группировать blocks по размеру;
- дать полностью освободившимся arena шанс быть возвращёнными системе.

Основная схема:

```text
OS
↓
Memory Manager
↓
pymalloc
↓
Arena
↓
Pool
↓
Block
↓
Python object
```

# 34. Важные уточнения к классической схеме

## Это CPython, а не обязательное устройство любого Python

`pymalloc`, `PyObject`, refcount, arena/pool/block — детали реализации CPython.

## Arena не всегда 256 KB

Классическая схема:

```text
Arena = 256 KiB
Pool  = 4 KiB
```

А в современном 64-bit CPython:

```text
Arena = 1 MiB
Pool  = 16 KiB
```

## Blocks не всегда с шагом 8 B

Классическое объяснение использует:

```text
8 B
```

На 64-bit CPython alignment может быть:

```text
16 B
```

## Не все allocations идут через pymalloc

`pymalloc` оптимизирован для небольших запросов до:

```text
512 B
```

## Frame — не просто обычный машинный stack frame

Для обучения удобно говорить:

```text
function call → frame → locals
```

Но физическое устройство современного CPython сложнее.

## Уничтожение объекта не равно возврату памяти ОС

```text
object destroyed
↓
block free
↓
pool available
↓
arena potentially empty
↓
system allocator
↓
OS
```

# 35. Заключение

Python — язык с **автоматическим управлением памятью**. В отличие от C или C++, где программист часто самостоятельно выделяет и освобождает память, в Python за это отвечает Memory Manager.

Это избавляет разработчика от большинства низкоуровневых ошибок управления памятью, хотя делает процесс менее гибким и менее прямым.

Программы не работают напрямую с физической RAM. Между приложением и памятью находятся виртуальное адресное пространство процесса, системный allocator и операционная система.

Для маленьких allocations CPython обычно использует `pymalloc` и иерархию:

```text
Arena
↓
Pool
↓
Block
```

В классической схеме:

```text
Arena = 256 KiB
Pool  = 4 KiB
64 pools per arena
```

В современном 64-bit CPython:

```text
Arena = 1 MiB
Pool  = 16 KiB
64 pools per arena
small allocations <= 512 B
```

Переменные являются ссылками на объекты:

```text
variable
   ↓
object
```

Объекты знают свой тип и в CPython содержат данные для подсчёта ссылок.

После удаления объекта его block обычно не возвращается ОС сразу. Он становится свободным и используется повторно:

```text
Allocated
    ↓
Free
    ↓
Reused
```

Python старается использовать наиболее заполненные arena раньше почти пустых:

```text
заполняем плотные arena
↓
почти пустые arena не трогаем
↓
они получают шанс полностью освободиться
↓
arena можно вернуть системе
```
