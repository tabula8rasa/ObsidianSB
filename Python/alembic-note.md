# Alembic — заметка для полного понимания

## 1. Что это вообще такое, одним предложением

**Alembic** — это инструмент **миграции схемы базы данных** для SQLAlchemy: он отслеживает изменения структуры БД (новая таблица, новая колонка, изменённый тип поля) как последовательность версионированных, применяемых по порядку шагов — примерно как Git отслеживает изменения кода, только для структуры БД.

Написан тем же автором, что и SQLAlchemy, и создан специально в паре с ним, хотя технически может использоваться и без ORM SQLAlchemy — просто с "сырым" SQL.

## 2. Зачем это нужно — проблема, которую он решает

### Без миграций

Представь: у тебя есть таблица `users` с колонками `id`, `email`, `password`. Приложение уже работает в проде, там реальные данные. Тебе нужно добавить колонку `phone_number`.

Варианты без специального инструмента:

- **Пересоздать БД с нуля** — не вариант, там живые данные.
- **Зайти руками через psql/DBeaver и выполнить `ALTER TABLE`** — сработает один раз, на одной БД. Но у тебя есть ещё стейджинг, тестовая среда, у каждого разработчика — своя локальная копия. Нужно повторить это действие везде, вручную, ничего не перепутав в порядке и синтаксисе.
- **Один разработчик добавил колонку локально, второй — свою, независимо** — как теперь понять, у кого какая версия схемы БД на самом деле? Схема БД нигде не зафиксирована как текст, её нельзя посмотреть в `git log` и понять, что именно и когда изменилось.

Это ровно та же проблема, что решает система контроля версий для кода — только для *структуры данных*, а не для файлов с исходным кодом. Код лежит в Git и историю изменений видно всегда; **схема БД без миграций — нет**.

### С Alembic

Каждое изменение схемы оформляется как отдельный файл — **миграция** — с явным "применить" (upgrade) и "откатить" (downgrade) шагом. Эти файлы кладутся в тот же Git-репозиторий, что и код приложения. Схема БД становится настолько же версионируемой, воспроизводимой и отслеживаемой, как и сам код.

## 3. Основные сущности

### 3.1 Миграция (Migration / Revision)

Один файл — один шаг изменения схемы. Каждая миграция имеет:

- **уникальный идентификатор ревизии** (`revision`) — случайный хэш вроде `ae1027a6acf`;
- ссылку на **предыдущую ревизию** (`down_revision`) — так миграции образуют **связный список** (цепочку), а не просто набор файлов без порядка;
- функцию **`upgrade()`** — что сделать, чтобы перейти к этой версии схемы (например, `ALTER TABLE users ADD COLUMN phone_number VARCHAR`);
- функцию **`downgrade()`** — как откатить это изменение назад (например, `ALTER TABLE users DROP COLUMN phone_number`).

Важная идея: миграции образуют **направленный граф версий** — как коммиты в Git. Есть "голова" (head) — последняя, самая свежая миграция, и вся цепочка от первой миграции до head'а полностью описывает, как получить текущую схему БД из пустой базы, шаг за шагом.

### 3.2 Alembic version table (`alembic_version`)

Alembic создаёт в самой базе данных служебную таблицу `alembic_version` **с одной строкой** — она хранит идентификатор той ревизии, до которой эта конкретная БД сейчас "докачена".

Это ключевой механизм: когда ты запускаешь команду "применить миграции", Alembic смотрит в эту таблицу, видит текущую версию, сравнивает с head'ом в файлах миграций и понимает, **какие именно** `upgrade()`-функции нужно выполнить (те, что идут после текущей версии по цепочке) — а не выполняет вообще все миграции заново.

### 3.3 `env.py` — конфигурация окружения

Файл, который Alembic генерирует один раз при инициализации проекта (`alembic init`). Он связывает Alembic с реальным подключением к БД и с моделями SQLAlchemy — говорит:

- как подключиться к базе (обычно читает строку подключения из настроек приложения, той же самой, что использует `create_engine`/`create_async_engine`);
- откуда брать **целевые метаданные** (`target_metadata`) — это объект `Base.metadata` из SQLAlchemy, то есть "как должна выглядеть схема согласно моделям в коде". Именно сюда смотрит автогенерация (см. ниже), чтобы понять, что изменилось.

### 3.4 Автогенерация (`alembic revision --autogenerate`)

Самая ценная возможность Alembic. Она сравнивает:

1. **Текущее состояние моделей SQLAlchemy** в коде приложения (класс `User(Base)` с полями)
2. с **фактической структурой БД** (через отражение — Alembic буквально подключается и смотрит, какие таблицы/колонки там реально есть)

...и на основе разницы **сама пишет черновик миграции**: если в модели появилось новое поле, а в БД его нет — автогенерация создаст `op.add_column(...)`. Разработчику не нужно вручную писать SQL для каждого изменения — только проверить сгенерированный файл (автогенерация не идеальна: не видит переименования колонки, путает его с "удалить одну + добавить другую", не всегда понимает сложные изменения типов).

### 3.5 Alembic CLI — команда `alembic`

Утилита командной строки, через которую разработчик взаимодействует со всем вышеописанным:

| Команда (смысл, не точный синтаксис) | Что делает |
|---|---|
| `alembic init` | разово создать структуру папки миграций в проекте |
| `alembic revision --autogenerate -m "..."` | сгенерировать новый файл миграции на основе разницы моделей и БД |
| `alembic upgrade head` | применить все ещё не применённые миграции, довести БД до последней версии |
| `alembic downgrade -1` | откатить последнюю применённую миграцию на шаг назад |
| `alembic current` | показать, на какой ревизии сейчас находится подключённая БД |
| `alembic history` | показать всю цепочку миграций от начала до head'а |

## 4. Область ответственности — что Alembic делает, а что нет

**Делает:**

- Версионирует **структуру** БД (DDL: `CREATE TABLE`, `ALTER TABLE`, индексы, constraints).
- Гарантирует **воспроизводимый порядок** применения изменений на любой копии БД (локальная машина разработчика, стейджинг, прод).
- Даёт возможность **откатить** изменение структуры, если что-то пошло не так.
- Автогенерирует черновики миграций на основе моделей SQLAlchemy.

**НЕ делает** (частое заблуждение):

- Не работает с **данными** сам по себе — если нужно не просто добавить колонку, а ещё и заполнить её значениями для существующих строк (data migration), это тоже пишется внутри той же миграции, но **вручную**, как обычный Python/SQL-код внутри `upgrade()` — Alembic не угадает бизнес-логику заполнения данных.
- Не заменяет саму SQLAlchemy — Alembic ничего не знает про то, как делать запросы к данным в рантайме приложения; это две разные ответственности: SQLAlchemy — работа с данными во время работы приложения, Alembic — эволюция структуры БД во времени.
- Не автоматически запускается при старте приложения (хотя это можно настроить самостоятельно) — по умолчанию это отдельный, осознанный шаг разработчика/деплоя.

## 5. Как это выглядит в реальном backend-проекте

### Пример 1: добавление новой колонки при развитии фичи

Задача: у модели `Order` появилось новое требование — хранить статус отмены с причиной.

```python
# app/models.py — меняем модель SQLAlchemy
class Order(Base):
    __tablename__ = "orders"
    id: Mapped[int] = mapped_column(primary_key=True)
    status: Mapped[str] = mapped_column(default="pending")
    cancellation_reason: Mapped[str | None] = mapped_column(nullable=True)  # новое поле
```

Дальше разработчик просто выполняет `alembic revision --autogenerate -m "add cancellation reason to orders"` — Alembic сам видит, что в модели появилось новое поле, которого нет в БД, и генерирует файл с `op.add_column("orders", sa.Column("cancellation_reason", sa.String(), nullable=True))`. Разработчик проверяет сгенерированный файл, коммитит его в Git вместе с изменением модели — теперь любой, кто подтянет эти изменения, при `alembic upgrade head` получит ровно ту же структуру БД.

### Пример 2: CI/CD и деплой

В типичном пайплайне деплоя backend-приложения (FastAPI + SQLAlchemy + Alembic — ровно тот стек, что мы разбирали в предыдущих заметках) шаг применения миграций обычно **отдельный и обязательный перед стартом самого приложения**:

```
1. Собрать Docker-образ с новым кодом
2. Запустить `alembic upgrade head` против базы прода
3. Только после успешного применения миграций — раскатить новую версию приложения
```

Порядок критичен: если сначала выкатить новый код (который уже ожидает колонку `cancellation_reason`), а миграцию применить позже — приложение начнёт падать с ошибками "колонка не существует" сразу после деплоя. Поэтому Alembic — не просто инструмент разработки, а полноценный шаг деплой-процесса, синхронизирующий состояние БД с ожиданиями кода.

### Пример 3: командная разработка, конфликт миграций

Два разработчика параллельно создают миграции от одной и той же "головной" ревизии (оба стартуют от одного `down_revision`). Когда оба пуш-реквеста мержатся, в истории миграций образуется **развилка** — два файла с одинаковым `down_revision`, но разными `revision`. Alembic обнаружит это как **множественные головы** (multiple heads) при попытке `alembic upgrade head` и потребует явно их слить (`alembic merge heads`), создав merge-миграцию — концептуально это прямой аналог merge-конфликта в Git, только для истории схемы БД, а не кода.

## 6. Итог

| Вопрос | Ответ |
|---|---|
| Что такое Alembic | Инструмент версионирования схемы БД, компаньон SQLAlchemy |
| Аналогия | Git, но для структуры базы данных, а не для файлов кода |
| Из чего состоит | Файлы-миграции с `upgrade()`/`downgrade()`, связанные в цепочку через `revision`/`down_revision`; служебная таблица `alembic_version` в самой БД; конфигурация `env.py` |
| Главная киллер-фича | `--autogenerate` — сравнивает модели SQLAlchemy с реальной БД и сама пишет черновик миграции |
| Что НЕ делает | Не пишет сама бизнес-логику миграции данных, не работает в рантайме приложения, не запускается автоматически без явной настройки |
| Где живёт в реальном проекте | Отдельный шаг в CI/CD, выполняемый перед раскаткой новой версии кода приложения |
