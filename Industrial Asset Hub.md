# 1. Общие положения

## 1.1. Назначение системы

Industrial Asset Hub (IAH) — серверная информационная система для ведения B2B-каталога промышленного оборудования и управления связанными с оборудованием цифровыми ресурсами.

Система обеспечивает централизованное хранение:

- Регистрационных и технических сведений об оборудовании.
    
- Сведений о производителях, поставщиках, ценах и остатках.
    
- Фотографий, видеоматериалов, инструкций, технических паспортов и сертификатов.
    
- Версий документов и истории их изменений.
    
- Сведений об операциях пользователей и действиях с объектами хранилища.
    

Структурированные сведения размещаются в PostgreSQL. Содержимое файлов размещается в RustFS посредством S3 API.

Взаимодействие пользователей с системой осуществляется через HTTP API, описываемый OpenAPI 3.1 и доступный через Swagger UI.

Разработка отдельного frontend-приложения в рамках версии 1.0 не предусматривается.

## 1.2. Цели

**G-01.** Реализовать управление жизненным циклом оборудования и его файлов.

**G-02.** Обеспечить логическую согласованность данных PostgreSQL и RustFS, включая восстановление после частичных отказов.

**G-03.** Реализовать операции S3 API: buckets, objects, multipart, presigned URLs, versions, tags, metadata, lifecycle, policies, notifications, object lock и encryption.

**G-04.** Реализовать разграничение прав доступа на уровне организаций, пользователей, товаров и документов.

**G-05.** Обеспечить воспроизводимое развёртывание через Docker Compose.

**G-06.** Реализовать автоматические функциональные, интеграционные, конкурентные и отказоустойчивые тесты.

## 1.3. За пределами версии 1.0

- Онлайн-оплата и эквайринг.
    
- Корзина, оформление и доставка заказов.
    
- Полноценная CRM.
    
- Отдельное frontend-приложение.
    
- Редактирование PDF и изображений в браузере.
    
- Собственная реализация протокола S3.
    
- Самостоятельная реализация распределённого алгоритма RustFS.
    
- Гарантированная отказоустойчивость при размещении RustFS на единственном диске.

# 2. Архитектура системы

## 2.1. Компоненты

|Компонент|Технология|Ответственность|
|---|---|---|
|API Server|FastAPI|HTTP API, авторизация, проверка данных, координация операций|
|Application Layer|Python|Сценарии использования и бизнес-правила|
|Domain Layer|Python|Сущности, инварианты, доменные события|
|Persistence|SQLAlchemy 2 Async|Доступ к PostgreSQL|
|Database|PostgreSQL|Бизнес-данные, связи, транзакции, задания|
|Object Storage|RustFS|Хранение бинарных данных и выполнение S3 API|
|Storage Adapter|boto3|Взаимодействие с S3|
|Background Worker|Python|Проверка загрузок, публикация, очистка, повторные операции|
|Migration Service|Alembic|Изменение структуры БД|
|Storage Bootstrap|Python / boto3|Создание бакетов и настройка политик|
|Antivirus|ClamAV|Проверка загружаемых файлов|
|Reverse Proxy|Caddy / Nginx|TLS и маршрутизация внешнего трафика|

## 2.2. Принципы

- **Модульный монолит.** Один кодовый проект с изолированными бизнес-модулями.
    
- **PostgreSQL — источник истины о бизнес-состоянии.** Активная версия документа определяется БД.
    
- **RustFS — источник истины о физическом существовании объекта.** Данные БД не подтверждают существование файла без проверки S3.
    
- **Разделение ответственности.** Domain не импортирует SQLAlchemy, FastAPI или boto3.
    
- **Идемпотентность.** Повтор запроса с тем же ключом идемпотентности не создаёт повторную бизнес-операцию.
    
- **Восстановимость.** Незавершённые межсистемные операции сохраняют состояние, необходимое для повторного выполнения.
    
- **Минимальные привилегии.** Пользователи приложения не получают административные ключи RustFS.
    
- **Наблюдаемость.** Значимые операции сопровождаются логированием, метриками и идентификаторами трассировки.
    

## 2.3. Взаимодействие компонентов

1. Клиент отправляет HTTP-запрос в FastAPI.
    
2. API проверяет аутентификацию, права пользователя и корректность параметров.
    
3. Application Service выполняет бизнес-операцию.
    
4. Repository обращается к PostgreSQL через Unit of Work.
    
5. Storage Adapter обращается к RustFS посредством boto3.
    
6. Длительные и потенциально повторяемые операции передаются Background Worker.
    
7. RustFS отправляет события в webhook-приёмник.
    
8. Worker обрабатывает события и восстанавливает незавершённые операции.
    

HTTP-запросы должны завершаться без ожидания длительного сканирования, массовой очистки и восстановления хранилища.

# 3. Пользователи, организации и права

## 3.1. Организация

Организация — независимый владелец каталога и связанных ресурсов.

Система поддерживает несколько организаций в одной базе данных.

Каждый товар, поставщик, файл, загрузка и журнал бизнес-операций привязан к организации.

## 3.2. Роли

|Роль|Полномочия|
|---|---|
|PLATFORM_ADMIN|Управление платформой, инфраструктурные операции|
|ORG_ADMIN|Пользователи, поставщики, товары и документы своей организации|
|CATALOG_MANAGER|Создание, изменение и публикация товаров|
|CONTENT_MANAGER|Загрузка файлов, изменение метаданных, замена версий|
|REVIEWER|Проверка и утверждение документов|
|VIEWER|Чтение доступного каталога и разрешённых документов|

Права проверяются по действиям и ресурсам, а не только по названиям ролей.

## 3.3. Матрица доступа

|Операция|Org Admin|Catalog Manager|Content Manager|Reviewer|Viewer|
|---|---|---|---|---|---|
|Создать товар|Да|Да|Нет|Нет|Нет|
|Изменить цену|Да|Да|Нет|Нет|Нет|
|Загрузить фото|Да|Да|Да|Нет|Нет|
|Заменить документ|Да|Да|Да|Нет|Нет|
|Утвердить документ|Да|Нет|Нет|Да|Нет|
|Скачать разрешённый файл|Да|Да|Да|Да|Да|
|Удалить товар логически|Да|Да|Нет|Нет|Нет|
|Управлять участниками|Да|Нет|Нет|Нет|Нет|

Дополнительные правила:

- Пользователь не может утверждать собственную загрузку защищённого документа.
    
- Доступ к данным другой организации запрещён.
    
- Глобальный администратор работает через отдельные административные маршруты.
    
- При отзыве доступа новые ссылки на скачивание не выдаются.
    
- Уже выданная presigned URL действует до своего срока истечения; отзыв прав в PostgreSQL сам по себе её не аннулирует.

# 4. Доменная модель

## 4.1. Агрегаты

Выделяются следующие агрегаты:

1. **Organization** — организация и её участники.
    
2. **Product** — товар и его характеристики.
    
3. **Asset** — логический файл и его версии.
    
4. **UploadSession** — управляемая процедура загрузки.
    
5. **DocumentReview** — процесс проверки документа.
    
6. **StorageOperation** — выполнение межсистемной операции.
    
7. **AuditEvent** — запись об изменениях и действиях пользователя.
    

Агрегаты определяют границы выполнения бизнес-инвариантов.

# 5. Сущности и атрибуты

## 5.1. Organization

**Назначение:** организация, владеющая каталогом.

|Атрибут|Тип|Ограничение|
|---|---|---|
|id|UUID|PK|
|name|VARCHAR(255)|NOT NULL|
|slug|VARCHAR(80)|UNIQUE|
|status|ENUM|ACTIVE, SUSPENDED|
|created_at|TIMESTAMPTZ|NOT NULL|
|updated_at|TIMESTAMPTZ|NOT NULL|

Правила:

- `slug` неизменяем после создания.
    
- Организация SUSPENDED не создаёт товары и файлы.
    
- Чтение существующих данных зависит от административной политики блокировки.
    
- Физическое удаление организации через публичный API запрещено.
    

## 5.2. User

**Назначение:** учётная запись пользователя.

|Атрибут|Тип|
|---|---|
|id|UUID, PK|
|email|VARCHAR(320), UNIQUE|
|password_hash|TEXT|
|status|ENUM(ACTIVE, BLOCKED)|
|token_version|INTEGER|
|created_at|TIMESTAMPTZ|
|last_login_at|TIMESTAMPTZ, NULL|

Инварианты:

- Электронная почта уникальна без учёта регистра.
    
- Пароль хранится исключительно в виде стойкого хеша Argon2id.
    
- Блокировка пользователя запрещает выдачу новых токенов доступа.
    
- Изменение `token_version` инвалидирует ранее выданные токены при проверке их версии.
    

## 5.3. Membership

**Назначение:** принадлежность пользователя организации.

Поля: `id`, `organization_id`, `user_id`, `role`, `status`, `joined_at`.

Ограничения:

- UNIQUE(organization_id, user_id).
    
- Одна запись определяет активную роль пользователя в организации.
    
- Удаление последнего активного ORG_ADMIN запрещено.
    

## 5.4. Supplier

**Назначение:** поставщик оборудования.

Поля:

- id — UUID.
    
- organization_id — FK.
    
- name — наименование.
    
- inn — ИНН, nullable.
    
- contact_email — контакт.
    
- phone — телефон.
    
- status — ACTIVE / INACTIVE.
    
- created_at, updated_at.
    

Поставщик принадлежит одной организации.

Товар не может ссылаться на поставщика другой организации.

Удаление поставщика при наличии связанных товаров запрещено. Допускается перевод в INACTIVE.

## 5.5. Category

**Назначение:** классификация оборудования.

Поля: `id`, `parent_id`, `name`, `slug`, `attribute_schema`, `created_at`.

`attribute_schema` — JSON Schema, определяющая допустимые технические характеристики товара.

Пример категории «Гидромолоты»:

- `operating_weight_kg`: number, значение больше 0.
    
- `oil_flow_lpm`: number, значение больше 0.
    
- `operating_pressure_bar`: number, значение больше 0.
    
- `tool_diameter_mm`: number, значение больше 0.
    

Изменение JSON Schema не должно автоматически делать существующие карточки невалидными. Для этого хранится версия схемы характеристик.

## 5.6. Product

**Назначение:** единица каталога оборудования.

|Атрибут|Тип|Правило|
|---|---|---|
|id|UUID|PK|
|organization_id|UUID|FK|
|supplier_id|UUID|FK|
|category_id|UUID|FK|
|sku|VARCHAR(100)|Уникален в организации|
|title|VARCHAR(255)|Обязателен|
|description|TEXT|Необязателен|
|manufacturer|VARCHAR(120)|Обязателен для публикации|
|model|VARCHAR(120)|Необязателен|
|price|NUMERIC(14,2)|Значение неотрицательно|
|currency|CHAR(3)|ISO 4217|
|stock_quantity|INTEGER|Значение неотрицательно|
|specifications|JSONB|Проверяется схемой категории|
|status|ENUM|DRAFT, ACTIVE, SUSPENDED, ARCHIVED|
|revision|INTEGER|Optimistic Lock|
|created_by|UUID|FK|
|created_at|TIMESTAMPTZ|Обязателен|
|updated_at|TIMESTAMPTZ|Обязателен|
|deleted_at|TIMESTAMPTZ|NULL для неудалённого товара|

**Инварианты Product:**

- Цена неотрицательна.
    
- Остаток неотрицателен.
    
- SKU уникален среди товаров одной организации.
    
- Изменение категории требует проверки характеристик по новой схеме.
    
- Публикация товара требует обязательных атрибутов и хотя бы одной утверждённой основной фотографии.
    
- Архивирование не удаляет прикреплённые файлы.
    
- Удаление товара осуществляется логически.
    
- Каждое изменение бизнес-полей увеличивает `revision`.
    

## 5.7. Asset

**Назначение:** логический цифровой ресурс товара.

Один Asset существует независимо от количества версий файла.

|Атрибут|Тип|
|---|---|
|id|UUID, PK|
|organization_id|UUID, FK|
|product_id|UUID, FK|
|kind|ENUM(IMAGE, VIDEO, MANUAL, CERTIFICATE, DRAWING, OFFER, OTHER)|
|title|VARCHAR(255)|
|original_filename|VARCHAR(255)|
|visibility|ENUM(CATALOG, INTERNAL, RESTRICTED)|
|status|ENUM(PENDING, ACTIVE, REJECTED, ARCHIVED, DELETION_PENDING, DELETED)|
|current_version_id|UUID, nullable|
|is_primary|BOOLEAN|
|created_by|UUID|
|created_at|TIMESTAMPTZ|
|updated_at|TIMESTAMPTZ|

Правила:

- Asset принадлежит одному товару.
    
- Asset принадлежит той же организации, что и товар.
    
- У Asset может быть несколько AssetVersion.
    
- У Asset существует не более одной опубликованной текущей версии.
    
- Основной фотографией товара может быть только ACTIVE Asset категории IMAGE.
    
- У одного товара существует не более одной основной фотографии.
    
- RESTRICTED запрещает выдачу ссылки без проверки права доступа.
    

## 5.8. AssetVersion

**Назначение:** конкретная редакция цифрового ресурса.

|Атрибут|Тип|
|---|---|
|id|UUID, PK|
|asset_id|UUID, FK|
|revision_number|INTEGER|
|bucket|VARCHAR(63)|
|object_key|TEXT|
|s3_version_id|TEXT|
|etag|TEXT|
|sha256|CHAR(64)|
|size_bytes|BIGINT|
|content_type|VARCHAR(255)|
|metadata|JSONB|
|status|ENUM(STORED, VALIDATING, READY, REJECTED, RETAINED, PURGED)|
|retention_mode|ENUM(GOVERNANCE, COMPLIANCE), nullable|
|retain_until|TIMESTAMPTZ, nullable|
|created_by|UUID|
|created_at|TIMESTAMPTZ|

Ограничения:

- UNIQUE(asset_id, revision_number).
    
- UNIQUE(bucket, object_key, s3_version_id) для опубликованных версий.
    
- `revision_number` возрастает внутри Asset.
    
- `s3_version_id` сохраняется без преобразований.
    
- `etag` не является подтверждением SHA-256.
    
- Подтверждение целостности основывается на рассчитанной контрольной сумме.
    

**Критически важно:** AssetVersion хранит идентификатор конкретной S3-версии. Запросы чтения опубликованного документа выполняются с `VersionId`, а не по текущей версии ключа в RustFS.

## 5.9. UploadSession

**Назначение:** управляемая операция загрузки файла.

Поля:

- id.
    
- organization_id.
    
- asset_id.
    
- actor_id.
    
- upload_mode: SIMPLE / MULTIPART.
    
- expected_size_bytes.
    
- expected_content_type.
    
- staging_bucket.
    
- staging_key.
    
- s3_upload_id — nullable.
    
- status.
    
- idempotency_key.
    
- expires_at.
    
- created_at.
    
- completed_at.
    

Сессия существует до завершения, отмены или истечения срока действия.

## 5.10. UploadPart

**Назначение:** учёт части multipart-загрузки.

Поля: `session_id`, `part_number`, `etag`, `size_bytes`, `uploaded_at`.

Ограничение: UNIQUE(session_id, part_number).

Повторная загрузка части с тем же номером заменяет сохранённый результат этой части после получения подтверждения от S3.

## 5.11. DocumentReview

**Назначение:** согласование технических и юридически значимых документов.

Поля:

- id.
    
- asset_version_id.
    
- submitted_by.
    
- reviewer_id.
    
- status: PENDING / APPROVED / REJECTED.
    
- comment.
    
- created_at.
    
- reviewed_at.
    

Инварианты:

- Собственная загрузка не может быть самостоятельно утверждена.
    
- Только APPROVED-версия защищённого документа может стать опубликованной.
    
- Отказ не удаляет файл немедленно.
    
- Решение фиксируется в AuditEvent.
    
- Изменение утверждённого документа осуществляется созданием новой версии.
    

## 5.12. StorageOperation

**Назначение:** сохранение состояния операции между PostgreSQL и S3.

Поля:

- id.
    
- operation_type.
    
- aggregate_id.
    
- idempotency_key.
    
- status: PENDING / RUNNING / SUCCEEDED / RETRYABLE / FAILED.
    
- attempt_count.
    
- next_attempt_at.
    
- locked_until.
    
- input_data JSONB.
    
- result_data JSONB.
    
- last_error.
    
- created_at.
    
- completed_at.
    

Используется для копирования, публикации, удаления, очистки и восстановления объектов.

## 5.13. StorageEvent

**Назначение:** входящие события RustFS.

Поля:

- id.
    
- event_fingerprint — уникальный идентификатор для дедупликации.
    
- event_name.
    
- bucket.
    
- object_key.
    
- s3_version_id.
    
- payload JSONB.
    
- received_at.
    
- processed_at.
    
- processing_status.
    

Повторное событие не должно приводить к повторному изменению бизнес-состояния.

## 5.14. AuditEvent

**Назначение:** неизменяемая прикладная история действий.

Поля:

- id.
    
- organization_id.
    
- actor_id.
    
- action.
    
- entity_type.
    
- entity_id.
    
- before_state JSONB.
    
- after_state JSONB.
    
- request_id.
    
- created_at.
    

Доступные действия: создание, изменение, утверждение, удаление, выдача ссылки, смена прав, изменение настроек хранения.

Через публичный API изменение и удаление AuditEvent запрещены.

## 5.15. IdempotencyRecord и OutboxEvent

**IdempotencyRecord** хранит организацию, маршрут, ключ, хеш запроса, состояние выполнения и сохранённый HTTP-ответ.

**OutboxEvent** хранит событие, сформированное внутри PostgreSQL-транзакции, и состояние его последующей обработки.

Уникальность IdempotencyRecord задаётся комбинацией `(organization_id, operation_name, idempotency_key)`.

# 6. Жизненный цикл Product

## 6.1. Состояния

- **DRAFT:** карточка создаётся и редактируется, не участвует в опубликованном каталоге.
    
- **ACTIVE:** карточка опубликована.
    
- **SUSPENDED:** карточка временно скрыта из опубликованного каталога, редактирование разрешено.
    
- **ARCHIVED:** карточка выведена из эксплуатации каталога, доступна для аудита, обычное редактирование запрещено.
    

## 6.2. Допустимые переходы

|Исходное|Целевое|Условие|
|---|---|---|
|DRAFT|ACTIVE|Проверка обязательных полей и основной фотографии|
|ACTIVE|SUSPENDED|Решение Catalog Manager|
|SUSPENDED|ACTIVE|Повторная проверка требований публикации|
|DRAFT|ARCHIVED|Разрешение менеджера|
|ACTIVE|ARCHIVED|Разрешение менеджера|
|SUSPENDED|ARCHIVED|Разрешение менеджера|
|ARCHIVED|DRAFT|Операция восстановления|

Прямой переход ARCHIVED → ACTIVE запрещён.

## 6.3. Поведение при удалении

1. Проверяются права.
    
2. Товар помечается `deleted_at`.
    
3. Товар исключается из обычных поисковых результатов.
    
4. Новые загрузки запрещаются.
    
5. Файлы передаются в процесс оценки возможности очистки.
    
6. Объекты под действующим Object Lock не удаляются физически.
    
7. В журнал аудита записывается операция.

# 7. Жизненный цикл Asset и S3 Object

## 7.1. Различие объектов

**Asset** — бизнес-сущность, например «Технический паспорт гидромолота».

**AssetVersion** — редакция бизнес-сущности, например «Редакция 3».

**S3 Object** — объект внутри RustFS.

**S3 Version** — физическая версия объекта, идентифицируемая `bucket + key + version_id`.

Эти четыре понятия не должны объединяться в одну сущность.

## 7.2. Правила идентичности

- Asset ID остаётся постоянным при замене документа.
    
- Каждая утверждаемая редакция получает новый AssetVersion ID.
    
- После публикации каждой редакции в версионируемый бакет формируется новая S3-версия.
    
- Активная редакция указывается через `Asset.current_version_id`.
    
- История не определяется автоматически через «самую новую» S3-версию.
    

## 7.3. Жизненный цикл загрузки

|Состояние|Событие|Следующее состояние|
|---|---|---|
|INITIATED|Начало передачи|UPLOADING|
|UPLOADING|Завершена передача|UPLOADED|
|UPLOADED|Начата проверка|VALIDATING|
|VALIDATING|Проверки пройдены|READY_FOR_PUBLICATION|
|VALIDATING|Проверка провалена|REJECTED|
|READY_FOR_PUBLICATION|Требуется согласование|WAITING_APPROVAL|
|WAITING_APPROVAL|Документ утверждён|PUBLISHING|
|READY_FOR_PUBLICATION|Согласование не требуется|PUBLISHING|
|PUBLISHING|Данные опубликованы|COMPLETED|
|INITIATED / UPLOADING|Отмена|ABORTED|
|Любое незавершённое|Срок истёк|EXPIRED|

`COMPLETED`, `ABORTED`, `REJECTED` и `EXPIRED` являются терминальными состояниями сессии. Для повторной загрузки создаётся новая сессия.

## 7.4. Публикация версии

Публикация состоит из операций:

1. Проверить исходный объект в staging.
    
2. Сверить размер и тип.
    
3. Проверить SHA-256.
    
4. Выполнить антивирусную проверку.
    
5. Проверить согласование документа.
    
6. Скопировать объект в целевой бакет с постоянным ключом Asset.
    
7. Получить S3 VersionId.
    
8. Создать или завершить AssetVersion.
    
9. Переключить указатель `current_version_id` в PostgreSQL.
    
10. Создать AuditEvent.
    
11. Запланировать удаление staging-объекта.
    

Если шаг 7 выполнен, а шаг 9 завершился ошибкой, бизнес-указатель остаётся неизменным. Повторное выполнение восстанавливается через StorageOperation.

## 7.5. Удаление версии

Различаются:

- **Логическое удаление:** версия становится недоступна через обычный API.
    
- **S3 Delete Marker:** маркер удаления для версионируемого ключа.
    
- **Физическое удаление:** `DeleteObject` с конкретным `VersionId`.
    

Логическое удаление не эквивалентно физическому.

Защищённые Object Lock версии не удаляются до окончания разрешённого срока хранения.

# 8. Организация пространства RustFS

## 8.1. Бакеты

|Bucket|Назначение|Versioning|Object Lock|
|---|---|---|---|
|iah-staging|Временные загрузки|Enabled|Disabled|
|iah-catalog|Фотографии и видео|Enabled|Disabled|
|iah-private|Паспорта, чертежи, предложения|Enabled|Disabled|
|iah-compliance|Защищённые документы|Enabled|Enabled|

Все бакеты изначально закрытые.

Публичность карточки товара не означает анонимный доступ к бакету.

## 8.2. Схема ключей

Временная загрузка:

`uploads/{organization_id}/{upload_session_id}/payload`

Постоянное хранение:

`organizations/{organization_id}/products/{product_id}/assets/{asset_id}/content`

Каждая редакция одного Asset публикуется по постоянному ключу. Различие редакций обеспечивается S3 VersionId.

Правила формирования:

- Ключ строится только из доверенных UUID и фиксированных сегментов.
    
- Исходное имя файла не включается в ключ.
    
- `..`, `.`, пустые сегменты и повторные разделители запрещены.
    
- Имена файлов хранятся как метаданные.
    
- Клиент не задаёт bucket или object key напрямую.
    

## 8.3. Метаданные

Системные HTTP-метаданные объекта:

- Content-Type.
    
- Content-Length.
    
- ETag.
    
- Last-Modified.
    
- VersionId.
    

Пользовательские метаданные, задаваемые приложением:

- `organization-id`.
    
- `product-id`.
    
- `asset-id`.
    
- `storage-operation-id`.
    
- `uploaded-by`.
    

S3 Object Tags:

- `asset-kind`.
    
- `lifecycle-state`.
    
- `data-class`.
    

Содержимое метаданных и тегов не должно включать пароли, токены, паспортные данные или другие секреты.

# 10. Сценарии использования

## UC-01. Создание товара

**Актор:** CATALOG_MANAGER.

**Предусловия:**

- Пользователь авторизован.
    
- Организация ACTIVE.
    
- Поставщик и категория существуют в данной области доступа.
    

**Основной сценарий:**

1. Пользователь отправляет POST `/api/v1/products`.
    
2. API валидирует тело запроса.
    
3. Application Service создаёт Product в состоянии DRAFT.
    
4. SQLAlchemy сохраняет запись в транзакции.
    
5. Система возвращает HTTP 201 и идентификатор товара.
    

**Альтернативы:**

- SKU уже существует → 409 Conflict.
    
- Цена отрицательна → 422.
    
- Поставщик принадлежит другой организации → 404.
    
- Пользователь не обладает правами → 403.
    

**Постусловие:** товар существует, файлы отсутствуют, статус DRAFT.

## UC-02. Простая загрузка фотографии

**Актор:** CONTENT_MANAGER.

**Предусловия:**

- Product существует.
    
- Product не ARCHIVED.
    
- Размер файла не превышает ограничение.
    
- У пользователя есть право записи.
    

**Основной сценарий:**

1. Создание Asset и UploadSession.
    
2. Приём файла через `multipart/form-data`.
    
3. Потоковая передача в staging bucket.
    
4. Проверка загруженного объекта.
    
5. Создание задания проверки.
    
6. Проверка типа, размера, контрольной суммы и вредоносного содержимого.
    
7. Публикация новой S3-версии.
    
8. Сохранение AssetVersion.
    
9. Перевод Asset в ACTIVE.
    
10. Возврат результата клиенту через API статуса загрузки.
    

**Альтернативы:**

- Ошибка сети → StorageOperation RETRYABLE.
    
- Несовпадение SHA-256 → REJECTED.
    
- Превышен размер → REJECTED.
    
- Недоступен RustFS → 503 при синхронной операции либо повтор фонового задания.
    

## UC-03. Загрузка посредством Presigned URL

**Актор:** CONTENT_MANAGER.

**Основной сценарий:**

1. Клиент вызывает POST `/api/v1/uploads`.
    
2. Backend создаёт UploadSession.
    
3. Backend выдаёт presigned PUT URL для уникального staging key.
    
4. Клиент отправляет PUT непосредственно в RustFS.
    
5. Клиент вызывает POST `/api/v1/uploads/{id}/complete`.
    
6. Worker выполняет HEAD и проверку содержимого.
    
7. После успешных проверок объект публикуется.
    

**Инварианты:**

- Выданная ссылка позволяет записать только определённый staging key.
    
- Ссылка имеет ограниченный срок действия.
    
- Ссылка не предоставляет полномочий на чтение других объектов.
    
- Завершение бизнес-загрузки без фактического S3-объекта запрещено.
    
- Сервер повторно проверяет размер содержимого, даже если размер заявлялся клиентом.
    

## UC-04. Multipart Upload

**Актор:** CONTENT_MANAGER.

**Основной сценарий:**

1. Создать UploadSession типа MULTIPART.
    
2. Вызвать CreateMultipartUpload.
    
3. Сохранить `s3_upload_id`.
    
4. Создать presigned URL для каждой части.
    
5. Загрузить части.
    
6. Сохранить ETag каждой успешно загруженной части.
    
7. Передать список частей в CompleteMultipartUpload.
    
8. Подтвердить существование итогового объекта.
    
9. Запустить валидацию и публикацию.
    

Правила:

- Части собираются в порядке номеров.
    
- Непоследняя часть не меньше 5 MiB.
    
- Повторное завершение одной сессии идемпотентно на уровне приложения.
    
- Отмена вызывает AbortMultipartUpload.
    
- Неудачная отмена фиксируется для повторной обработки.
    

## UC-05. Замена документа

1. Пользователь создаёт новую UploadSession для существующего Asset.
    
2. Загружает новую редакцию.
    
3. Система выполняет проверку.
    
4. Для защищённого документа создаётся DocumentReview.
    
5. Reviewer утверждает редакцию.
    
6. Система публикует новую S3-версию по постоянному ключу.
    
7. В PostgreSQL появляется новая AssetVersion.
    
8. `Asset.current_version_id` указывает на новую редакцию.
    
9. Предыдущая редакция остаётся доступной через историю при наличии прав и соблюдении retention policy.
    

## UC-06. Восстановление старой редакции

1. Пользователь получает историю AssetVersion.
    
2. Выбирает существующую редакцию.
    
3. Проверяются права.
    
4. Система создаёт StorageOperation RESTORE.
    
5. Избранная редакция копируется в новую S3-версию.
    
6. Создаётся новая AssetVersion с новым `revision_number`.
    
7. Новая версия становится текущей после проверки и согласования, если оно требуется.
    

Восстановление не изменяет содержимое старой редакции.

## UC-07. Логическое удаление и архивирование

1. Пользователь отправляет запрос удаления.
    
2. Система проверяет ссылки на объект.
    
3. Проверяет retention и Legal Hold.
    
4. Помечает Asset как DELETION_PENDING.
    
5. Исключает его из обычной выдачи.
    
6. Формирует StorageOperation для физической очистки, когда она разрешена.
    
7. После подтверждения отсутствия подлежащих удалению S3-версий изменяет статус на DELETED.
    

Система не сообщает о физическом удалении до фактического подтверждения.

## UC-08. Просмотр и скачивание

1. Клиент запрашивает Product.
    
2. Backend читает Product и Asset из PostgreSQL.
    
3. Для каждого Asset возвращает метаданные, состояние и идентификатор активной версии.
    
4. При отдельном запросе скачивания проверяет права.
    
5. Формирует presigned GET с конкретным S3 VersionId.
    
6. Клиент скачивает объект из RustFS.
    

Для Range GET клиент передаёт HTTP-заголовок Range в запросе к S3. Набор допустимых заголовков определяется контрактом подписанной ссылки.

# 12. Бизнес-правила

## BR-01. Изоляция организаций

Каждый запрос с организационно зависимой сущностью проверяет membership и organization_id.

ID объекта другой организации не даёт доступ к нему.

## BR-02. Публикация товара

Товар ACTIVE должен содержать:

- SKU.
    
- Название.
    
- Производителя.
    
- Категорию.
    
- Корректную цену.
    
- Основное изображение в состоянии ACTIVE.
    

## BR-03. Типы файлов

Начальная политика:

|Тип|Форматы|Максимальный размер|
|---|---|---|
|IMAGE|JPEG, PNG, WebP|25 MiB|
|MANUAL|PDF|100 MiB|
|CERTIFICATE|PDF|100 MiB|
|DRAWING|PDF|100 MiB|
|VIDEO|MP4, WebM|5 GiB|
|OFFER|PDF|100 MiB|

Размеры являются выбранными ограничениями приложения, а не ограничениями RustFS.

Файл проверяется по содержимому, а не только по расширению.

## BR-04. Версии

- Новая версия не удаляет предыдущую.
    
- Текущая версия определяется PostgreSQL.
    
- История версий неизменяема на уровне публичного API.
    
- Утверждённая версия не редактируется напрямую.
    

## BR-05. Сроки

Начальная конфигурация приложения:

- Presigned GET: 5 минут.
    
- Presigned PUT: 15 минут.
    
- Multipart session: 24 часа.
    
- Очистка временных объектов: после 24 часов при отсутствии активной сессии.
    
- Хранение защищённых документов: 365 дней с момента фиксации retention, если политика организации не требует более длительного срока.
    

## BR-06. Повторные запросы

Запросы создания и изменения, имеющие внешние побочные эффекты, принимают `Idempotency-Key`.

Повтор с тем же ключом и тем же содержимым возвращает сохранённый результат.

Повтор с тем же ключом и другим содержимым возвращает 409.

## BR-07. Конкурентное изменение

Обновление Product выполняется с использованием optimistic locking.

Если клиент отправляет устаревшую revision, обновление отклоняется.

## BR-08. Квоты

Для организации хранятся:

- Максимальное количество товаров.
    
- Максимальное количество файлов.
    
- Максимальный суммарный размер файлов.
    
- Максимальное количество активных загрузок.
    

Перед созданием UploadSession проверяется квота. Резерв объёма учитывается отдельно от фактического использования. Неиспользованный резерв освобождается после завершения или отмены сессии.

# 13. Транзакции и согласованность

## 13.1. Граница транзакции

PostgreSQL и RustFS не участвуют в общей ACID-транзакции.

**Запрещено** считать успешный COMMIT PostgreSQL подтверждением сохранения S3-объекта.

Unit of Work охватывает только операции PostgreSQL.

Длительные сетевые вызовы S3 выполняются вне открытой SQL-транзакции.

## 13.2. Паттерн StorageOperation

Каждая межсистемная операция сохраняет своё состояние.

Алгоритм публикации:

1. Создать StorageOperation и необходимые записи БД.
    
2. Зафиксировать PostgreSQL.
    
3. Worker получает задачу через `FOR UPDATE SKIP LOCKED`.
    
4. Устанавливает lease на выполнение.
    
5. Выполняет S3-операцию.
    
6. Сохраняет S3 VersionId и результат.
    
7. Обновляет бизнес-состояние в отдельной транзакции.
    
8. Помечает StorageOperation как SUCCEEDED.
    

В случае ошибки операция переходит в RETRYABLE или FAILED.

## 13.3. Восстановление после неопределённого результата CopyObject

Если RustFS выполнил CopyObject, но приложение потеряло соединение до получения ответа:

- Worker не считает операцию однозначно неуспешной.
    
- Он получает версии целевого ключа.
    
- Проверяет метаданные `storage-operation-id` и контрольную сумму.
    
- При обнаружении соответствующей версии восстанавливает её VersionId.
    
- Завершает PostgreSQL-транзакцию.
    
- Если соответствующая версия не найдена, операция повторяется.
    

Повторное копирование не должно переключать текущую бизнес-версию без успешной транзакции приложения.

Дополнительные S3-версии, появившиеся вследствие сбоев, передаются на контролируемую очистку.

## 13.4. Outbox

Событие домена и изменение агрегата записываются одной PostgreSQL-транзакцией.

Worker забирает OutboxEvent и выполняет требуемую обработку.

Повторная обработка допустима. Обработчики обязаны быть идемпотентными.

## 13.5. Reconciliation

Фоновая процедура проверяет:

- Записи AssetVersion без соответствующего S3-объекта.
    
- Опубликованные S3-версии без подтверждённой записи БД.
    
- Истёкшие UploadSession.
    
- Незавершённые multipart-загрузки.
    
- StorageOperation с истёкшим lease.
    
- Ошибки очистки staging.
    
- Несоответствие фактических размеров и контрольных сумм.
    

Проверка выполняется инкрементально, с пагинацией и ограничением нагрузки.

При отсутствии физического файла опубликованный Asset не должен продолжать выдавать рабочую ссылку.

# 15. Безопасность

## 15.1. Аутентификация

- Access Token — JWT.
    
- Refresh Token — ротационный, с серверным учётом.
    
- Пароли — Argon2id.
    
- Проверка issuer, audience, expiry и подписи JWT.
    
- Запрещено принимать `alg=none`.
    
- Секреты не сохраняются в Git.
    

## 15.2. Авторизация

Авторизация выполняется на уровне Application Service.

Проверяются:

- Существование пользователя.
    
- Статус пользователя.
    
- Membership.
    
- Активная организация.
    
- Право на операцию.
    
- Принадлежность ресурса организации.
    
- Статус ресурса.
    

## 15.3. RustFS IAM

Приложение использует отдельный service account с минимальными правами.

Root credentials применяются только для bootstrap и административного восстановления.

Права на чтение, запись и удаление ограничиваются необходимыми бакетами и префиксами.

S3 ACL не используется как механизм авторизации приложения.

## 15.4. Presigned URLs

- Генерируются только после проверки прав.
    
- Включают конкретный bucket, key и, для чтения версии, VersionId.
    
- Срок действия ограничен.
    
- Не журналируются полностью.
    
- Секретные параметры URL не сохраняются в AuditEvent.
    
- При компрометации ссылки доступ ограничен её сроком действия и объёмом подписанной операции.
    

## 15.5. Object Lock

Для защищённых документов используются механизмы:

- Retention Mode GOVERNANCE.
    
- Retention Mode COMPLIANCE.
    
- Legal Hold.
    

Политики устанавливаются администратором хранения.

COMPLIANCE применяется только к документам, для которых требуется неизменяемое хранение.

Для локальных тестов используются отдельные объекты и контролируемая retention policy.

## 15.6. Шифрование

- Внешний доступ — HTTPS.
    
- Соединение API ↔ PostgreSQL в производственной среде — TLS.
    
- Внешний S3 API — HTTPS.
    
- Секреты размещаются в защищённой конфигурации.
    
- Для защищённых документов предусматривается SSE-KMS через поддерживаемый RustFS KMS backend.
    
- Производственная конфигурация KMS использует внешнюю систему управления ключами.
    

## 15.7. Защита загрузок

- Ограничение размера файла.
    
- Проверка сигнатуры содержимого.
    
- Антивирусное сканирование.
    
- Запрет публикации до окончания проверки.
    
- Исключение небезопасных object keys.
    
- Ограничение числа активных multipart-сессий.
    
- Rate limiting.
    
- Проверка прав при завершении загрузки.

# 16. Фоновая обработка

Фоновые обработчики запускаются отдельным процессом Worker.

## 16.1. Типы заданий

|Задание|Действие|
|---|---|
|VALIDATE_UPLOAD|Проверка файла|
|PUBLISH_ASSET|Копирование и публикация|
|CLEAN_STAGING|Очистка временного хранилища|
|ABORT_MULTIPART|Отмена незавершённой загрузки|
|RECONCILE_STORAGE|Проверка согласованности|
|PURGE_ASSET_VERSION|Физическое удаление разрешённой версии|
|PROCESS_STORAGE_EVENT|Обработка уведомления RustFS|

## 16.2. Повторы

Политика для сетевых ошибок:

- До 5 автоматических попыток в рамках одной серии.
    
- Экспоненциальная задержка.
    
- Случайный jitter.
    
- После исчерпания попыток — FAILED.
    
- Администратор может запросить повторное выполнение.
    

Логические ошибки и нарушения инвариантов автоматически не повторяются.

## 16.3. Защита от параллельной обработки

- Выборка заданий с `FOR UPDATE SKIP LOCKED`.
    
- Lease с `locked_until`.
    
- Проверка идентификатора владельца lease.
    
- Идемпотентный обработчик.
    
- Уникальные ограничения БД на результаты значимых операций.

|ADR-009|Все бакеты закрыты по умолчанию|Контроль доступа через Application Service|

# 23. Основные технические риски

|Риск|Механизм предотвращения|
|---|---|
|Несовместимость отдельного S3 API|Контрактные тесты и закреплённая версия RustFS|

|Нарушение доступности при росте нагрузки|Измерение, индексы, пул соединений, фоновые задачи|

# 24. Ожидаемый результат реализации

После завершения проекта разработчик должен иметь:

1. Полнофункциональное FastAPI-приложение с автоматически сформированным Swagger UI.
    
2. PostgreSQL с согласованной структурой бизнес-сущностей.
    
3. RustFS с четырьмя настроенными бакетами и проверенными S3-функциями.
    
4. Набор начальных товаров, поставщиков, пользователей и файлов.
    
5. Реализованное версионирование документов с сохранением S3 VersionId.
    
6. Рабочие сценарии прямой загрузки, multipart-upload и временных ссылок.
    
7. Разграничение прав доступа и защищённое хранение документов.
    
8. Отказоустойчивую прикладную обработку с повторными операциями и reconciliation.
    
9. Полный набор автоматических тестов.
    
10. Воспроизводимое локальное окружение Docker Compose.
    

**Главный критерий качества:** система должна правильно сохранять, читать, изменять и удалять логические ресурсы, даже когда операции PostgreSQL и RustFS выполняются независимо и любая из зависимостей может отказать в произвольный момент.
