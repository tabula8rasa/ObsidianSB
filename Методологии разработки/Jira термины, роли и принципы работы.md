## 1. Что такое Jira

**Jira** — система для управления задачами, процессами и разработкой продуктов.

В Jira команда может:

- создавать и описывать задачи;
    
- назначать ответственных;
    
- устанавливать приоритеты;
    
- отслеживать текущее состояние работы;
    
- планировать спринты;
    
- вести бэклог;
    
- связывать зависимые задачи;
    
- учитывать версии и релизы;
    
- строить отчёты;
    
- автоматизировать повторяющиеся действия.
    

Jira не является отдельной методологией. Она может использоваться с:

- Scrum;
    
- Kanban;
    
- Scrumban;
    
- Waterfall;
    
- собственным процессом компании.
    

То есть Scrum определяет правила организации работы, а Jira предоставляет инструменты для отображения и контроля этого процесса.

---

# 2. Важное замечание о терминологии

В Jira традиционно использовались термины:

- **Project** — проект;
    
- **Issue** — задача или объект работы;
    
- **Issue Type** — тип задачи.
    

Atlassian постепенно обновляет терминологию Jira Cloud:

- **Project → Space**;
    
- **Issue → Work item**;
    
- **Issue Type → Work type**.
    

При этом старые термины по-прежнему встречаются в интерфейсе, JQL, документации, интеграциях и повседневной речи команд. Поэтому на работе можно услышать как «создай issue в проекте», так и «создай work item в space». Смысл обычно одинаковый.

В этой заметке преимущественно используется привычное слово **задача**, а рядом указывается английский термин.

---

# 3. Основная структура Jira

Упрощённо Jira можно представить следующим образом:

**Организация → Jira → проект/пространство → задачи → подзадачи**

Например:

**Компания → Jira → Проект интернет-магазина → Задача оплаты → Подзадача создания API**

## Project или Space

**Project/Space** — отдельное рабочее пространство, в котором хранятся связанные задачи, доски, настройки и отчёты.

Проект может соответствовать:

- программному продукту;
    
- отдельной команде;
    
- бизнес-процессу;
    
- внутреннему сервису;
    
- направлению деятельности;
    
- конкретному клиентскому проекту.
    

Например:

- `SHOP` — интернет-магазин;
    
- `BANK` — мобильное банковское приложение;
    
- `DATA` — платформа данных;
    
- `SUPPORT` — техническая поддержка.
    

Jira Cloud позволяет использовать пространство для управления продуктом, проектом, командой или сервисом.

---

# 4. Что такое Issue или Work item

**Issue**, или **work item**, — основной объект работы в Jira.

Несмотря на буквальный перевод слова issue как «проблема», в Jira оно может обозначать практически любую единицу работы:

- новую функцию;
    
- ошибку;
    
- пользовательскую историю;
    
- техническую задачу;
    
- исследование;
    
- запрос;
    
- улучшение;
    
- подзадачу.
    

В Jira один work item может представлять Story, Bug, Task или другой настроенный в компании тип работы.

Каждая задача получает уникальный ключ.

Например:

```text
SHOP-125
DATA-842
BANK-301
```

Где:

- `SHOP` — ключ проекта;
    
- `125` — порядковый номер задачи.
    

Ключ задачи часто используется:

- в названии Git-ветки;
    
- в сообщении коммита;
    
- в Pull Request;
    
- в переписке;
    
- в документации;
    
- при поиске задачи.
    

Например:

```text
feature/DATA-842-add-user-mart
```

---

# 5. Иерархия задач в Jira

Стандартную иерархию можно представить так:

```text
Epic
└── Story / Task / Bug
    └── Subtask
```

По умолчанию Jira использует три уровня:

1. более крупная работа — обычно **Epic**;
    
2. стандартные задачи — Story, Task, Bug;
    
3. более мелкая работа — **Subtask**.
    

В крупных организациях над Epic могут находиться дополнительные уровни:

```text
Initiative
└── Capability
    └── Epic
        └── Story / Task / Bug
            └── Subtask
```

Дополнительные уровни иерархии зависят от тарифа и настройки Jira. Расширенная настройка иерархии доступна в Jira Cloud Premium и Enterprise.

---

# 6. Epic — эпик

**Epic** — крупное направление работы, которое нельзя разумно завершить в рамках одной небольшой задачи или одного короткого спринта.

Эпик объединяет несколько связанных Story, Task и Bug.

Пример эпика:

```text
EPIC: Реализовать оплату заказов
```

В него могут входить:

- добавить оплату банковской картой;
    
- создать API для проведения платежа;
    
- интегрироваться с платёжным провайдером;
    
- разработать страницу оплаты;
    
- добавить возврат средств;
    
- настроить журналирование платежей;
    
- добавить мониторинг ошибок;
    
- провести нагрузочное тестирование.
    

Эпик обычно описывает крупную пользовательскую или бизнес-возможность, а не одно техническое действие.

## Хороший эпик

```text
Реализовать систему онлайн-оплаты заказов
```

## Слишком маленький эпик

```text
Добавить кнопку «Оплатить»
```

Это скорее Story или Task.

## Слишком большой эпик

```text
Создать интернет-магазин
```

Такую работу лучше разделить на несколько эпиков:

- каталог;
    
- личный кабинет;
    
- корзина;
    
- оплата;
    
- доставка;
    
- уведомления.
    

В стандартной иерархии Epic находится над Story, Task и Bug, а подзадачи располагаются ниже стандартных типов.

---

# 7. Story — пользовательская история

**Story**, или **User Story**, — требование, сформулированное с точки зрения пользователя и описывающее полезный для него результат.

Классический формат:

```text
Как <роль>,
я хочу <действие>,
чтобы <получить ценность>.
```

Пример:

```text
Как покупатель,
я хочу сохранить банковскую карту,
чтобы не вводить её данные при каждом заказе.
```

Story должна объяснять не только то, **что** нужно создать, но и **зачем** это необходимо пользователю.

## Story обычно содержит

- краткое название;
    
- пользовательскую ценность;
    
- описание;
    
- критерии приёмки;
    
- ограничения;
    
- макеты или ссылки;
    
- оценку;
    
- зависимости;
    
- принадлежность к эпику.
    

## Acceptance Criteria — критерии приёмки

Критерии приёмки описывают условия, при которых Story считается реализованной правильно.

Пример:

```text
1. Пользователь может сохранить карту после успешной оплаты.
2. Полный номер карты не хранится в системе.
3. Пользователь может удалить сохранённую карту.
4. Просроченная карта не может использоваться для оплаты.
5. При ошибке отображается понятное сообщение.
```

Story отвечает на вопрос:

> Какую ценность должен получить пользователь?

---

# 8. Task — задача

**Task** — работа, которую необходимо выполнить, но которую необязательно формулировать как пользовательскую историю.

Примеры:

- настроить мониторинг сервиса;
    
- обновить версию Python;
    
- подготовить миграцию базы данных;
    
- создать техническую документацию;
    
- настроить CI/CD;
    
- исследовать производительность запроса;
    
- создать витрину данных;
    
- настроить резервное копирование.
    

Task часто используется для:

- инфраструктурных работ;
    
- внутренних технических изменений;
    
- аналитики;
    
- документации;
    
- исследования;
    
- организационной работы.
    

## Разница между Story и Task

**Story:**

```text
Как клиент, я хочу скачать банковскую выписку,
чтобы передать её в бухгалтерию.
```

**Task:**

```text
Настроить хранение сформированных PDF-выписок в объектном хранилище.
```

Story описывает пользовательскую ценность, а Task — конкретную работу команды.

---

# 9. Bug — ошибка

**Bug** — дефект, при котором система работает не так, как ожидалось.

Пример:

```text
При оплате заказа двумя картами сумма списывается дважды
```

## Хорошее описание Bug

### Шаги воспроизведения

```text
1. Открыть корзину.
2. Выбрать оплату двумя картами.
3. Указать по 50% суммы для каждой карты.
4. Подтвердить оплату.
```

### Фактический результат

```text
С каждой карты списывается полная стоимость заказа.
```

### Ожидаемый результат

```text
С каждой карты списывается указанная пользователем часть суммы.
```

### Дополнительные данные

- окружение;
    
- версия приложения;
    
- браузер или устройство;
    
- время возникновения;
    
- скриншоты;
    
- логи;
    
- идентификатор запроса;
    
- частота воспроизведения.
    

## Bug и Story

Bug может:

- принадлежать эпику;
    
- быть добавлен в спринт;
    
- иметь приоритет;
    
- иметь исполнителя;
    
- содержать подзадачи;
    
- быть связан с другими задачами.
    

---

# 10. Subtask — подзадача

**Subtask** — небольшая часть Story, Task или Bug.

Подзадача используется, когда одну задачу необходимо разделить между несколькими действиями или специалистами.

Пример:

```text
STORY: Добавить регистрацию пользователя

SUBTASK 1: Разработать форму регистрации
SUBTASK 2: Создать API регистрации
SUBTASK 3: Создать таблицу пользователей
SUBTASK 4: Добавить отправку письма
SUBTASK 5: Написать автоматические тесты
```

Подзадачи позволяют отдельно отслеживать:

- исполнителей;
    
- статусы;
    
- трудозатраты;
    
- технические этапы;
    
- прогресс родительской задачи.
    

Подзадача не должна существовать независимо от родительской задачи. Jira позволяет разбивать стандартные задачи — Story, Task и Bug — на более мелкие подзадачи.

---

# 11. Initiative — инициатива

**Initiative** — крупная бизнес-цель, объединяющая несколько эпиков.

Она чаще используется в больших компаниях и при масштабировании Agile.

Пример:

```text
INITIATIVE: Повысить конверсию интернет-магазина
```

В неё могут входить эпики:

- упростить регистрацию;
    
- улучшить поиск;
    
- внедрить рекомендации;
    
- добавить новые способы оплаты;
    
- сократить количество шагов оформления заказа.
    

Initiative обычно отвечает на вопрос:

> Какую крупную бизнес-цель должна реализовать компания?

Стандартная Jira не обязательно содержит Initiative как отдельный тип: структура зависит от тарифа и конфигурации организации.

---

# 12. Spike — исследование

**Spike** — исследовательская задача, создаваемая, когда команда пока не знает, как реализовать решение или сколько работы оно потребует.

Примеры:

- сравнить Kafka и RabbitMQ;
    
- проверить возможность миграции на новую базу данных;
    
- исследовать причины медленного SQL-запроса;
    
- создать прототип интеграции;
    
- оценить ограничения внешнего API.
    

Результатом Spike обычно является не готовая функция, а:

- документ;
    
- прототип;
    
- набор измерений;
    
- архитектурное решение;
    
- оценка;
    
- список рисков;
    
- рекомендации.
    

Spike не является обязательным стандартным типом Jira. Компания может создать его как отдельный work type либо использовать обычный Task с соответствующей меткой.

---

# 13. Основные поля задачи

## Summary — название

Коротко описывает суть работы.

Хороший пример:

```text
Добавить фильтрацию операций по дате
```

Плохой пример:

```text
Доработать систему
```

Название должно быть понятным без открытия полного описания.

---

## Description — описание

Подробно объясняет:

- контекст;
    
- проблему;
    
- требуемое изменение;
    
- ограничения;
    
- ожидаемый результат;
    
- технические детали;
    
- критерии приёмки.
    

Хорошая задача должна позволять исполнителю понять, что именно требуется сделать.

---

## Assignee — исполнитель

**Assignee** — человек, который в настоящий момент отвечает за выполнение задачи.

В зависимости от настроек задача может быть:

- назначена конкретному сотруднику;
    
- назначена автоматически;
    
- оставлена без исполнителя — Unassigned.
    

Право изменять Assignee регулируется разрешениями Jira.

Важно:

> Assignee — не обязательно тот, кто создал задачу или отвечает за весь продукт. Это текущий исполнитель конкретной работы.

---

## Reporter — автор или инициатор

**Reporter** — человек, который создал задачу или от имени которого она была зарегистрирована.

Например:

- аналитик создал Story;
    
- тестировщик зарегистрировал Bug;
    
- сотрудник поддержки оформил обращение клиента;
    
- Product Owner создал задачу на новую функцию.
    

Reporter и Assignee могут быть разными людьми.

Поле Reporter автоматически заполняется при создании задачи, а возможность изменить его зависит от разрешений.

---

## Priority — приоритет

Показывает относительную важность задачи.

Часто используются уровни:

- Highest;
    
- High;
    
- Medium;
    
- Low;
    
- Lowest.
    

Конкретный набор приоритетов настраивается компанией. Jira позволяет администраторам создавать схемы приоритетов и выбирать, какие уровни доступны в отдельных пространствах.

Приоритет не равен порядку выполнения автоматически. На решение также влияют:

- ценность;
    
- срочность;
    
- риски;
    
- зависимости;
    
- размер задачи;
    
- доступность специалистов;
    
- цель спринта.
    

---

## Status — статус

**Status** показывает текущее состояние задачи.

Пример:

```text
To Do → In Progress → Code Review → Testing → Done
```

Другие возможные статусы:

- Open;
    
- Selected for Development;
    
- Analysis;
    
- Ready for Development;
    
- Blocked;
    
- Reopened;
    
- Ready for Release;
    
- Closed.
    

Набор статусов определяется workflow конкретной компании.

---

## Resolution — итоговое решение

**Resolution** показывает, почему задача была окончательно закрыта.

Примеры:

- Done;
    
- Fixed;
    
- Won’t Do;
    
- Duplicate;
    
- Cannot Reproduce;
    
- Declined;
    
- Obsolete.
    

Status и Resolution — разные понятия.

```text
Status: Done
Resolution: Fixed
```

означает, что работа завершена, потому что ошибка была исправлена.

```text
Status: Done
Resolution: Duplicate
```

означает, что задача закрыта, потому что такая проблема уже зарегистрирована в другой задаче.

---

## Labels — метки

**Labels** — свободные текстовые метки для дополнительной классификации.

Примеры:

```text
backend
security
technical-debt
urgent
migration
customer-request
```

Labels удобны для поиска и фильтрации, но при отсутствии правил могут быстро превратиться в неупорядоченный набор похожих значений:

```text
backend
back-end
BackEnd
be
```

Поэтому в команде желательно согласовать единый стиль меток. Jira позволяет выбирать существующую метку или создавать новую непосредственно в поле Labels.

---

## Components — компоненты

**Component** — логическая часть продукта, подразделение или направление работы.

Примеры:

- Backend;
    
- Frontend;
    
- Mobile;
    
- Payments;
    
- Notifications;
    
- Data Platform;
    
- Authorization.
    

Components помогают группировать задачи вокруг функций продукта, подразделений или рабочих потоков. Для компонента можно определить владельца и автоматическое назначение задач. В Jira Cloud компоненты доступны в company-managed пространствах.

---

## Fix Version — версия исправления

**Fix Version** показывает, в какой версии продукта планируется выпустить функцию или исправление.

Примеры:

```text
2.4.0
2026.07
Q3 Release
Mobile 5.12
```

Когда в пространстве включается функция Releases, в задачах появляется поле Fix versions и отдельный раздел Releases.

---

## Affects Version — затронутая версия

Показывает, в какой версии была обнаружена проблема.

Например:

```text
Affects Version: 2.3.1
Fix Version: 2.3.2
```

То есть ошибка существует в версии 2.3.1 и должна быть исправлена в 2.3.2.

---

## Sprint

Поле показывает, к какому спринту относится задача.

Например:

```text
Sprint 24
Payments Sprint 2026-07
```

Спринты применяются на Scrum-досках и планируются через Backlog. В Kanban-пространствах спринты не используются.

---

## Story Points

**Story Points** — относительная оценка объёма, сложности и неопределённости работы.

Часто используется ряд:

```text
1, 2, 3, 5, 8, 13, 21
```

Story Points не должны напрямую переводиться в часы.

Например:

- 2 Story Points — знакомая и небольшая работа;
    
- 5 Story Points — средняя задача;
    
- 13 Story Points — крупная или неопределённая задача.
    

Story Points показывают относительные усилия по сравнению с другими задачами команды.

---

## Original Estimate

Первоначальная оценка времени:

```text
4h
2d
1w
```

## Remaining Estimate

Оставшееся предполагаемое время.

## Time Spent

Фактически зарегистрированное время.

Не каждая компания использует учёт времени в Jira. Некоторые команды работают только со Story Points.

---

## Due Date

Дата, к которой задачу желательно или необходимо завершить.

Due Date полезен для задач:

- с договорным сроком;
    
- с обязательной датой;
    
- связанных с аудитом;
    
- привязанных к внешнему мероприятию;
    
- имеющих законодательный срок.
    

Не следует назначать искусственный Due Date каждой задаче, иначе поле перестаёт показывать реальную срочность.

---

## Watchers — наблюдатели

**Watcher** — человек, который следит за изменениями задачи и получает уведомления о значимых событиях.

Например:

- изменении статуса;
    
- новом комментарии;
    
- обновлении полей;
    
- назначении исполнителя.
    

Watcher не обязательно выполняет работу или управляет задачей.

---

## Attachments — вложения

К задаче можно прикреплять:

- изображения;
    
- документы;
    
- логи;
    
- схемы;
    
- видеозаписи;
    
- файлы с примерами;
    
- экспорт данных.
    

---

## Comments — комментарии

Комментарии используются для обсуждения работы и фиксации решений.

Хороший комментарий содержит конкретную информацию:

```text
Проверил ошибку на test-окружении. Причина — повторная обработка callback.
Pull Request: ...
После объединения изменений необходимо повторно протестировать сценарии 1–4.
```

Плохой комментарий:

```text
Посмотрел.
```

Важные решения лучше фиксировать в описании задачи или документации, а не оставлять только внутри длинной цепочки комментариев.

---

# 14. Связи между задачами

Задачи могут быть связаны между собой.

Распространённые типы связей:

- **blocks** — блокирует;
    
- **is blocked by** — заблокирована другой задачей;
    
- **duplicates** — дублирует;
    
- **is duplicated by** — имеет дубликат;
    
- **clones** — клонирует;
    
- **is cloned by** — клонирована;
    
- **relates to** — связана с другой задачей.
    

Например:

```text
DATA-100 blocks DATA-120
```

Это означает, что DATA-120 нельзя нормально завершить до выполнения DATA-100.

Связи помогают отображать зависимости между командами и пространствами.

## Parent и Linked issue — не одно и то же

**Parent** означает иерархическую принадлежность:

```text
Epic
└── Story
```

**Link** означает логическую зависимость или связь:

```text
Story A blocks Story B
```

Задача может иметь одного родителя, но несколько связей с другими задачами.

---

# 15. Backlog — бэклог

**Backlog** — упорядоченный список работ, которые потенциально должны быть выполнены.

В бэклоге могут находиться:

- идеи;
    
- будущие Story;
    
- Bug;
    
- технические задачи;
    
- исследования;
    
- задачи, ещё не включённые в спринт.
    

Product Owner или другой ответственный регулярно:

- добавляет задачи;
    
- уточняет их;
    
- меняет порядок;
    
- удаляет неактуальные элементы;
    
- связывает задачи с эпиками;
    
- готовит работу для следующих спринтов.
    

В Scrum backlog содержит задачи, распределённые между общим бэклогом и спринтами. В нём можно создавать, обновлять, ранжировать задачи и назначать их эпикам, версиям и спринтам.

## Backlog — не склад забытых задач

Хороший бэклог:

- регулярно очищается;
    
- упорядочен;
    
- содержит понятные задачи;
    
- отражает текущие приоритеты;
    
- не перегружен устаревшими идеями.
    

---

# 16. Board — доска

**Board** — визуальное представление задач и их движения через этапы процесса.

Пример:

|To Do|In Progress|Code Review|Testing|Done|
|---|---|---|---|---|
|Запланировано|Разрабатывается|Проверяется код|Тестируется|Завершено|

Каждая карточка на доске соответствует задаче Jira.

Важно:

> Доска не хранит отдельные копии задач. Она показывает задачи, которые подходят под её фильтр.

Одна задача может отображаться на нескольких досках, если соответствует их условиям.

Доска может показывать задачи:

- одного проекта;
    
- нескольких проектов;
    
- конкретной команды;
    
- определённого компонента;
    
- выбранного типа;
    
- конкретной версии.
    

Jira позволяет создавать доски на основе JQL-фильтров, включая задачи из одного или нескольких пространств.

---

# 17. Scrum Board

Scrum-доска используется для работы спринтами.

Обычно она включает:

- Backlog;
    
- будущие спринты;
    
- активный спринт;
    
- отчёты;
    
- диаграмму Burndown;
    
- Velocity Chart.
    

Общий порядок работы:

```text
Создание задач
→ уточнение бэклога
→ планирование спринта
→ запуск спринта
→ выполнение задач
→ завершение спринта
```

---

# 18. Kanban Board

Kanban-доска используется для непрерывного потока работы.

Пример:

```text
Backlog → Ready → In Progress → Review → Testing → Done
```

Основное отличие от Scrum:

- нет обязательных спринтов;
    
- задачи берутся по мере освобождения команды;
    
- работа движется непрерывным потоком;
    
- часто применяются ограничения WIP.
    

Kanban backlog может отдельно показывать Backlog и Selected for Development, чтобы команда видела подготовленные задачи, не перегружая рабочую доску.

---

# 19. Column, Status и Workflow — в чём разница

Эти понятия часто путают.

## Status

Текущее состояние задачи:

```text
Code Review
```

## Column

Визуальная колонка на доске:

```text
In Progress
```

## Workflow

Полный маршрут, по которому может двигаться задача:

```text
Open
→ Analysis
→ Ready for Development
→ In Progress
→ Code Review
→ Testing
→ Ready for Release
→ Done
```

Одна колонка может содержать несколько статусов.

Например:

```text
Колонка In Progress:
- Development
- Code Review
- Testing
```

Перед перемещением карточек администратор сопоставляет статусы workflow с колонками доски.

---

# 20. Workflow — рабочий процесс

**Workflow** — набор статусов и допустимых переходов задачи между ними.

Jira определяет workflow как совокупность статусов и transitions, через которые задача проходит в течение своего жизненного цикла.

Пример:

```text
To Do → In Progress → Review → Testing → Done
```

## Transition — переход

**Transition** — разрешённое перемещение из одного статуса в другой.

Например:

```text
Start work:
To Do → In Progress

Send to review:
In Progress → Code Review

Reopen:
Done → To Do
```

Чтобы переместить задачу между двумя статусами, между ними должен существовать transition. Переходы направленные: для движения в обе стороны обычно нужны два отдельных перехода.

## Workflow может содержать правила

Например:

- только разработчик может отправить задачу на Code Review;
    
- нельзя завершить задачу без заполненного Fix Version;
    
- при переходе в Done автоматически устанавливается Resolution;
    
- при переходе в Testing задача назначается тестировщику;
    
- при создании критического Bug отправляется уведомление.
    

В Jira workflow-правила могут ограничивать переход, проверять данные и выполнять действия после изменения статуса.

---

# 21. Пример жизненного цикла задачи

Рассмотрим Story:

```text
Добавить выгрузку банковской выписки в PDF
```

## 1. Backlog

Задача создана, но пока не запланирована.

## 2. Selected for Development

Product Owner определил, что задача достаточно важна и подготовлена к разработке.

## 3. In Progress

Разработчик начал работу.

## 4. Code Review

Создан Pull Request, другой разработчик проверяет код.

## 5. Testing

Изменения развёрнуты на тестовом окружении, QA проверяет критерии приёмки.

## 6. Ready for Release

Функция готова, но ещё не выпущена пользователям.

## 7. Done

Функция выпущена и соответствует критериям готовности.

Если тестировщик обнаружит ошибку, задача может вернуться:

```text
Testing → In Progress
```

---

# 22. Definition of Ready

**Definition of Ready — DoR** описывает условия, при которых задачу можно брать в разработку.

Пример:

- понятна бизнес-цель;
    
- есть описание;
    
- определены критерии приёмки;
    
- приложены макеты;
    
- известны зависимости;
    
- задача оценена;
    
- отсутствуют критические вопросы;
    
- задача достаточно мала для выполнения.
    

DoR обычно является правилом команды, а не обязательным встроенным объектом Jira.

---

# 23. Definition of Done

**Definition of Done — DoD** описывает общие требования к завершённой работе.

Пример:

- код написан;
    
- проведено код-ревью;
    
- тесты пройдены;
    
- критерии приёмки выполнены;
    
- документация обновлена;
    
- мониторинг добавлен;
    
- миграции проверены;
    
- критические ошибки отсутствуют;
    
- изменение готово к эксплуатации.
    

## DoD и Acceptance Criteria

**Acceptance Criteria** относятся к конкретной задаче:

```text
Пользователь может скачать выписку за выбранный период.
```

**Definition of Done** применяется ко всем задачам команды:

```text
Проведено код-ревью и пройдены автоматические тесты.
```

---

# 24. Sprint — спринт

**Sprint** — ограниченный период, в течение которого Scrum-команда работает над выбранной целью и набором задач.

Обычно спринт длится:

- одну неделю;
    
- две недели;
    
- три недели;
    
- четыре недели.
    

В Jira спринт создаётся в Backlog, после чего команда:

1. добавляет задачи;
    
2. формулирует цель;
    
3. запускает спринт;
    
4. перемещает задачи по доске;
    
5. завершает спринт.
    

Спринты относятся к Scrum-доскам и не применяются к Kanban-пространствам.

## Active Sprint

Текущий запущенный спринт.

## Future Sprint

Будущий спринт, который ещё не начался.

## Completed Sprint

Завершённый спринт.

Незавершённые задачи при закрытии спринта обычно переносятся в Backlog или другой спринт в зависимости от выбранного действия и настроек.

---

# 25. Роли в Jira и роли в Scrum

Необходимо различать:

1. **роли в процессе разработки**;
    
2. **роли и разрешения в Jira**;
    
3. **поля конкретной задачи**.
    

Это разные сущности.

---

# 26. Продуктовые и командные роли

## Product Owner

Отвечает за ценность продукта и порядок Product Backlog.

Обычно Product Owner:

- формирует приоритеты;
    
- уточняет требования;
    
- принимает продуктовые решения;
    
- определяет цель спринта вместе с командой;
    
- взаимодействует с заинтересованными сторонами;
    
- принимает или отклоняет результат.
    

Product Owner может активно работать в Jira, но Jira не требует, чтобы у каждого проекта обязательно существовала системная роль с таким названием.

---

## Scrum Master

Помогает команде применять Scrum:

- организует события;
    
- помогает устранять препятствия;
    
- улучшает процесс;
    
- защищает команду от ненужных вмешательств;
    
- следит за соблюдением принципов Scrum.
    

Scrum Master не обязательно является администратором Jira.

---

## Developer

Разрабатывает продукт:

- берёт задачи;
    
- уточняет требования;
    
- изменяет Assignee;
    
- обновляет статусы;
    
- оставляет комментарии;
    
- прикладывает Pull Request;
    
- регистрирует трудозатраты;
    
- участвует в оценке.
    

---

## QA Engineer

Отвечает за проверку качества:

- уточняет критерии приёмки;
    
- создаёт тестовые сценарии;
    
- проверяет реализованные задачи;
    
- регистрирует Bug;
    
- возвращает задачу на доработку;
    
- подтверждает исправление.
    

---

## Business Analyst или System Analyst

Помогает формализовать требования:

- описывает бизнес-процессы;
    
- создаёт Story и Task;
    
- формулирует критерии приёмки;
    
- описывает интеграции;
    
- добавляет схемы;
    
- связывает зависимости;
    
- уточняет ограничения.
    

---

## Tech Lead

Отвечает за техническое направление:

- помогает разбивать крупные задачи;
    
- принимает архитектурные решения;
    
- выявляет технические риски;
    
- участвует в оценке;
    
- контролирует качество технических решений.
    

---

## Project Manager

Может отвечать за:

- сроки;
    
- риски;
    
- бюджет;
    
- зависимости;
    
- коммуникации;
    
- отчётность;
    
- координацию участников.
    

В Agile-командах обязанности Project Manager могут быть распределены между Product Owner, Scrum Master, Delivery Manager и командой.

# 27. Системные роли и права Jira

## Jira Administrator

Администратор Jira управляет настройками всей системы:

- типами задач;
    
- глобальными полями;
    
- workflow;
    
- схемами разрешений;
    
- экранами;
    
- уведомлениями;
    
- приоритетами;
    
- интеграциями;
    
- глобальными настройками.
    

---

## Space/Project Administrator

Администратор отдельного пространства или проекта.

В зависимости от типа проекта он может:

- настраивать участников;
    
- изменять доску;
    
- добавлять статусы;
    
- управлять компонентами;
    
- настраивать автоматизацию;
    
- изменять доступ;
    
- управлять версиями.
    

В team-managed пространствах команда получает более простую и автономную настройку. В company-managed пространствах общими схемами и экранами обычно управляет Jira Administrator.

---

## Board Administrator

Администратор конкретной доски.

Он может управлять:

- фильтром доски;
    
- колонками;
    
- сопоставлением статусов;
    
- быстрыми фильтрами;
    
- swimlanes;
    
- отображением карточек;
    
- оценкой;
    
- некоторыми настройками спринтов.
    

Board Administrator не обязательно является администратором всего проекта.

---

## User

Обычный пользователь Jira, возможности которого определяются разрешениями.

Он может иметь право:

- просматривать задачи;
    
- создавать задачи;
    
- комментировать;
    
- назначать исполнителя;
    
- изменять статус;
    
- редактировать поля;
    
- регистрировать время;
    
- закрывать задачи.

# 28. Assignee, Reporter и Watcher — не роли проекта

Это поля или отношения внутри конкретной задачи.

|Термин|Значение|
|---|---|
|Assignee|Текущий ответственный за выполнение|
|Reporter|Автор или инициатор задачи|
|Watcher|Наблюдает за изменениями|
|Project Admin|Управляет настройками проекта|
|Board Admin|Управляет доской|
|Product Owner|Управляет ценностью и приоритетами продукта|

Один человек может одновременно быть:

- Product Owner проекта;
    
- Reporter конкретной Story;
    
- Watcher нескольких Bug;
    
- Assignee отдельной аналитической задачи.

# 29. Team-managed и Company-managed проекты

В Jira Cloud существуют два основных способа управления пространствами.

## Team-managed

Подходит автономной команде.

Особенности:

- более простая настройка;
    
- команда самостоятельно изменяет процесс;
    
- конфигурация не распространяется на другие пространства;
    
- меньше зависимости от центрального администратора.
    

## Company-managed

Подходит организации, где нужно стандартизировать работу нескольких команд.

Особенности:

- централизованные схемы;
    
- общие workflow;
    
- более сложные разрешения;
    
- общие поля и экраны;
    
- больше возможностей настройки;
    
- изменения могут затрагивать несколько пространств.
    

Atlassian рекомендует team-managed пространства для автономных команд, которым нужна простая самостоятельная настройка, а company-managed — для стандартизации процессов между несколькими командами и сложной конфигурации.

# 30. Filters — фильтры

Фильтр выбирает задачи по определённым условиям.

Например:

- все мои незавершённые задачи;
    
- все критические Bug;
    
- задачи текущего спринта;
    
- задачи компонента Backend;
    
- просроченные задачи;
    
- задачи без исполнителя.
    

Фильтры можно сохранять и предоставлять другим пользователям. Jira содержит каталог личных и общих фильтров.

---

# 31. JQL — Jira Query Language

**JQL** — язык запросов для поиска задач в Jira.

Он похож по назначению на SQL-фильтрацию, но используется только для поиска объектов Jira.

## Мои незавершённые задачи

```text
assignee = currentUser()
AND statusCategory != Done
```

## Все открытые Bug проекта DATA

```text
project = DATA
AND issuetype = Bug
AND statusCategory != Done
```

## Задачи с высоким приоритетом

```text
priority IN (Highest, High)
AND statusCategory != Done
```

## Задачи без исполнителя

```text
assignee IS EMPTY
```

## Просроченные задачи

```text
duedate < now()
AND statusCategory != Done
```

## Задачи текущего спринта

```text
sprint IN openSprints()
```

## Задачи текущего пользователя в активном спринте

```text
assignee = currentUser()
AND sprint IN openSprints()
AND statusCategory != Done
ORDER BY priority DESC
```

В JQL операторы сравнивают поле слева со значением или функцией справа, а функции вроде `now()` позволяют создавать динамические запросы.

---

# 32. Quick Filters

**Quick Filter** — кнопка на доске, которая временно оставляет только подходящие задачи.

Примеры:

- Only My Issues;
    
- Bugs;
    
- Backend;
    
- Blocked;
    
- High Priority;
    
- No Assignee.
    

Quick Filters позволяют быстро переключаться между разными представлениями общей доски, например показывать только ошибки или задачи определённой команды.

---

# 33. Dashboard — дашборд

**Dashboard** — экран с отчётами и виджетами Jira.

На нём могут находиться:

- список моих задач;
    
- задачи по статусам;
    
- задачи по исполнителям;
    
- Created vs Resolved;
    
- Sprint Burndown;
    
- календарь;
    
- статистика по приоритетам;
    
- результаты сохранённого фильтра;
    
- диаграмма трудозатрат.
    

Дашборд может быть:

- личным;
    
- командным;
    
- общим для проекта;
    
- доступным определённой группе.
    

Общие дашборды имеют владельца и настройки предоставления доступа.

# 35. Release и Version

**Version** — конкретная версия продукта.

**Release** — процесс выпуска версии пользователям.

Пример:

```text
Version: 2.5.0
Release Date: 30 July 2026
```

В неё могут входить:

- новые Story;
    
- исправленные Bug;
    
- технические Task.
    

На странице релиза Jira может показывать связанные с задачами:

- commits;
    
- branches;
    
- pull requests;
    
- builds;
    
- deployments,
    

если Jira подключена к соответствующим инструментам разработки.

# 36. Automation

Jira Automation позволяет выполнять действия автоматически.

Правило обычно состоит из трёх частей:

```text
Trigger → Condition → Action
```

## Trigger — триггер

Событие, запускающее правило:

- создана задача;
    
- изменён статус;
    
- наступила дата;
    
- добавлен комментарий;
    
- изменён приоритет;
    
- завершён спринт.
    

## Condition — условие

Проверка:

- тип задачи равен Bug;
    
- приоритет равен Highest;
    
- компонент равен Backend;
    
- исполнитель отсутствует.
    

## Action — действие

Автоматическое действие:

- назначить исполнителя;
    
- изменить поле;
    
- добавить комментарий;
    
- создать подзадачу;
    
- отправить уведомление;
    
- связать задачи;
    
- переместить статус.
    

Пример:

```text
Когда создаётся Bug с Priority = Highest,
назначить его дежурному инженеру
и отправить сообщение в командный канал.
```

В актуальной Jira Cloud автоматизация описывается как flow из триггера, условий и действий.

# 37. Как обычно выглядит работа разработчика в Jira

## Утром

1. Открыть активный спринт или Kanban-доску.
    
2. Проверить назначенные задачи.
    
3. Посмотреть комментарии и уведомления.
    
4. Проверить заблокированные задачи.
    
5. Выбрать следующую приоритетную работу.
    

## Перед началом задачи

1. Прочитать описание.
    
2. Проверить критерии приёмки.
    
3. Посмотреть родительский Epic.
    
4. Проверить связанные задачи.
    
5. Убедиться, что нет блокирующих зависимостей.
    
6. Задать вопросы, если требования непонятны.
    
7. Назначить задачу на себя.
    
8. Перевести в In Progress.
    

## Во время работы

1. Создать Git-ветку с ключом задачи.
    
2. Фиксировать важные решения.
    
3. Обновлять оценку или остаток времени при необходимости.
    
4. Сообщить о блокере.
    
5. Связать Pull Request с задачей.
    

## После разработки

1. Проверить критерии приёмки.
    
2. Добавить тесты.
    
3. Создать Pull Request.
    
4. Перевести задачу в Code Review.
    
5. Исправить замечания.
    
6. Передать задачу на тестирование.
    
7. После успешной проверки перевести в Done или Ready for Release.

# 38. Полный пример структуры задач

## Initiative

```text
Повысить удобство оформления заказов
```

## Epic

```text
Реализовать новые способы оплаты
```

## Story

```text
Как покупатель,
я хочу оплачивать заказ через СБП,
чтобы не вводить данные банковской карты.
```

## Acceptance Criteria

```text
1. Пользователь может выбрать СБП.
2. Система показывает QR-код.
3. Успешная оплата изменяет статус заказа.
4. Неуспешная оплата не создаёт оплаченный заказ.
5. Повторный callback не приводит к повторному зачислению.
```

## Tasks

```text
Создать интеграцию с API платёжного провайдера
Настроить обработку callback
Добавить мониторинг платежей
Подготовить документацию
```

## Subtasks

```text
Создать таблицу payment_transactions
Добавить endpoint создания платежа
Реализовать проверку подписи callback
Добавить unit-тесты
Добавить метрики Prometheus
```

## Bugs

```text
При повторном callback заказ повторно отмечается оплаченным
QR-код не обновляется после истечения срока
```

## Links

```text
BANK-125 blocks BANK-140
BANK-141 relates to BANK-125
BANK-170 duplicates BANK-141
```

# 39. Как писать хорошие задачи

## Название

Должно описывать конкретный результат:

```text
Добавить проверку уникальности номера телефона
```

## Контекст

Почему задача появилась:

```text
Сейчас пользователь может зарегистрировать несколько аккаунтов
на один номер телефона, что нарушает правила бонусной программы.
```

## Требование

Что необходимо изменить:

```text
Перед созданием пользователя проверять наличие активного аккаунта
с таким номером.
```

## Критерии приёмки

Как проверить результат:

```text
1. Повторная регистрация активного номера запрещена.
2. Пользователь получает понятное сообщение.
3. Удалённый аккаунт не блокирует новую регистрацию.
4. Проверка покрыта автоматическими тестами.
```

## Дополнительные материалы

- макеты;
    
- API-контракт;
    
- схема;
    
- документация;
    
- примеры данных;
    
- связанные задачи.

# 40. Типичные ошибки новичков

## 1. Задача находится в In Progress, но работа ещё не началась

Статус должен отражать реальность.

## 2. Работа началась, но задача остаётся в To Do

Команда не видит фактическую загрузку.

## 3. В одной Story находится месячный объём работ

Крупную работу необходимо разделить.

## 4. Создаётся Task без понятного результата

Название «заняться API» не объясняет, что должно быть получено.

## 5. Bug не содержит шагов воспроизведения

Исполнитель не может подтвердить проблему.

## 6. Все задачи имеют High Priority

Если всё срочное, приоритет перестаёт помогать.

## 7. Важные решения остаются только в личной переписке

Остальные участники не видят контекст.

## 8. Задача закрывается без проверки критериев

Статус Done должен означать фактическую готовность.

## 9. Подзадачи используются вместо самостоятельных задач

Если работа имеет отдельную ценность, собственный жизненный цикл или может выполняться независимо, лучше создать Task или Story.

## 10. Доска содержит слишком много статусов

Избыточный workflow становится сложным и редко отражается корректно. Atlassian рекомендует сохранять workflow простым и ограничивать количество статусов и переходов.

# 42. Главное, что нужно запомнить

Jira строится вокруг задачи и её жизненного цикла:

```text
Задача создаётся
→ описывается
→ оценивается
→ получает приоритет
→ назначается исполнителю
→ включается в план
→ проходит через workflow
→ проверяется
→ завершается
```

Основная иерархия:

```text
Epic
└── Story / Task / Bug
    └── Subtask
```

Основная работа разработчика:

```text
Прочитать задачу
→ уточнить требования
→ взять в работу
→ обновлять статус
→ связать изменения кода
→ передать на проверку
→ исправить замечания
→ завершить задачу
```

Jira должна отражать реальное состояние работы команды. Если карточки не обновляются, зависимости не указываются, а требования обсуждаются только в личной переписке, доска перестаёт быть надёжным источником информации.

При первом знакомстве не нужно изучать все административные возможности. Для начала достаточно уметь:

1. найти проект и доску;
    
2. открыть свою задачу;
    
3. понять её тип и родителя;
    
4. прочитать описание и критерии приёмки;
    
5. проверить Assignee, Priority и Sprint;
    
6. посмотреть связанные задачи;
    
7. изменить статус;
    
8. оставить содержательный комментарий;
    
9. создать Bug или Task;
    
10. найти задачи через обычный поиск или простой JQL.
