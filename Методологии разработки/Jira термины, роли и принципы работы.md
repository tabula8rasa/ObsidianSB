## 1. Что такое Jira

**Jira** — система для управления задачами, процессами и разработкой продуктов.

В Jira команда может:

- создавать и описывать задачи;
    
- назначать ответственных;
    
- устанавливать приоритеты;
    
- отслеживать текущее состояние работы;
    
- планировать спринты;
    
- вести бэклог;
    
- связывать зависимые задачи;
    
- учитывать версии и релизы;
    
- строить отчёты;
    
- автоматизировать повторяющиеся действия.
    

Jira не является отдельной методологией. Она может использоваться с:

- Scrum;
    
- Kanban;
    
- Scrumban;
    
- Waterfall;
    
- собственным процессом компании.
    

То есть Scrum определяет правила организации работы, а Jira предоставляет инструменты для отображения и контроля этого процесса.

---

# 2. Важное замечание о терминологии

В Jira традиционно использовались термины:

- **Project** — проект;
    
- **Issue** — задача или объект работы;
    
- **Issue Type** — тип задачи.
    

Atlassian постепенно обновляет терминологию Jira Cloud:

- **Project → Space**;
    
- **Issue → Work item**;
    
- **Issue Type → Work type**.
    

При этом старые термины по-прежнему встречаются в интерфейсе, JQL, документации, интеграциях и повседневной речи команд. Поэтому на работе можно услышать как «создай issue в проекте», так и «создай work item в space». Смысл обычно одинаковый.

В этой заметке преимущественно используется привычное слово **задача**, а рядом указывается английский термин.

# 3. Основная структура Jira

Упрощённо Jira можно представить следующим образом:

**Организация → Jira → проект/пространство → задачи → подзадачи**

Например:

**Компания → Jira → Проект интернет-магазина → Задача оплаты → Подзадача создания API**

## Project или Space

**Project/Space** — отдельное рабочее пространство, в котором хранятся связанные задачи, доски, настройки и отчёты.

Проект может соответствовать:

- программному продукту;
    
- отдельной команде;
    
- бизнес-процессу;
    
- внутреннему сервису;
    
- направлению деятельности;
    
- конкретному клиентскому проекту.
    

Например:

- `SHOP` — интернет-магазин;
    
- `BANK` — мобильное банковское приложение;
    
- `DATA` — платформа данных;
    
- `SUPPORT` — техническая поддержка.
    

Jira Cloud позволяет использовать пространство для управления продуктом, проектом, командой или сервисом.

---

# 4. Что такое Issue или Work item

**Issue**, или **work item**, — основной объект работы в Jira.

Несмотря на буквальный перевод слова issue как «проблема», в Jira оно может обозначать практически любую единицу работы:

- новую функцию;
    
- ошибку;
    
- пользовательскую историю;
    
- техническую задачу;
    
- исследование;
    
- запрос;
    
- улучшение;
    
- подзадачу.
    

В Jira один work item может представлять Story, Bug, Task или другой настроенный в компании тип работы.

Каждая задача получает уникальный ключ.

Например:

```text
SHOP-125
DATA-842
BANK-301
```

Где:

- `SHOP` — ключ проекта;
    
- `125` — порядковый номер задачи.
    

Ключ задачи часто используется:

- в названии Git-ветки;
    
- в сообщении коммита;
    
- в Pull Request;
    
- в переписке;
    
- в документации;
    
- при поиске задачи.
    

Например:

```text
feature/DATA-842-add-user-mart
```

# 5. Иерархия задач в Jira

Стандартную иерархию можно представить так:

```text
Epic
└── Story / Task / Bug
    └── Subtask
```

По умолчанию Jira использует три уровня:

1. более крупная работа — обычно **Epic**;
    
2. стандартные задачи — Story, Task, Bug;
    
3. более мелкая работа — **Subtask**.
    

В крупных организациях над Epic могут находиться дополнительные уровни:

```text
Initiative
└── Capability
    └── Epic
        └── Story / Task / Bug
            └── Subtask
```

Дополнительные уровни иерархии зависят от тарифа и настройки Jira. Расширенная настройка иерархии доступна в Jira Cloud Premium и Enterprise.

# 6. Epic — эпик

**Epic** — крупное направление работы, которое нельзя разумно завершить в рамках одной небольшой задачи или одного короткого спринта.

Эпик объединяет несколько связанных Story, Task и Bug.

Пример эпика:

```text
EPIC: Реализовать оплату заказов
```

В него могут входить:

- добавить оплату банковской картой;
    
- создать API для проведения платежа;
    
- интегрироваться с платёжным провайдером;
    
- разработать страницу оплаты;
    
- добавить возврат средств;
    
- настроить журналирование платежей;
    
- добавить мониторинг ошибок;
    
- провести нагрузочное тестирование.
    

Эпик обычно описывает крупную пользовательскую или бизнес-возможность, а не одно техническое действие.

## Хороший эпик

```text
Реализовать систему онлайн-оплаты заказов
```

## Слишком маленький эпик

```text
Добавить кнопку «Оплатить»
```

Это скорее Story или Task.

## Слишком большой эпик

```text
Создать интернет-магазин
```

Такую работу лучше разделить на несколько эпиков:

- каталог;
    
- личный кабинет;
    
- корзина;
    
- оплата;
    
- доставка;
    
- уведомления.
    

В стандартной иерархии Epic находится над Story, Task и Bug, а подзадачи располагаются ниже стандартных типов.

# 7. Story — пользовательская история

**Story**, или **User Story**, — требование, сформулированное с точки зрения пользователя и описывающее полезный для него результат.

Классический формат:

```text
Как <роль>,
я хочу <действие>,
чтобы <получить ценность>.
```

Пример:

```text
Как покупатель,
я хочу сохранить банковскую карту,
чтобы не вводить её данные при каждом заказе.
```

Story должна объяснять не только то, **что** нужно создать, но и **зачем** это необходимо пользователю.

## Story обычно содержит

- краткое название;
    
- пользовательскую ценность;
    
- описание;
    
- критерии приёмки;
    
- ограничения;
    
- макеты или ссылки;
    
- оценку;
    
- зависимости;
    
- принадлежность к эпику.
    

## Acceptance Criteria — критерии приёмки

Критерии приёмки описывают условия, при которых Story считается реализованной правильно.

Пример:

```text
1. Пользователь может сохранить карту после успешной оплаты.
2. Полный номер карты не хранится в системе.
3. Пользователь может удалить сохранённую карту.
4. Просроченная карта не может использоваться для оплаты.
5. При ошибке отображается понятное сообщение.
```

Story отвечает на вопрос:

> Какую ценность должен получить пользователь?

## Разница между Story и Task

**Story:**

```text
Как клиент, я хочу скачать банковскую выписку,
чтобы передать её в бухгалтерию.
```

**Task:**

```text
Настроить хранение сформированных PDF-выписок в объектном хранилище.
```

Story описывает пользовательскую ценность, а Task — конкретную работу команды.

# 8. Subtask — подзадача

**Subtask** — небольшая часть Story, Task или Bug.

Подзадача используется, когда одну задачу необходимо разделить между несколькими действиями или специалистами.

Пример:

```text
STORY: Добавить регистрацию пользователя

SUBTASK 1: Разработать форму регистрации
SUBTASK 2: Создать API регистрации
SUBTASK 3: Создать таблицу пользователей
SUBTASK 4: Добавить отправку письма
SUBTASK 5: Написать автоматические тесты
```

Подзадачи позволяют отдельно отслеживать:

- исполнителей;
    
- статусы;
    
- трудозатраты;
    
- технические этапы;
    
- прогресс родительской задачи.
    

Подзадача не должна существовать независимо от родительской задачи. Jira позволяет разбивать стандартные задачи — Story, Task и Bug — на более мелкие подзадачи.

# 9. Initiative — инициатива

**Initiative** — крупная бизнес-цель, объединяющая несколько эпиков.

Она чаще используется в больших компаниях и при масштабировании Agile.

Пример:

```text
INITIATIVE: Повысить конверсию интернет-магазина
```

В неё могут входить эпики:

- упростить регистрацию;
    
- улучшить поиск;
    
- внедрить рекомендации;
    
- добавить новые способы оплаты;
    
- сократить количество шагов оформления заказа.
    

Initiative обычно отвечает на вопрос:

> Какую крупную бизнес-цель должна реализовать компания?

Стандартная Jira не обязательно содержит Initiative как отдельный тип: структура зависит от тарифа и конфигурации организации.

---

# 10. Spike — исследование

**Spike** — исследовательская задача, создаваемая, когда команда пока не знает, как реализовать решение или сколько работы оно потребует.

Примеры:

- сравнить Kafka и RabbitMQ;
    
- проверить возможность миграции на новую базу данных;
    
- исследовать причины медленного SQL-запроса;
    
- создать прототип интеграции;
    
- оценить ограничения внешнего API.
    

Результатом Spike обычно является не готовая функция, а:

- документ;
    
- прототип;
    
- набор измерений;
    
- архитектурное решение;
    
- оценка;
    
- список рисков;
    
- рекомендации.
    

Spike не является обязательным стандартным типом Jira. Компания может создать его как отдельный work type либо использовать обычный Task с соответствующей меткой.

# 12. Связи между задачами

Задачи могут быть связаны между собой.

Распространённые типы связей:

- **blocks** — блокирует;
    
- **is blocked by** — заблокирована другой задачей;
    
- **duplicates** — дублирует;
    
- **is duplicated by** — имеет дубликат;
    
- **clones** — клонирует;
    
- **is cloned by** — клонирована;
    
- **relates to** — связана с другой задачей.
    

Например:

```text
DATA-100 blocks DATA-120
```

Это означает, что DATA-120 нельзя нормально завершить до выполнения DATA-100.

Связи помогают отображать зависимости между командами и пространствами.

## Parent и Linked issue — не одно и то же

**Parent** означает иерархическую принадлежность:

```text
Epic
└── Story
```

**Link** означает логическую зависимость или связь:

```text
Story A blocks Story B
```

Задача может иметь одного родителя, но несколько связей с другими задачами.

# 13. Backlog — бэклог

**Backlog** — упорядоченный список работ, которые потенциально должны быть выполнены.

В Scrum backlog содержит задачи, распределённые между общим бэклогом и спринтами. В нём можно создавать, обновлять, ранжировать задачи и назначать их эпикам, версиям и спринтам.

---

# 14. Board — доска

**Board** — визуальное представление задач и их движения через этапы процесса.

Пример:

|To Do|In Progress|Code Review|Testing|Done|
|---|---|---|---|---|
|Запланировано|Разрабатывается|Проверяется код|Тестируется|Завершено|

Каждая карточка на доске соответствует задаче Jira.

Важно:

> Доска не хранит отдельные копии задач. Она показывает задачи, которые подходят под её фильтр.

Одна задача может отображаться на нескольких досках, если соответствует их условиям.

Доска может показывать задачи:

- одного проекта;
    
- нескольких проектов;
    
- конкретной команды;
    
- определённого компонента;
    
- выбранного типа;
    
- конкретной версии.
    

Jira позволяет создавать доски на основе JQL-фильтров, включая задачи из одного или нескольких пространств.

---

# 15. Scrum Board

Scrum-доска используется для работы спринтами.

Обычно она включает:

- Backlog;
    
- будущие спринты;
    
- активный спринт;
    
- отчёты;
    
- диаграмму Burndown;
    
- Velocity Chart.
    

Общий порядок работы:

```text
Создание задач
→ уточнение бэклога
→ планирование спринта
→ запуск спринта
→ выполнение задач
→ завершение спринта
```

---

# 16. Kanban Board

Kanban-доска используется для непрерывного потока работы.

Пример:

```text
Backlog → Ready → In Progress → Review → Testing → Done
```

Основное отличие от Scrum:

- нет обязательных спринтов;
    
- задачи берутся по мере освобождения команды;
    
- работа движется непрерывным потоком;
    
- часто применяются ограничения WIP.
    

Kanban backlog может отдельно показывать Backlog и Selected for Development, чтобы команда видела подготовленные задачи, не перегружая рабочую доску.

---

# 17. Пример жизненного цикла задачи

Рассмотрим Story:

```text
Добавить выгрузку банковской выписки в PDF
```

## 1. Backlog

Задача создана, но пока не запланирована.

## 2. Selected for Development

Product Owner определил, что задача достаточно важна и подготовлена к разработке.

## 3. In Progress

Разработчик начал работу.

## 4. Code Review

Создан Pull Request, другой разработчик проверяет код.

## 5. Testing

Изменения развёрнуты на тестовом окружении, QA проверяет критерии приёмки.

## 6. Ready for Release

Функция готова, но ещё не выпущена пользователям.

## 7. Done

Функция выпущена и соответствует критериям готовности.

Если тестировщик обнаружит ошибку, задача может вернуться:

```text
Testing → In Progress
```

# 31. JQL — Jira Query Language

**JQL** — язык запросов для поиска задач в Jira.

Он похож по назначению на SQL-фильтрацию, но используется только для поиска объектов Jira.

## Мои незавершённые задачи

```text
assignee = currentUser()
AND statusCategory != Done
```

## Все открытые Bug проекта DATA

```text
project = DATA
AND issuetype = Bug
AND statusCategory != Done
```

## Задачи с высоким приоритетом

```text
priority IN (Highest, High)
AND statusCategory != Done
```

## Задачи без исполнителя

```text
assignee IS EMPTY
```

## Просроченные задачи

```text
duedate < now()
AND statusCategory != Done
```

## Задачи текущего спринта

```text
sprint IN openSprints()
```

## Задачи текущего пользователя в активном спринте

```text
assignee = currentUser()
AND sprint IN openSprints()
AND statusCategory != Done
ORDER BY priority DESC
```

В JQL операторы сравнивают поле слева со значением или функцией справа, а функции вроде `now()` позволяют создавать динамические запросы.

# 36. Automation

Jira Automation позволяет выполнять действия автоматически.

Правило обычно состоит из трёх частей:

```text
Trigger → Condition → Action
```

Пример:

```text
Когда создаётся Bug с Priority = Highest,
назначить его дежурному инженеру
и отправить сообщение в командный канал.
```

В актуальной Jira Cloud автоматизация описывается как flow из триггера, условий и действий.

# 39. Как писать хорошие задачи

## Название

Должно описывать конкретный результат:

```text
Добавить проверку уникальности номера телефона
```

## Контекст

Почему задача появилась:

```text
Сейчас пользователь может зарегистрировать несколько аккаунтов
на один номер телефона, что нарушает правила бонусной программы.
```

## Требование

Что необходимо изменить:

```text
Перед созданием пользователя проверять наличие активного аккаунта
с таким номером.
```

## Критерии приёмки

Как проверить результат:

```text
1. Повторная регистрация активного номера запрещена.
2. Пользователь получает понятное сообщение.
3. Удалённый аккаунт не блокирует новую регистрацию.
4. Проверка покрыта автоматическими тестами.
```
