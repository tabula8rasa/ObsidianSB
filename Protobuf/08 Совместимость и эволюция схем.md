## 1. Главная цель

В распределённой системе невозможно гарантировать одновременное обновление всех сервисов.

Поэтому схема должна позволять:

```text
новому producer работать со старым consumer
старому producer работать с новым consumer
```

хотя бы во время миграции.

## 2. Почему добавление поля обычно безопасно

Версия 1:

```proto
message User {
  int64 id = 1;
  string name = 2;
}
```

Версия 2:

```proto
message User {
  int64 id = 1;
  string name = 2;
  optional string email = 3;
}
```

Старый consumer не знает поле `3`, но может пропустить его благодаря wire type.

Новый consumer читает старое сообщение и видит отсутствие `email`.

## 3. Номера важнее имён

Бинарный формат использует:

```text
номер + wire type + значение
```

Переименование при сохранении номера может остаться бинарно совместимым:

```proto
// Было
string name = 2;

// Стало
string display_name = 2;
```

Но это может сломать:

- Python-код;
- JSON;
- TextFormat;
- generated SDK;
- пользователей поля по имени.

Поэтому переименование всё равно требует анализа.

## 4. Нельзя менять номер

```proto
// Было
string email = 3;

// Стало
string email = 7;
```

Для wire format это два разных поля.

## 5. Нельзя переиспользовать номер

```proto
// Было
string email = 3;

// Позже
Address address = 3;
```

Старые байты поля `3` могут быть прочитаны с новым смыслом.

Правильно:

```proto
message User {
  reserved 3;
  reserved "email";
}
```

## 6. Изменение типа

Опасно:

```proto
// Было
int64 id = 1;

// Стало
string id = 1;
```

Даже если некоторые типы имеют одинаковый wire type, это не означает, что изменение безопасно на уровне семантики и generated code.

Практическое правило:

> Не изменять тип существующего поля. Создать новое поле с новым номером.

```proto
int64 legacy_id = 1 [deprecated = true];
string id = 4;
```

## 7. Изменение смысла

Формально тип может остаться тем же:

```proto
int64 value = 1;
```

Но если раньше это была цена в копейках, а теперь количество секунд, контракт сломан семантически.

Смысл поля — часть API.

## 8. Singular и repeated

Опасно менять:

```proto
string role = 1;
```

на:

```proto
repeated string role = 1;
```

Даже при частичной wire-совместимости прикладное поведение и generated API изменятся.

## 9. Enum

Безопаснее добавлять новые значения:

```proto
enum Status {
  STATUS_UNSPECIFIED = 0;
  STATUS_ACTIVE = 1;
  STATUS_BLOCKED = 2;
}
```

Но старые consumers должны корректно обрабатывать незнакомое числовое значение.

Не следует:

- менять номера существующих значений;
- переиспользовать удалённый номер;
- строить логику, считающую, что перечисление навсегда закрыто.

Удаление:

```proto
enum Status {
  reserved 2;
  reserved "STATUS_BLOCKED";

  STATUS_UNSPECIFIED = 0;
  STATUS_ACTIVE = 1;
}
```

## 10. Unknown fields

Старый runtime может сохранить неизвестные поля при бинарном parse/serialize.

Но они могут быть потеряны:

- после преобразования в JSON;
- после построения нового объекта вручную;
- после `DiscardUnknownFields()`;
- в некоторых промежуточных преобразованиях.

## 11. Presence

При implicit scalar presence отсутствуют различия:

```text
не передано
передано значение 0
```

При развитии API это может мешать patch-операциям.

Для полей, где отсутствие означает «не изменять», используйте `optional`.

```proto
message UpdateUserRequest {
  int64 user_id = 1;
  optional string name = 2;
  optional string email = 3;
}
```

## 12. Версионирование package

```proto
package company.users.v1;
```

Для несовместимого нового API:

```proto
package company.users.v2;
```

Так одновременно существуют:

```text
company.users.v1.User
company.users.v2.User
```

Используйте новую major-версию, когда совместимая миграция невозможна или новый контракт концептуально другой.

## 13. Expand — migrate — contract

Правильная миграция:

### Expand

Добавить новое поле, не удаляя старое:

```proto
string old_id = 1 [deprecated = true];
string canonical_id = 2;
```

### Migrate

1. обновить generated SDK;
2. развернуть consumers;
3. начать читать новое поле;
4. обновить producers;
5. начать заполнять оба или новое поле;
6. перенести данные.

### Contract

Только когда старое поле больше не используется:

```proto
reserved 1;
reserved "old_id";
```

## 14. Порядок развёртывания

Для нового поля:

```text
1. Изменить общую схему.
2. Проверить совместимость.
3. Выпустить новую версию SDK.
4. Обновить consumers.
5. Развернуть consumers.
6. Обновить producer.
7. Начать отправлять новое поле.
```

Для удаления старого поля процесс занимает несколько релизов.

## 15. Центральный контракт

Плохой подход:

```text
service-a/user.proto
service-b/user.proto
service-c/user.proto
```

с ручным копированием.

Хороший подход:

```text
company-protos/
└── company/
    ├── users/v1/
    ├── orders/v1/
    └── common/v1/
```

Из этого источника создаются generated packages для всех языков.

## 16. Автоматическая проверка

```bash
buf lint
buf breaking --against '.git#branch=main'
```

`lint` проверяет качество текущей схемы.

`breaking` сравнивает новую схему со старой.
