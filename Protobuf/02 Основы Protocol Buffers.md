## 1. Проблема, которую решает Protobuf

В памяти Python можно создать объект:

```python
user = {
    "id": 150,
    "name": "Ann",
    "email": "a@b",
}
```

Но по сети нельзя передать сам Python-словарь. Сеть передаёт байты. Поэтому нужны два преобразования:

```text
структурированные данные → bytes
bytes → структурированные данные
```

Первое называется **сериализацией**, второе — **десериализацией**.

Protobuf предоставляет:

- язык описания структуры данных;
- генераторы кода для разных языков;
- runtime-библиотеки;
- компактный бинарный формат;
- правила совместимого изменения схем.

## 2. Из каких частей состоит Protobuf

### `.proto`

Человекочитаемая схема:

```proto
message User {
  int64 id = 1;
  string name = 2;
}
```

### Компилятор `protoc`

Читает `.proto` и запускает генератор нужного языка:

```bash
protoc --python_out=. user.proto
```

### Сгенерированный код

Для Python:

```text
user_pb2.py
```

Он предоставляет класс:

```python
user_pb2.User
```

### Runtime-библиотека

Python-пакет:

```bash
python -m pip install protobuf
```

Runtime:

- создаёт классы сообщений;
- проверяет присваиваемые типы;
- сериализует объекты;
- разбирает байты;
- работает с дескрипторами схем.

### Wire format

Набор правил, определяющих, как номера полей и значения записываются в бинарном виде.

## 3. Что Protobuf делает

```python
payload = message.SerializeToString()
```

```python
message.ParseFromString(payload)
```

То есть:

```text
объект ↔ bytes
```

## 4. Что Protobuf не делает

Protobuf сам:

- не открывает TCP-соединение;
- не знает IP-адрес и порт;
- не создаёт HTTP-запрос;
- не выбирает Kafka topic;
- не шифрует данные;
- не сжимает данные;
- не определяет права доступа;
- не проверяет бизнес-правила;
- не определяет границы сообщений в TCP-потоке.

## 5. Роль транспорта

```text
Python User
   ↓ Protobuf
bytes
   ↓ HTTP / TCP / Kafka / gRPC
bytes
   ↓ Protobuf другого языка
Java User / Go User / Python User
```

| Технология | За что отвечает |
|---|---|
| Protobuf | Представление данных |
| TCP | Надёжный поток байтов |
| HTTP | Запросы, ответы, маршруты и заголовки |
| Kafka | Хранение и доставка событий |
| gRPC | RPC-вызовы, HTTP/2, framing и статусы |
| TLS | Шифрование транспортного соединения |

## 6. Protobuf-класс — не `dataclass`

В Python объект выглядит похоже на типизированную структуру:

```python
user = user_pb2.User(id=1, name="Alex")
```

Но это не обычный `dataclass`. Он:

- наследуется от `google.protobuf.message.Message`;
- создаётся на основе дескриптора схемы;
- не разрешает произвольные поля;
- использует специальные контейнеры;
- имеет встроенные методы сериализации;
- по-особому работает с presence и вложенными сообщениями.

## 7. Межъязыковое взаимодействие

Одна схема:

```proto
message User {
  int64 id = 1;
  string name = 2;
}
```

может породить:

```text
Python-класс User
Java-класс User
Go-структуру User
C++-класс User
```

Синтаксис классов разный, но бинарный контракт общий.

## 8. Нужна ли идентичная схема

Лучше всего все сервисы используют один версионируемый источник `.proto`.

Однако схемы могут иметь разные совместимые версии.

Старый получатель:

```proto
message User {
  int64 id = 1;
  string name = 2;
}
```

Новый отправитель:

```proto
message User {
  int64 id = 1;
  string name = 2;
  string email = 3;
}
```

Старый сервис прочитает известные поля `1` и `2`. Поле `3` для него неизвестно.

Нельзя менять существующий контракт:

```proto
// Было
int64 id = 1;

// Стало
string email = 1;
```

## 9. Где Protobuf применяется

- gRPC;
- Kafka и другие брокеры сообщений;
- межсервисное взаимодействие;
- мобильные клиенты;
- event-driven системы;
- хранение небольших структурированных записей;
- конфигурационные и служебные данные;
- события и команды.

## 10. Где он неудобен

- документы, которые должны редактировать люди;
- публичные API без клиентских библиотек;
- полностью динамические структуры;
- хранение больших видео и файлов внутри сообщения;
- аналитические таблицы, которые нужно читать SQL-запросами напрямую;
- случаи, где невозможно распространить схему.
