## 1. Что хранится в бинарном сообщении

Схема:

```proto
message User {
  int64 id = 1;
  string name = 2;
  string email = 3;
}
```

Объект:

```python
user = User(
    id=150,
    name="Ann",
    email="a@b",
)
```

Байты могут выглядеть так:

```text
08 96 01 12 03 41 6e 6e 1a 03 61 40 62
```

В payload обычно нет строк:

```text
User
id
name
email
int64
string
```

Там находятся:

- номера полей;
- wire types;
- длины;
- значения.

Поэтому получателю нужна совместимая схема.

## 2. Ключ поля

Каждое поле кодируется как:

```text
ключ + значение
```

Ключ:

```text
key = (field_number << 3) | wire_type
```

Младшие три бита содержат wire type, остальные — номер поля.

## 3. Основные wire types

| Wire type | Кодирование | Типы |
|---:|---|---|
| `0` | Varint | int, uint, sint, bool, enum |
| `1` | 64-bit | fixed64, sfixed64, double |
| `2` | Length-delimited | string, bytes, message, packed repeated |
| `5` | 32-bit | fixed32, sfixed32, float |

Wire types `3` и `4` исторически использовались для groups.

## 4. Разбор `id = 150`

```proto
int64 id = 1;
```

Номер поля:

```text
1
```

Wire type для `int64`:

```text
0
```

Ключ:

```text
(1 << 3) | 0 = 8 = 0x08
```

Значение `150` кодируется varint:

```text
96 01
```

Поле целиком:

```text
08 96 01
```

## 5. Varint

Varint разбивает число на группы по 7 бит.

У каждого байта:

- 7 младших бит содержат данные;
- старший бит показывает, есть ли продолжение.

Небольшие числа занимают мало байт.

Пример:

```text
1   → 01
127 → 7f
128 → 80 01
150 → 96 01
```

Обычные отрицательные `int32` и `int64` кодируются неэффективно. Для них лучше `sint32` и `sint64`.

## 6. ZigZag

Используется `sint32` и `sint64`.

Условное отображение:

```text
 0 → 0
-1 → 1
 1 → 2
-2 → 3
 2 → 4
```

После этого результат кодируется varint.

## 7. Разбор строки

```proto
string name = 2;
```

Wire type:

```text
2
```

Ключ:

```text
(2 << 3) | 2 = 18 = 0x12
```

`"Ann"` в UTF-8:

```text
41 6e 6e
```

Длина:

```text
03
```

Поле:

```text
12 03 41 6e 6e
```

Структура length-delimited:

```text
ключ | длина | содержимое
```

## 8. Вложенное сообщение

```proto
message Address {
  string city = 1;
}

message User {
  Address address = 3;
}
```

Вложенное сообщение:

1. сериализуется отдельно;
2. его размер записывается как длина;
3. байты помещаются в поле wire type `2`.

```text
ключ address
длина вложенного payload
байты Address
```

## 9. Repeated-поля

### Непакованное представление

Номер поля повторяется для каждого значения:

```text
field=value1
field=value2
field=value3
```

### Packed-представление

Для чисел:

```text
ключ
общая длина
value1 value2 value3
```

В proto3 packed обычно включён по умолчанию для подходящих repeated scalar-полей.

## 10. Почему default-значения часто отсутствуют

```proto
message User {
  int64 id = 1;
  string name = 2;
}
```

```python
user = User(id=0, name="")
payload = user.SerializeToString()
```

Для implicit scalar-полей default-значения обычно не записываются:

```python
payload == b""
```

Это уменьшает размер, но создаёт неоднозначность между отсутствием и явным default. Для presence используйте `optional`.

## 11. Порядок полей

Декодер не обязан получать поля в порядке их объявления.

Корректны оба варианта:

```text
поле 1, поле 2, поле 3
```

и:

```text
поле 3, поле 1, поле 2
```

На порядок сериализованных полей нельзя полагаться как на постоянный контракт.

## 12. Unknown fields

Если декодер встречает незнакомый номер поля, он может определить его длину по wire type и пропустить.

Именно поэтому новая схема может добавлять поля, не ломая старую.

## 13. Сообщение не содержит тип

Байты сами по себе обычно не сообщают:

```text
это company.users.v1.User
```

Внешний протокол должен определить ожидаемый тип:

- URL HTTP;
- RPC-метод gRPC;
- Kafka topic;
- отдельный type field;
- envelope;
- заранее согласованный канал.

## 14. Protobuf не является self-delimiting

Если записать подряд:

```text
message1 bytes + message2 bytes
```

получатель не знает, где закончился первый объект.

Нужен framing:

```text
длина1 + message1 + длина2 + message2
```

Или транспорт, который уже хранит границы сообщений:

- HTTP body;
- Kafka record;
- gRPC frame;
- отдельный файл на сообщение.

## 15. Детерминированная сериализация

```python
message.SerializeToString(
    deterministic=True,
)
```

Может стабилизировать порядок в рамках конкретной реализации, но не гарантирует вечное каноническое бинарное представление между:

- разными языками;
- разными runtime;
- разными версиями;
- изменёнными схемами.

Не следует строить долговечный криптографический контракт на сырых сериализованных байтах без собственного канонического формата.

## 16. Полезные команды анализа

Вывод hex:

```python
print(payload.hex(" "))
```

Декодирование без схемы:

```bash
protoc --decode_raw < message.bin
```

Декодирование со схемой:

```bash
protoc \
  --decode=demo.v1.User \
  user.proto \
  < message.bin
```

Сохранение:

```python
from pathlib import Path

Path("user.bin").write_bytes(payload)
```
