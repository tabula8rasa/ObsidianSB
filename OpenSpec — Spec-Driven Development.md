**OpenSpec** — инструмент для разработки по спецификациям (Spec-Driven Development, SDD). Позволяет сначала определить требования, архитектуру и задачи, а затем реализовать их с помощью AI-агентов.

**Основной принцип:** Specification → Implementation → Verification.

## 1. Структура проекта

- `docs/` — исходная документация проекта.
    
- `openspec/config.yaml` — контекст и правила проекта.
    
- `openspec/specs/` — актуальные утверждённые требования системы.
    
- `openspec/changes/` — планируемые и разрабатываемые изменения.
    
- `.agents/skills/` — навыки OpenSpec для AI-агентов.
    
- `AGENTS.md` — общие инструкции Codex.
    

## 2. Change — единица разработки

**Change** — отдельное функциональное изменение с полным циклом разработки.

Содержит четыре основных артефакта:

|Файл|Назначение|
|---|---|
|`proposal.md`|Зачем и что изменяем|
|`specs/*/spec.md`|Функциональные требования и сценарии|
|`design.md`|Архитектура и технические решения|
|`tasks.md`|Задачи для реализации|

После завершения Change архивируется, а его требования синхронизируются с `openspec/specs/`.

## 3. Основные Skills

|Skill|Назначение|
|---|---|
|`$openspec-explore`|Исследование проблемы и решений|
|`$openspec-propose`|Создание Change со всеми документами|
|`$openspec-update-change`|Корректировка документов Change|
|`$openspec-apply-change`|Реализация задач и написание кода|
|`$openspec-sync-specs`|Синхронизация требований|
|`$openspec-archive-change`|Завершение и архивирование Change|
|`$openspec-verify-change`|Проверка реализации (дополнительный Skill)|

## 4. Рабочий процесс

1. **Explore** — исследовать требования и архитектуру.
    
2. **Propose** — создать Change.
    
3. **Review** — проверить спецификации и задачи.
    
4. **Apply** — реализовать функциональность.
    
5. **Test & Verify** — проверить код, тесты и соответствие требованиям.
    
6. **Archive** — завершить Change и обновить основные спецификации.
    

## 5. CLI-команды

- `npm install -g @fission-ai/openspec@latest` — установка.
    
- `openspec init --tools codex` — инициализация проекта.
    
- `openspec status --change <name>` — статус Change.
    
- `openspec validate <name> --strict` — проверка спецификаций.
    
- `openspec instructions apply --change <name>` — инструкции реализации.
    
- `openspec config profile` — настройка доступных Skills.
    
- `openspec update` — обновление интеграций и Skills.
    

## 6. Интеграция с Multi-Agent Codex

OpenSpec определяет **что разрабатывать**, Codex — **как организовать исполнение**.

Роли агентов задаются через `.codex/agents/*.toml`.

Пример workflow:

**Master → Developers (параллельно) → Tester → Reviewer → Master**

- Master — оркестрация и управление задачами.
    
- Developers — реализация независимых компонентов.
    
- Tester — автоматизированное и интеграционное тестирование.
    
- Reviewer — независимая проверка качества и соответствия спецификациям.
    

Правила взаимодействия и последовательность этапов фиксируются в `AGENTS.md` либо отдельном orchestration Skill.

## 7. Ключевые правила

- Один Change — одна логически завершённая функциональность.
    
- Не начинать реализацию до согласования спецификаций.
    
- Требования должны быть проверяемыми (SHALL + сценарии).
    
- Изменения требований отражать в OpenSpec, а не только в коде.
    
- Отмечать задачи завершёнными только после проверки.
    
- Архивировать Change после реализации и верификации.
    

**OpenSpec ≠ Git.** Change описывает логическое изменение, Git сохраняет историю кода.
