## Краткая суть

Статья описывает практический кейс Авито по борьбе с bloat в PostgreSQL, когда стандартные инструменты вроде `VACUUM FULL`, `CLUSTER`, `pg_repack` и `pgcompacttable` не подходили из-за риска downtime, эксклюзивных блокировок, нехватки места или отсутствия поддержки со стороны DBA.

Команда столкнулась с деградацией главного сервиса платформы отправлений: страницы заказов с доставкой загружались медленно, возникали провалы в работе, были проблемы с созданием новых заказов. После анализа выяснилось, что на ситуацию повлияли рост нагрузки, увеличение времени выполнения запросов, проблемы с коннектами и ночная архивация, которая переносила данные в холодное хранилище и удаляла их из горячего PostgreSQL-хранилища. Это усилило bloat в таблицах и индексах.

## Основная идея решения

Идея решения: создать новую таблицу, перенести в неё данные из старой, поменять таблицы местами через переименование, а затем удалить старую таблицу. При таком переносе bloat из старой таблицы не переносится в новую.

Однако команда обнаружила, что B-tree индексы в новой таблице всё равно могут получить bloat при копировании данных. Поэтому после переключения таблиц было решено выполнять `REINDEX`. Также команда анализировала использование индексов и удаляла те, которые не использовались.

## Алгоритм

### 1. Создание таблицы-реплики и триггеров

![[Pasted image 20260709140715.png]]

Сначала создаётся таблица-реплика. На исходную таблицу навешиваются триггеры на вставку, обновление и удаление. Они нужны, чтобы все изменения после момента **T** запуска переноса попадали и в исходную таблицу, и в таблицу-реплику.

Для вставок и обновлений используется логика upsert: если записи в реплике ещё нет, она вставляется; если запись уже есть, она обновляется через `ON CONFLICT DO UPDATE`.

Для удалений создаётся отдельный триггер, который удаляет соответствующую строку из таблицы-реплики.

``` sql
-- 1. Пытаемся вставить строку в table_replica, если не получилось - обновляем
CREATE OR REPLACE FUNCTION upsert_table_replica()
    RETURNS TRIGGER AS $$
BEGIN
    -- Вставка записи в table_replica с обновлением в случае конфликта по id
    INSERT INTO table_replica (id, field_1, ...)
    VALUES (NEW.id, NEW.field_1, ...)
    ON CONFLICT (id)
        DO UPDATE SET
        	field_1 = EXCLUDED.field_1,
		...
RETURN NULL;
END;
$$ LANGUAGE plpgsql;

-- 2. Создаем триггер типа AFTER на создание и обновление строк в table
CREATE TRIGGER trigger_upsert_table
    AFTER INSERT OR UPDATE ON table
    FOR EACH ROW
EXECUTE FUNCTION upsert_table_replica();

-- 3. Создаем триггер на удаление для таблицы table
CREATE OR REPLACE FUNCTION delete_table_replica()
    RETURNS TRIGGER AS $$
BEGIN
    -- Удаление записи из table_replica по id
    DELETE FROM table_replica
    WHERE id = OLD.id;


    RETURN NULL; 
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trigger_delete_table
    AFTER DELETE ON table
    FOR EACH ROW
EXECUTE FUNCTION delete_table_replica();
```

**Здесь также важно поговорить о времени работы.** Триггеры — неотъемлемые части операций вставки и обновления. Это значит, что время работы операций с основной таблицей увеличивается. Если говорить о блокировках на таблицах, то здесь они берутся классические, как и при обычной вставке.

Блокировки в таблице-реплике тоже будут браться симметричные строкам в основной таблице. Этот факт означает, что не возникнет ситуации, когда взяты несколько блокировок в исходной таблице при разных операциях и при этом они борются за блокировку какой-то одной строки в таблице-реплике. Из этого делаем вывод, что блокировки на таблице-реплике не приводят к увеличению времени работы сервиса, для которого чистится bloat. 

### 2. Батчевый перенос данных
![[Pasted image 20260709141808.png]]

После настройки триггеров данные из исходной таблицы переносятся в таблицу-реплику батчами. Для этого используется самописный дубликатор на основе CTE-запроса. Он переносит данные порциями и запоминает последний обработанный идентификатор.

Во время переноса используется `FOR UPDATE`, чтобы в момент копирования с выбранными строками не происходили конфликтующие изменения.

``` sql
drop function if exists copy_rows_from_table(size integer);
create or replace function copy_rows_from_table(size integer) returns bool as $$
declare
    all_duplicated bool;
begin
    with batch as (
        select
            ...
        from table as ts
        where ts.id > (select last_id from dup_id) and ts.id < (select max_id from dup_id)
        order by ts.id asc
        limit size
        for update -- чтобы в момент переноса ничего не происходило со строками из батча
    ), duplicated as (
        insert into table_replica select ... from batch on conflict(id) do nothing
    ), duplication_offset as (
        -- Запоминаем последний id из батча
        -- если в батче для переноса ничего нет, то оставляем текущий id
        update dup_ids set last_id = COALESCE((select max(id) from batch), last_id)
    )
    --  Запрос необходимо повторять до тех пор, пока значение all_done не станет true
    -- если в батче переноса ничего нет, то продолжать нет смысла
    select count(*)::integer = 0 as all_done into all_duplicated from batch; 
    return all_duplicated;
end;
$$ language plpgsql;
```

### 3. Перестановка таблиц

Когда данные перенесены и актуальность проверена, исходная таблица переименовывается во временную, а таблица-реплика получает имя исходной таблицы. Эта операция требует `ACCESS EXCLUSIVE LOCK`, поэтому её выполняют в период низкой нагрузки.

Также нужно учитывать sequence: старая таблица может оставаться владельцем генератора последовательности. Поэтому после переименования требуется изменить владельца sequence, иначе старую таблицу не получится удалить.

### 4. Работа с внешними ключами

Перед переключением нужно обработать внешние ключи. Если этого не сделать, они могут продолжить ссылаться на переименованную старую таблицу, а запись уже будет идти в новую. Это приведёт к ошибкам записи и поломке сервиса.

Удаление внешних ключей тоже требует кратковременной эксклюзивной блокировки двух таблиц, поэтому такие операции выполнялись в период низкой нагрузки.

### 5. REINDEX и удаление неиспользуемых индексов

После перестановки таблиц выполняется `REINDEX`, потому что B-tree индексы могли накопить bloat во время дублирования данных.

Дополнительно команда проверяла статистику использования индексов через `pg_stat_user_indexes`. Индексы с нулевыми значениями `idx_scan`, `idx_tup_read` и `idx_tup_fetch` рассматривались как неиспользуемые, но перед удалением требовалась дополнительная проверка: когда индекс был создан, почему он не используется, может ли он понадобиться позже и используется ли он на репликах.

## Важные технические нюансы

Перед критическим переключением команда:

- создавала таблицу-реплику;
    
- навешивала триггеры;
    
- прогоняла дубликатор;
    
- проверяла актуальность данных;
    
- тестировала переключение на тестовом окружении.
    

Во время критических операций могли мешать процессы автовакуума, потому что они могли не дать взять эксклюзивную блокировку. Поэтому команда учитывала возможность временного отключения автовакуума.

Также во время `REINDEX` могла возникать деградация сервиса из-за большого количества операций записи. Опция `CONCURRENTLY` в этом случае не помогала, поэтому при наличии лимитов на WIOPS нужно было заранее учитывать нагрузку.

## Итоги кейса

Весь процесс занял около трёх месяцев. За это время команда обработала внешние ключи, реиндексы и лишние индексы, а затем в полуавтоматическом режиме применяла процесс к нужным таблицам.

Результаты:

- было освобождено около 50% места на сервере;
    
- SR поиска составил примерно 99,99%;
    
- SR создания составил 100%;
    
- 99,99% времени сервис стал отвечать без ошибок;
    
- аналогичная проблема после этого больше не возникала;
    
- удалось сохранить работоспособность сервиса без downtime.
    

## Выводы по bloat

Bloat действительно ухудшает состояние базы данных, но проблемы из-за него обычно накапливаются постепенно. Само наличие bloat не всегда означает немедленную аварию: даже при bloat больше 50% база может работать приемлемо, если производительность устраивает.

Команда сделала вывод, что очистка bloat помогла базе данных и позволила продолжить архивацию, но уже в более щадящем режиме, распределяя нагрузку на большее время.

## Правила массового переноса и удаления данных

Авторы сформулировали два практических правила:

1. Лучше в два раза увеличить батч, чем в два раза уменьшить таймаут (1000 записей за 2 секунды лучше, чем 500 записей за 1 секунду).
    
2. Более продолжительная дополнительная нагрузка лучше, чем менее продолжительная (3М записей за 8 часов лучше, чем 3М записей за 3 часа).

То есть при массовом переносе или удалении данных важнее не выполнить операцию максимально быстро, а не создать резкий пик нагрузки на базу данных.

## Возможная оптимизация алгоритма

В качестве дальнейшего улучшения авторы предлагают партицирование. Вместо периодического повторения алгоритма для отдельных таблиц можно один раз перенести данные в новую партицированную таблицу, проверить корректность, переключить таблицы, а затем автоматизировать создание новых партиций и очистку пустых. В таком варианте очистка bloat становится менее болезненной и более управляемой.
