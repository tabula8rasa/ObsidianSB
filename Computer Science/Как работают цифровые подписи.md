## Что такое цифровая подпись

**Цифровая подпись** — это криптографический механизм, который позволяет проверить:

1. **Целостность** — документ не изменился после подписания.
2. **Подлинность** — подпись создана владельцем соответствующего закрытого ключа.
3. **Авторство** — при наличии доверенного сертификата можно связать открытый ключ с конкретным человеком или организацией.

Цифровая подпись создаётся с помощью пары связанных ключей:

- **закрытый ключ** — хранится только у владельца и используется для создания подписи;
- **открытый ключ** — доступен другим людям и используется для проверки подписи.
---

## Основные элементы

| Элемент | Назначение |
|---|---|
| Исходный документ | Файл или данные, которые необходимо подписать |
| Хэш-функция | Создаёт короткий цифровой отпечаток документа |
| Хэш | Результат работы хэш-функции |
| Закрытый ключ | Используется владельцем для создания подписи |
| Открытый ключ | Используется получателем для проверки подписи |
| Цифровая подпись | Криптографическое значение, связанное с документом и закрытым ключом |
| Сертификат | Подтверждает, кому принадлежит открытый ключ |

---

# Этап 1. Создание цифровой подписи

## Шаг 1. Подготовка исходного документа

Отправитель выбирает документ, который необходимо подписать.

Это может быть:

- PDF-файл;
- договор;
- электронное письмо;
- архив;
- исполняемый файл;
- запрос к серверу;
- любой другой набор цифровых данных.

Сам документ обычно не шифруется и может оставаться доступным для чтения.

---

## Шаг 2. Вычисление хэша документа

Документ передаётся в хэш-функцию, например **SHA-256**:

```text
Документ → SHA-256 → Хэш документа
```

Хэш — это значение фиксированной длины, которое представляет содержимое документа.

Условный пример:

```text
Документ:
Договор №15

Хэш:
4f8a1c7e...
```

Если изменить даже один символ:

```text
Договор №15
```

на:

```text
Договор №16
```

будет получен совершенно другой хэш.

### Свойства криптографического хэша

- одинаковые данные дают одинаковый хэш;
- небольшое изменение данных сильно меняет хэш;
- по хэшу практически невозможно восстановить исходный документ;
- крайне сложно найти два разных документа с одинаковым хэшем.

---

## Шаг 3. Создание подписи закрытым ключом

Полученный хэш обрабатывается алгоритмом цифровой подписи с использованием **закрытого ключа отправителя**:

```text
Хэш документа + закрытый ключ → цифровая подпись
```

На схемах этот процесс часто называют:

```text
«Шифрование хэша закрытым ключом»
```

Это допустимое упрощение, но технически не все алгоритмы подписи работают как обычное шифрование.

Например, современные алгоритмы **RSA-PSS**, **ECDSA** и **EdDSA** используют специальные математические операции создания и проверки подписи.

---

## Шаг 4. Формирование пакета для отправки

После создания подписи отправитель формирует пакет:

```text
Исходный документ
+
Цифровая подпись
```

Дополнительно к нему могут прикладываться:

- сертификат открытого ключа;
- информация об алгоритме подписи;
- отметка времени;
- цепочка сертификатов;
- служебные данные.

Цифровая подпись может храниться:

- внутри самого документа;
- в отдельном файле;
- в специальном контейнере вместе с документом.

---

## Шаг 5. Передача по сети

Документ и подпись отправляются получателю:

```text
Документ + подпись → сеть → получатель
```

Во время передачи злоумышленник теоретически может изменить документ. Однако после изменения подпись перестанет успешно проверяться.

При этом цифровая подпись сама по себе **не скрывает содержимое документа**. Для конфиденциальности необходимо отдельное шифрование.

---

# Этап 2. Проверка цифровой подписи

## Шаг 6. Получение документа и подписи

Получатель получает:

```text
Документ
+
Цифровую подпись
```

Также ему необходим открытый ключ отправителя или сертификат, содержащий этот ключ.

---

## Шаг 7. Вычисление нового хэша

Получатель самостоятельно пропускает полученный документ через ту же хэш-функцию:

```text
Полученный документ → SHA-256 → вычисленный хэш
```

Этот хэш отражает текущее содержимое полученного документа.

Если документ был изменён во время передачи, вычисленный хэш будет отличаться от хэша исходного документа.

---

## Шаг 8. Проверка подписи открытым ключом

Получатель использует **открытый ключ отправителя**, чтобы проверить цифровую подпись.

Упрощённо этот процесс изображают так:

```text
Цифровая подпись + открытый ключ → исходный хэш
```

Однако точнее говорить:

```text
Подпись + открытый ключ + хэш документа → результат проверки
```

Алгоритм устанавливает, могла ли эта подпись быть создана соответствующим закрытым ключом для конкретного документа.

---

## Шаг 9. Сравнение результатов

Проверяется соответствие подписи вычисленному хэшу документа.

### Подпись действительна

```text
Хэш документа соответствует подписи
```

Это означает:

- документ не изменился после подписания;
- подпись была создана закрытым ключом, соответствующим открытому ключу;
- данные не были незаметно подменены.

### Подпись недействительна

```text
Хэш документа не соответствует подписи
```

Возможные причины:

- документ изменили после подписания;
- подпись была повреждена;
- используется неправильный открытый ключ;
- подпись относится к другому документу;
- данные были некорректно переданы;
- подпись была создана другим закрытым ключом.

---

# Общая схема

```text
ОТПРАВИТЕЛЬ

1. Исходный документ
        ↓
2. Вычисление хэша
        ↓
3. Создание подписи закрытым ключом
        ↓
4. Документ + цифровая подпись
        ↓
5. Передача по сети


ПОЛУЧАТЕЛЬ

6. Получение документа и подписи
        ↓
7. Вычисление хэша полученного документа
        ↓
8. Проверка подписи открытым ключом
        ↓
9. Сравнение результатов
        ↓
Подпись действительна или недействительна
```
