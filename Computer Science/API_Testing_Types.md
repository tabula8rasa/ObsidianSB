# Виды тестирования API

API можно проверять на разных уровнях: от простого ответа сервиса до нагрузки, безопасности и устойчивости к некорректным данным.

Ниже — 9 основных видов тестирования API.

---

## 1. Smoke Testing

**Smoke testing** — быстрая проверка того, что API вообще работает и основные endpoint'ы доступны.

Обычно проверяют:

- сервис запускается;
- критические endpoint'ы отвечают;
- нет очевидных `5xx` ошибок;
- базовые зависимости доступны.

Пример:

```http
GET /health
```

Ожидаемый ответ:

```http
200 OK
```

Главный вопрос:

> API вообще жив и способен обрабатывать базовые запросы?

Smoke-тесты обычно запускаются первыми после деплоя.

---

## 2. Functional Testing

**Functional testing** проверяет, правильно ли API выполняет бизнес-логику согласно требованиям.

Проверяется не только HTTP status code, но и содержимое ответа.

Например:

```http
POST /orders
```

Нужно проверить:

- правильно ли рассчитана итоговая стоимость;
- применена ли скидка;
- правильно ли рассчитан налог;
- корректный ли статус заказа;
- сохранены ли нужные данные.

Схема:

```text
Request
   ↓
API
   ↓
Actual Response
   ↓
сравнение
   ↓
Expected Result
```

Главный вопрос:

> Делает ли endpoint именно то, что должен?

---

## 3. Contract Testing

**Contract testing** проверяет соответствие API заранее определённому контракту.

Контракт может описывать:

- endpoint'ы;
- HTTP-методы;
- поля request;
- поля response;
- типы данных;
- обязательные поля;
- допустимые ошибки;
- статус-коды.

Например:

```http
GET /products/{id}
```

Контракт ожидает:

```json
{
  "id": 123,
  "name": "Keyboard",
  "price": 100
}
```

Тест проверяет, что API внезапно не начал возвращать несовместимую структуру.

Контракт может быть описан через:

```text
OpenAPI
Protobuf
Avro Schema
Thrift IDL
JSON Schema
```

Главный вопрос:

> Соответствуют ли request и response договорённости между consumer и provider?

---

## 4. Integration Testing

**Integration testing** проверяет взаимодействие нескольких сервисов и компонентов.

Например создание заказа может выглядеть так:

```text
Client
  ↓
Order API
  ↓
Inventory API
  ↓
Payment API
  ↓
Notification API
```

Тест может проверить, что после:

```http
POST /orders
```

произошло всё необходимое:

```text
товар зарезервирован
↓
платёж подтверждён
↓
заказ сохранён
↓
уведомление отправлено
```

Главный вопрос:

> Правильно ли несколько систем работают вместе?

---

## 5. Regression Testing

**Regression testing** проверяет, что после изменений старая функциональность продолжает работать.

Например разработчик добавил новую систему скидок:

```text
v1
↓
изменение логики скидок
↓
v2
```

После этого нужно повторно проверить:

```text
создание заказа
оплату
возвраты
историю заказов
расчёт стоимости
```

Даже если эти части напрямую не изменялись.

Обычно для этого существует набор автоматизированных тестов:

```text
Regression Suite
```

Главный вопрос:

> Не сломали ли новые изменения то, что раньше уже работало?

---

## 6. Load Testing

**Load testing** проверяет работу API под ожидаемой или высокой, но реалистичной нагрузкой.

Например:

```text
1000 одновременных пользователей
```

или:

```text
5000 requests/sec
```

Для генерации нагрузки могут использоваться:

```text
k6
JMeter
Gatling
Locust
```

Измеряют:

- latency;
- throughput;
- requests/sec;
- error rate;
- CPU;
- RAM;
- использование БД и других зависимостей.

Часто смотрят не только среднее время ответа, но и percentiles:

```text
p50
p95
p99
```

Например:

```text
p95 latency < 300 ms
error rate < 1%
```

Главный вопрос:

> Справляется ли API с ожидаемым количеством запросов?

---

## 7. Stress Testing

**Stress testing** похож на load testing, но нагрузку намеренно увеличивают выше нормальной.

Например:

```text
1000 req/s
↓
3000 req/s
↓
5000 req/s
↓
10000 req/s
↓
...
```

Пока система не начнёт деградировать.

Могут появиться:

```text
429 Too Many Requests
timeouts
5xx
рост latency
исчерпание connection pool
перегрузка CPU/RAM
```

Цель — найти:

```text
breaking point
```

Также важно проверить, ломается ли система полностью или деградирует контролируемо.

Главный вопрос:

> Где предел API и как оно ведёт себя после превышения этого предела?

---

## 8. Security Testing

**Security testing** проверяет защищённость API.

Проверяются:

- authentication;
- authorization;
- access control;
- обработка пользовательского ввода;
- утечки данных;
- работа токенов;
- права разных пользователей;
- injection-атаки;
- неправильный доступ к чужим ресурсам.

Например:

```text
User A
↓
GET /users/B/orders
```

Если пользователь `A` не имеет права видеть заказы пользователя `B`, API должно вернуть, например:

```http
403 Forbidden
```

Главный вопрос:

> Может ли пользователь получить или изменить то, к чему у него не должно быть доступа?

---

## 9. Fuzz Testing

**Fuzz testing** — отправка большого количества необычных, случайных или намеренно некорректных входных данных.

Например:

```json
{}
```

или:

```json
{
  "quantity": -1
}
```

или огромные строки и повреждённые структуры.

Также можно отправлять:

```text
сломанный JSON
неожиданные типы
очень большие числа
пустые значения
случайные bytes
вложенные структуры огромной глубины
```

API при таких запросах не должно:

```text
падать
зависать
утекать памятью
раскрывать внутренние данные
выполнять небезопасные действия
```

Главный вопрос:

> Что произойдёт, если API получит неожиданные или специально повреждённые данные?

---

# Load Testing vs Stress Testing

Эти два вида часто путают.

### Load Testing

Проверяет работу при **ожидаемой нагрузке**.

```text
Нормальная production-нагрузка
          ↓
         API
          ↓
 latency и error rate в пределах SLA?
```

### Stress Testing

Идёт дальше ожидаемой нагрузки:

```text
normal
↓
high
↓
very high
↓
extreme
↓
breaking point
```

То есть:

```text
Load Testing
=
выдерживаем ли нормальную нагрузку?

Stress Testing
=
где мы сломаемся?
```

---

# Smoke vs Functional vs Integration

```text
Smoke
↓
работает ли API вообще?

Functional
↓
правильно ли работает конкретный endpoint?

Integration
↓
правильно ли вместе работают несколько систем?
```

Например для:

```http
POST /orders
```

### Smoke

```text
POST /orders отвечает и не падает с 500
```

### Functional

```text
цена, скидка, налог и статус рассчитаны правильно
```

### Integration

```text
Order API
↓
Inventory
↓
Payment
↓
Notification

весь workflow завершился успешно
```

# Общая схема

```text
API Testing

├── Smoke
│   └── API вообще доступно?
│
├── Functional
│   └── бизнес-логика правильная?
│
├── Contract
│   └── API соответствует контракту?
│
├── Integration
│   └── сервисы правильно работают вместе?
│
├── Regression
│   └── новые изменения не сломали старое?
│
├── Load
│   └── выдерживаем ожидаемую нагрузку?
│
├── Stress
│   └── где предел системы?
│
├── Security
│   └── API защищено?
│
└── Fuzz
    └── что будет при неожиданных данных?
```

# Краткая таблица

| Тип | Что проверяет |
|---|---|
| **Smoke** | Базовую доступность API |
| **Functional** | Корректность бизнес-логики |
| **Contract** | Соответствие API-контракту |
| **Integration** | Взаимодействие сервисов |
| **Regression** | Что изменения не сломали существующее поведение |
| **Load** | Производительность под ожидаемой нагрузкой |
| **Stress** | Поведение при экстремальной нагрузке |
| **Security** | Авторизацию, доступ и защищённость |
| **Fuzz** | Устойчивость к неожиданным и некорректным данным |
