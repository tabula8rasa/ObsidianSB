## Что такое TCP

TCP — транспортный протокол, который предоставляет приложению **надёжный, упорядоченный, двунаправленный поток байтов**.

TCP не знает, что передаваемые данные являются:

- HTTP-запросом;
- JSON;
- изображением;
- файлом;
- строкой;
- protobuf-сообщением.

Для TCP всё это просто последовательность байтов.

```text
Application
    ↓
TCP
    ↓
IP
```

---

## TCP — это поток, а не протокол сообщений

Если приложение вызвало:

```python
sock.send(b"HELLO")
sock.send(b"WORLD")
```

получатель не обязан увидеть:

```python
recv() -> b"HELLO"
recv() -> b"WORLD"
```

Он может увидеть:

```python
recv() -> b"HEL"
recv() -> b"LOWORLD"
```

или:

```python
recv() -> b"HELLOWORLD"
```

TCP сохраняет **порядок байтов**, но не сохраняет границы вызовов `send()`.

Поэтому любой протокол сообщений поверх TCP должен самостоятельно определить, где заканчивается одно сообщение и начинается другое. Это называется **framing**. Подробнее: [[05 HTTP framing - как определяется конец сообщения]].

# TCP Sequence Numbers

TCP нумерует не HTTP-запросы и даже не сами TCP-сегменты, а **байты потока**.

Для простоты можно представить поток:

```text
0-999
1000-1999
2000-2999
3000-3999
4000-4999
...
```

Если один HTTP-запрос занимает первые 3000 байт, а второй следующие 2000, TCP всё равно видит просто:

```text
0 ------------------------------------ 4999
```

А HTTP уже интерпретирует:

```text
0-2999       → HTTP message 1
3000-4999    → HTTP message 2
```

TCP не знает, где заканчивается первый запрос.

## Sequence Numbers продолжаются всё время жизни соединения

Пока существует одно TCP-соединение, sequence numbers относятся к одному непрерывному потоку.

Условно:

```text
HTTP request 1 → bytes 1000-2499
HTTP request 2 → bytes 2500-3999
HTTP request 3 → bytes 4000-6199
```

Для TCP:

```text
1000 1001 1002 ... 6199
```

Новый HTTP-запрос не обнуляет TCP sequence number.

В реальности sequence number 32-битный и может переполниться, поэтому арифметика TCP работает по модулю `2^32`.

---

## Initial Sequence Number

TCP обычно не начинает нумерацию с нуля.

При создании соединения каждая сторона выбирает собственный **Initial Sequence Number (ISN)**.

Например:

```text
Client ISN = 1 923 000 000
Server ISN =   817 000 000
```

После этого клиент и сервер имеют независимые последовательности номеров байтов.

---

# TCP full-duplex

TCP — двунаправленный протокол.

В одном TCP-соединении существуют два независимых потока:

```text
CLIENT                                SERVER

Seq(client): 1000, 1001, 1002...
------------------------------------->

              Seq(server): 7000, 7001, 7002...
<-------------------------------------
```

То есть sequence numbers клиента и сервера независимы.

---

# TCP не ждёт ACK после каждого сегмента

Неверная модель:

```text
send segment 1
wait ACK

send segment 2
wait ACK

send segment 3
wait ACK
```

Так TCP был бы крайне медленным.

TCP использует **скользящее окно (sliding window)** и может иметь одновременно множество неподтверждённых байтов «в полёте».

```text
segment 1  ------------------------>
segment 2  ------------------------>
segment 3  ------------------------>
segment 4  ------------------------>
segment 5  ------------------------>

             <---------------- ACK
```

Сколько данных разрешено отправить без ожидания, определяется прежде всего:

- `rwnd` — receive window, сколько данных способен принять получатель;
- `cwnd` — congestion window, сколько данных отправитель считает безопасным держать в сети.

Упрощённо:

```text
send window ≈ min(rwnd, cwnd)
```

---

# Как TCP понимает, что данные доставлены

TCP использует подтверждения — **ACK**.

Упрощённо, если получатель отправляет:

```text
ACK = 3000
```

это означает:

> непрерывно получены все байты до 2999, следующим ожидаю байт 3000.

Это называется cumulative acknowledgement.

---

# Как TCP обнаруживает потерю

Допустим отправлено:

```text
0-999       ✓
1000-1999   ✓
2000-2999   X
3000-3999   ✓
4000-4999   ✓
```

Получатель видит дыру.

Он всё ещё ожидает байт `2000`, поэтому подтверждение непрерывной части остаётся около:

```text
ACK = 2000
```

Современный TCP также обычно использует **SACK — Selective Acknowledgement**.

С помощью SACK получатель может сообщить:

```text
непрерывно есть всё до 1999
3000-4999 тоже уже получено
но 2000-2999 отсутствует
```

Отправитель понимает, что необходимо повторно передать пропавший диапазон.

TCP также использует таймеры retransmission. Если подтверждение не приходит достаточно долго, данные отправляются повторно.

---

# Что происходит, если середина потока потерялась

Допустим пришло:

```text
1 ✓
2 ✓
3 X
4 ✓
5 ✓
6 ✓
```

Данные `4-6` действительно могут физически находиться на компьютере получателя.

Ядро ОС сохраняет их в буфере соответствующего TCP-соединения.

```text
TCP receive buffer:

[1][2][???][4][5][6]
        ↑
       ждём 3
```

Но приложение не получает байты после дырки как непрерывное продолжение потока.

TCP обещает приложению **упорядоченный поток**. Поэтому сначала нужно восстановить отсутствующие данные.

После retransmission:

```text
[1][2][3][4][5][6]
```

поток снова непрерывный и TCP может отдавать его приложению дальше.

Это важная причина **TCP Head-of-Line Blocking**.

---

# Head-of-Line Blocking в TCP

Если внутри одного TCP-соединения потерян участок потока, более поздние байты могут уже находиться у получателя, но TCP не может передать их приложению впереди пропавших байтов.

```text
получено:
[1][2][X][4][5][6]

приложение:
      ↑
не может получить непрерывное продолжение после X
```

Это особенно важно для HTTP/2, потому что несколько независимых HTTP/2 streams разделяют один TCP byte stream. Подробнее: [[03 HTTP 2 - streams и multiplexing]].

# У ОС не одна общая TCP-очередь

Для каждого TCP-соединения ядро хранит отдельное состояние, в том числе собственные send/receive buffers.

Упрощённо:

```text
Kernel

TCP connection A
├── send buffer
└── receive buffer

TCP connection B
├── send buffer
└── receive buffer

TCP connection C
├── send buffer
└── receive buffer
```

---

# Как ОС понимает, какому соединению принадлежит пакет

TCP-соединение определяется комбинацией:

```text
source IP
source port
destination IP
destination port
```

Это часто называют **4-tuple**.

Например:

```text
192.168.1.20:51000 → 203.0.113.10:443
192.168.1.21:53000 → 203.0.113.10:443
```

Оба клиента идут на серверный порт `443`, но это разные TCP-соединения.

Когда приходит пакет, ядро смотрит:

```text
IP header:
source IP
destination IP

TCP header:
source port
destination port
```

и находит соответствующее TCP connection state.

После этого payload попадает в receive buffer именно этого соединения.

# Listening socket и connected sockets

Сервер сначала создаёт listening socket:

```python
socket()
bind(...)
listen(...)
```

Например:

```text
*:443
```

Listening socket не является тем же самым сокетом, через который сервер потом читает данные каждого клиента.

После установления соединения ОС создаёт отдельный connected socket.

```text
                 listening socket :443
                    /          \
                   /            \
                  v              v
       connection A          connection B
       own buffers           own buffers
```

Поэтому один порт `443` может обслуживать тысячи TCP-соединений одновременно.

# Главное

TCP следует воспринимать так:

```text
соединение
    ↓
два независимых непрерывных потока байтов
    ↓
sequence numbers
    ↓
ACK + retransmission
    ↓
надёжность и порядок
```

Но TCP не имеет понятия:

```text
HTTP request
HTTP response
JSON message
HTTP/2 stream
```

Границы сообщений создаёт протокол прикладного уровня.
