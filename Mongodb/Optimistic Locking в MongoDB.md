
**Optimistic Locking** — подход к контролю конкурентных изменений, при котором документ заранее не блокируется.

Идея: клиент читает документ вместе с его версией, а при обновлении проверяет, что версия не изменилась.

## Пример документа

```js
{
  _id: 1,
  balance: 100,
  version: 5
}
```

Клиент прочитал:

```text
balance = 100
version = 5
```

Затем пытается изменить документ:

```js
db.accounts.updateOne(
  {
    _id: 1,
    version: 5
  },
  {
    $set: {
      balance: 80
    },
    $inc: {
      version: 1
    }
  }
)
```

После успешного обновления:

```js
{
  _id: 1,
  balance: 80,
  version: 6
}
```

## Конкурентное изменение

Допустим два клиента одновременно прочитали:

```text
version = 5
```

Первый клиент успешно обновил документ:

```text
version: 5 → 6
```

Второй клиент затем пытается выполнить запрос:

```js
db.accounts.updateOne(
  {
    _id: 1,
    version: 5
  },
  {
    $set: {
      balance: 50
    },
    $inc: {
      version: 1
    }
  }
)
```

Но текущая версия уже:

```text
version = 6
```

Поэтому фильтр:

```js
version: 5
```

не находит документ.

Результат:

```js
matchedCount: 0
modifiedCount: 0
```

Приложение понимает, что документ был изменён другим клиентом.

## Логика

```text
Client A                    Client B
   │                           │
   ├── READ version = 5        ├── READ version = 5
   │                           │
   ├── UPDATE version = 5      │
   │       ↓                   │
   │    version = 6            │
   │                           │
   │                           ├── UPDATE version = 5
   │                           │
   │                           └── FAIL
   │                               matchedCount = 0
```

## Почему называется optimistic

Система предполагает, что конфликты происходят редко.

Поэтому она не блокирует документ заранее:

```text
READ
↓
работа приложения
↓
UPDATE с проверкой версии
```

Конфликт проверяется только в момент записи.

## Compare-and-Set

Optimistic Locking основан на принципе:

```text
Измени значение,
только если текущее состояние всё ещё такое,
каким я его видел ранее.
```

То есть:

```text
IF version == expectedVersion
    UPDATE
ELSE
    CONFLICT
```

## Можно проверять не version, а само значение

Например:

```js
db.accounts.updateOne(
  {
    _id: 1,
    balance: 100
  },
  {
    $set: {
      balance: 80
    }
  }
)
```

Обновление произойдёт только если `balance` всё ещё равен `100`.

Но отдельное поле:

```js
version
```

удобнее, когда изменяться может много полей.

## Когда использовать

Optimistic Locking нужен, когда:

- несколько клиентов могут менять один документ;
    
- выполняется последовательность `READ → вычисление → UPDATE`;
    
- нельзя допустить потерю изменений;
    
- полная транзакция не нужна;
    
- конфликты происходят редко.
    
## Главное

```text
Optimistic Locking =
version field
+
условие в фильтре UPDATE
+
атомарное увеличение version
```

MongoDB не создаёт такое пользовательское версионирование автоматически. Поле `version` и обработку конфликта реализует приложение.
