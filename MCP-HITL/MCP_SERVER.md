# MCP HITL — спецификация MVP

## Назначение

Принимать запросы Codex, ожидать решение пользователя и возвращать результат **исходному вызову MCP**.

## Интерфейсы

- `POST /mcp` — транспорт MCP (в том числе `tools/call`); обслуживается MCP Python SDK.
- MCP-инструмент `hitl.request(type, title, description)` — единственный инструмент агента.
- `POST /internal/answer` — ответ от Telegram-бота: `request_id`, `answer`; ответ сервера: `accepted: true/false`.

Допустимые типы: `approval`, `question`, `manual_action`.

## Функции

**`hitl_request(type, title, description)`**
1. Проверяет аргументы по схеме инструмента.
2. Генерирует UUIDv4 и создаёт `asyncio.Future`.
3. Регистрирует `pending[request_id] = future`.
4. Выполняет `await send_to_bot(...)` — `POST /internal/messages`.
5. Выполняет `await future` с внутренним таймаутом 3550 секунд.
6. Возвращает агенту ответ либо `HITL_TIMEOUT`, всегда удаляет запись из `pending`.

**`receive_answer(request_id, answer)`**
1. Проверяет авторизацию внутреннего запроса.
2. Находит активный Future в `pending`.
3. Если запрос активен — вызывает `set_result(answer)` и возвращает `accepted: true`; иначе `false`.

## Результаты

- `{"status":"answered","answer":"..."}` — текстовый ответ.
- `{"status":"approved"}` / `{"status":"rejected"}` — разрешение.
- `{"status":"completed"}` / `{"status":"unable"}` — ручное действие.
- `{"status":"timeout","error_code":"HITL_TIMEOUT"}` — время истекло.

## Ограничения

- Python, MCP Python SDK, FastAPI (внутреннее HTTP API), Docker.
- Один процесс MCP; несколько параллельных запросов через `asyncio`.
- Нет SQLite/Redis: активные запросы существуют только в `pending` (RAM).
- Время ожидания HITL — **3550 с**, лимит вызова в Codex — **3600 с**.
- При отправке сообщения с ошибкой вызов завершается ошибкой и очищает `pending`.
- При перезапуске сервера ожидающие вызовы теряются. Просроченные/неизвестные ответы отклоняются.
- Внутренние HTTP-вызовы защищены `INTERNAL_API_TOKEN`.

**Статус:** проектный контракт; реализация и проверка длительного MCP-вызова в Codex ещё не выполнены.


## Дополнения к жизненному циклу запроса

- Первый валидный ответ побеждает: для одного запроса только один ответ может получить `accepted: true`.
- Сервер проверяет, что запрос ещё активен, Future не завершён и не отменён, а ответ соответствует типу исходного запроса: `approved` / `rejected` для `approval`, `answered` с текстовым `answer` для `question`, `completed` / `unable` для `manual_action`.
- Проверка активности и принятие ответа должны исключать принятие двух конкурентных ответов. Повторные, поздние и не соответствующие типу ответы не завершают Future и получают `accepted: false`.
- Завершённый или отменённый запрос нельзя открыть повторно. Это правило не определяет новый интерфейс отмены; способ инициирования отмены остаётся отдельным вопросом проектирования.
- После `accepted: true` бот удаляет кнопки сообщения. Удаление кнопок не заменяет серверную проверку повторных ответов.

## Дополнения к контексту и ограничениям

- Telegram должен показывать имя агента (`agent_name`) и роль (`agent_role`), когда они доступны. Источник этих данных и способ их передачи между Codex, MCP и ботом ещё предстоит определить; гарантированное автоматическое получение идентичности субагента не предполагается.
- Существующая схема `hitl.request(type, title, description)` сохраняется до отдельного решения о передаче идентификационных данных.
- Восстановление доставки, включая неоднозначный результат HTTP-вызова, отложено; существующее поведение при ошибке отправки остаётся в силе.
- Таймаут ожидания остаётся **3550 секунд**. Возможный более короткий таймаут для будущего тестирования не меняет текущий контракт.
