# Codex HITL — MVP

## Цель

Позволить Codex и его субагентам запрашивать решение пользователя и продолжать работу после ответа. Пользователь взаимодействует через Telegram.

## Компоненты

1. **Skill `hitl`** — описывает агенту, когда и как вызвать `hitl.request`.
2. **MCP HITL Server** — принимает вызов, создаёт UUID + `Future`, ожидает ответ и возвращает его тому же вызову Codex.
3. **Telegram Bot Server** — отправляет сообщение с нужными кнопками, принимает ответ, передаёт его MCP.

Один репозиторий, два Docker-контейнера (MCP и Bot), запуск через Docker Compose.

## Сценарий

```text
Codex → POST /mcp → hitl.request(type, title, description)
                   → UUID + pending[UUID] = Future
                   → POST Bot /internal/messages
                   → Telegram → пользователь
                   ← POST MCP /internal/answer
                   ← Future.set_result(answer)
Codex ← результат исходного вызова
```

## Правила MVP

- Типы: `approval`, `question`, `manual_action`.
- У агента только три входных поля; он не знает UUID, Telegram и механизм ожидания.
- MCP ждёт максимум **3550 секунд**; Codex ограничен **3600 секундами**.
- При `HITL_TIMEOUT` субагент прекращает заблокированную работу и передаёт ошибку родителю; родитель решает, что делать дальше.
- Все активные запросы хранятся в RAM, без SQLite, Redis и очередей.
- При перезапуске MCP ожидания теряются. После завершения запроса поздний ответ отклоняется.
- Внутренние HTTP-интерфейсы защищаются токеном; Telegram-ответы принимаются от разрешённого пользователя.

## Дополнительные согласованные решения

1. Первый валидный ответ принимается окончательно. Завершённый или отменённый запрос нельзя открыть повторно.
2. На запрос `question` пользователь отвечает текстом через прямой ответ (`reply_to_message`) на соответствующее сообщение Telegram.
3. Текстовые ответы на сообщения типов `approval` и `manual_action` бот игнорирует и удаляет из чата; такие ответы не завершают запрос.
4. После подтверждения приёма ответа сервером MCP бот удаляет кнопки из соответствующего сообщения Telegram.
5. Восстановление доставки и обработка неоднозначных результатов доставки отложены за рамки текущего MVP.
6. Таймаут **3550 секунд** остаётся без изменений. Возможное сокращение таймаута при тестировании рабочей реализации является будущим решением и не меняет текущую спецификацию.
